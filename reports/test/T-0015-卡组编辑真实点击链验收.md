## 2. 之前为什么不测这条路

D-141 / D-143 的验证方式是「往 `room:create` 里注入 30 个 defId」——
它证明的是**服务端校验**正确，绕过了编辑页。于是编辑页上的三个锚点
（`deck-total` / `use-deck` / `deck-in-use`）从来没有被任何用例点过，
「玩家点得通吗」这个问题一直没人回答。

## 3. 写测试时撞到的 bug：昵称会丢

第一次跑挂在「建房后拿不到房间码」。页面快照显示昵称输入框是**空的**：

| 环节 | 行为 |
| --- | --- |
| 输入昵称 | 只改 React state |
| 点「编辑卡组」 | HomeScreen 卸载 |
| 点「返回」 | HomeScreen **重新挂载**，从 `localStorage['fc.nickname']` 初始化 → 空 |
| 点「创建房间」 | `nickname` 为空 → 服务端按 schema 拒绝 |

昵称原本只在「建房 / 加入成功」时才写入 localStorage，所以「输名字 → 去看卡组 → 回来」就丢。
**这不是测试写错，是真实用户路径上的问题**（改卡组是很自然的动作）。

修法：`onChange` 即时落盘，与 `fc.activeDeckId` 的处理方式一致。

## 4. 新增 E2E 覆盖

| 步骤 | 断言 |
| --- | --- |
| 编辑页新建卡组 | 出现 `30/30` 之前的空态 |
| 10 张卡各点 3 次 | `deck-total` 显示 **30** |
| 点「设为开局卡组」 | 出现「开局使用中」（`deck-in-use`） |
| 返回主界面 | 「我的卡组」下拉已选中该卡组（非空值） |
| 建房 → 加入 → 双方准备 | 进入对战桌 |
| 开局手牌 | **每一张**都属于自建卡组的 10 种卡名；混进默认卡组的卡即失败 |

选卡刻意跨两个阵营（炎刃 5 种 + 霜律 5 种），这样「用阵营默认卡组」与「用自建卡组」
在起手上几乎必然能区分开。
