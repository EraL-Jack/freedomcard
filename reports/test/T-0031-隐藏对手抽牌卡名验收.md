## 2. 结论

**可发布（第三轮 · 覆盖完整口径后的最终判定）。**

两条子项在**最终快照**（§1 哈希）上都有实测证据，且都不是「看起来对」，而是「旧实现下会红、新实现下会绿」：

- **`deck → hand`（抽牌）**：人机局 / 移动抽屉 / 双端联机两侧 / 连开 8 局，`电脑 抽到` 行数恒为 0，对手行恒为「抽了 1 张」；自己的抽牌恒为「抽到 <卡名>」，且卡名与 DOM 手牌交叉一致（§3~§5，本轮不重做）。
- **`deck → cost`（充能）**：对手 `电脑 最高费用 → 3` 后面紧跟 **`电脑 充能 1 张` ×2**、不含卡名；自己的自动充能仍是 **`炎刃战术 置入费用区` / `炎刃军师 置入费用区`**，自己的**手动**充能（点手牌 → 点「充能」）仍是 **`炎刃骑士 置入费用区`**（§15.2，页面原文逐行照录）。
- **公开区没被误伤**：同一个窗口里 `霜律长枪兵 登场`、`霜律新兵：费用区 → 弃牌区`、`裁决 2 vs 0 → 防守方破坏` 都照旧（`展示：炎刃卫士` 这条原文来自第二轮窗口 §14.3，第三轮那两局没触发展示，由单测 `对手展示仍然念卡名` 兜底）—— 分叉点是「是不是牌库顶 + 是不是我」，不是「整段静音」。
- **回归面（第三轮我自己重跑，不引用工程师/主理人数字）**：单测 **464**（core 237 / server 160 / **client 67**）、E2E **58 passed（4.7m）**、typecheck **0 错**、lint **0 错**（§7）。充能那半的反向验证：只把 `src/log.ts` 退回 HEAD 后，**只含充能断言的 2 条单测红**（实际值 `霜律终裁 置入费用区`）、**页面原文里当场出现对手卡名 `星轨斥候 / 星轨弓手 置入费用区`**（§15.4）。

**结论的性质必须写清（否则会被误读成「藏住了」）**：这次修的是**被动暴露**，不是**可获得性**。对手费用区点开浮窗**仍然看得到卡面**（我实测点了：`费用区 2 ›` → 浮窗 2 张 → `星轨斥候` / `星轨弓手`），而且同一回合里被支付的牌会以 `霜律新兵：费用区 → 弃牌区` 把名字说回来（§15.6）。两者都是既有设计（费用区 `content='float'`、弃牌区本就公开可查）与服务端未脱敏同一类，不构成本分支的阻塞，但报告里不许把它们说成「信息被藏住了」。我对「被动推送 vs 主动查看」这个论证的独立判断见 §15.5。

残留项里唯一值得 Era 知道的仍是**架构级限制**：服务端快照与事件未脱敏（`pipeline.ts` 的 `Snapshot.state` 就是全量 `GameState`），DevTools 仍能读到对手手牌。这不是本分支引入的，ADR-0065 已写成已知限制并说明「真防作弊需另立需求」—— 我同意，不作阻塞。

> 上一版（第一轮）我判的是**阻塞**，理由是「充能未实现，只修了抽牌就留下同款漏洞」（当时的页面原文见 §14.2）。工程师随后实现了 `from === 'deck' && to === 'cost'` 分支并补了 `meRef` 同步，第三轮在最终快照上复验通过，**阻塞结论已撤销**。撤销的依据是本节列出的实测，不是「他们说修了」。

## 3. 口径 1 · 对手抽牌不出现卡名

**口径**：战报里对手（含人机「电脑」）的 `deck → hand` 只显示「抽了 1 张」，不含任何卡名。

| # | 场景 | 实测（战报原文片段） | 判定 |
| --- | --- | --- | --- |
| 1 | 人机局 · 起手（桌面 1280） | `电脑 抽了 1 张` ×5，`电脑 抽到` **0 行**（战报 23 行） | 通过 |
| 2 | 人机局 · 打到第 5 回合（含 AI 每个回合的抽牌） | `电脑 抽了 1 张` ×**9**，`电脑 抽到` **0 行**（战报 157 行） | 通过 |
| 3 | 人机局 · 移动 390×844（走日志抽屉） | `电脑 抽了 1 张` ×7，`电脑 抽到` **0 行** | 通过 |
| 4 | 双端联机 · **Host 视角**看对手 Guest | `Guest 抽了 1 张` ×5，`Guest 抽到` **0 行** | 通过 |
| 5 | 双端联机 · **Guest 视角**看对手 Host | `Host 抽了 1 张` ×8，`Host 抽到` **0 行** | 通过 |
| 6 | 人机局连续开局 **8 次** | 8/8 次 `foeNamed = 0`，`foeAmount = 5`（起手 5 张逐张成行） | 通过 |

> 第 4/5 条是本轮最有力的对照：**同一批抽牌**在 Host 页面记为「Host 抽到卡名」、在 Guest 页面记为「Host 抽了 1 张」，两侧互为镜像，说明分叉点是 `ownerId === viewer` 而不是「谁的页面」碰巧。数字也对得上：Host 起手 6 + 后续 2 = 8 行，Guest 起手 5 行。

**副作用（如实记录）**：起手会**连出 5 条**「电脑 抽了 1 张」（`draw:completed` 不带张数，逐张 `card:moved` 各成一行）。观感偏吵，但不是泄露，ADR-0065 已把它列为代价。

## 6. 反向验证（确认用例不是假绿）

## 9. fail-closed 的副作用分析（`viewer` 默认 `null`）

**结论：正常链路里**不可触发**；只有「刷新重连」这一条窄路上存在理论窗口，且方向安全（宁可少显示，不会多泄露）。不构成缺陷。**

### 9.1 时序事实（代码位置）

| 事实 | 位置 |
| --- | --- |
| `me` 是 **state**（异步） | `useRoom.ts:231` `const [me, setMe] = useState<PlayerId \| null>(null)` |
| `meRef.current` 在 **passive effect** 里同步 | `useRoom.ts:418-421` `useEffect(() => { namesRef.current = names; meRef.current = me; }, [names, me])` |
| 建房 / 加入的 ack 里 `setMe(...)`，**同时**同步写 `stateRef.current` | `useRoom.ts:628-647`（`acceptIdentity`，`:639` `setMe`，`:642` `stateRef.current = res.snapshot.state`） |
| 重连的 ack 里 `setMe(playerId)`，也同步写 `stateRef.current` | `useRoom.ts:798-814`（`:804` `setMe`，`:807` `stateRef.current`） |
| 事件到达即入队并启动播放 | `useRoom.ts:560-582`；`pump` 里逐条 `describeEvent(e, namesRef.current, next, meRef.current)`（`:457`）|

### 9.2 四条链路分别判断

| 链路 | `setMe` 与「第一批含抽牌的事件」之间的间隔 | 判断 |
| --- | --- | --- |
| **人机局**（建房 → 准备） | `setMe` 发生在**建房 ack**；对局与起手抽牌发生在**用户下一次点击「准备」之后**（两个独立 user event，中间必然有过 render + effect flush） | **窗口不存在**。实测 8/8 次自己的抽牌都是卡名 |
| **双端联机**（建房 / 加入 → 双方准备） | 同上，`setMe` 在建房/加入 ack，开局要等双方各点一次「准备」 | **窗口不存在**。实测 Host 8 行、Guest 5 行全带卡名 |
| **换牌阶段 / BO3 下一局** | 不重新 `setMe`（只有 `leave` 会置 `null`）；`meRef` 一直有值 | **窗口不存在** |
| **刷新 / 断线重连** | `setMe(playerId)` 与 `stateRef.current = snapshot` 在**同一个 ack 回调**里；服务端随后补发 `lastSeq` 之后的增量事件 | **理论窗口存在**：`meRef` 要等 passive effect 才更新，而 `stateRef` 已经同步就绪，若「快照/事件包」与 ack 落在**同一个 JS 任务**里被处理，`pump` 会读到 `meRef === null` |

### 9.3 这个窗口的实际可达性与后果

- **可达性**：`socket.ts` 用 `transports: ['websocket', 'polling']`。WebSocket 下每个 packet 是独立 message 任务，React 的 passive effect 调度任务通常在下一个 socket message 之前先跑（同为宏任务、FIFO），窗口在实践上基本关闭；**polling 回退**时一个 HTTP 响应里可能带多个 packet、在**同一任务内同步**处理 —— 窗口才真正打开。**我无法用界面操作稳定复现**（重连时通常本就没有「自己的抽牌」事件要补发），故只能作代码级判断，不宣称实测。
- **后果**：只有「自己的抽牌行退化成『抽了 1 张』」这一种，属于**过度隐藏**，不泄露任何信息，且只在重连那一瞬的增量批次里出现。
- **如果要彻底关掉这个窗口**（建议，非阻塞）：在 `acceptIdentity` / 重连 ack 里**同步**写 `meRef.current = res.playerId`（与 `stateRef.current` 同一处），一行代码即可，代价为零。→ **第三轮已落地**：`useRoom.ts:655` / `:823` 两处都写了，见 §15.3。

> 另外核对过一处易漏点：`card:moved` 的 `playerId` 由引擎统一注入（`core/src/ops.ts:36` `ev(at, 'card:moved', { playerId, uid, from, to, … })`），所以「`ownerId === undefined` 导致把**自己的**抽牌误判成对手」在实践中不会发生；即便发生，也是走向隐藏，不是泄露。

### 15.5 「被动推送 vs 主动查看」这个论证站不站得住（我的独立判断）

**先核事实**（这才是关键，论证本身好不好看是次要的）：

| 检查 | 实测 | 结论 |
| --- | --- | --- |
| 对手**手牌**区 | 纯文本 `对方手牌 3 张`；区内 `[data-testid="card"]` = **0**；点它**不弹**浮窗 | 手牌：**连主动也看不到** |
| 对手**卡组**区 | `content='count'`；点它不弹浮窗 | 卡组顺序：主动也看不到 |
| 对手**费用**区 | `费用区 2 ›` → 点击 → `zone-float` 可见、内含 **2 张**、原文 `费用区2 张 关闭 星轨斥候 随从 费 0 力 1 伤 1 星轨弓手 随从 费 0 力 2 伤 1` | 费用区：**主动点开就能看到卡面** |

所以：**原注释里「桌面上看不到对手的费用区 ⇒ 战报比桌面更公开」这个论证是错的**（费用区 `content='float'`，`TableScreen.tsx:1916`；`inspectable = content==='float' && cards.length>0`，`:434`）。工程师把它改掉了，改成「战报是自动推送，不得把需要主动点开才看得到的私有流向直接刷给你」，并把「主动点开仍可见」记为已知限制 —— **改对了，而且是往保守方向改**（把话说小了，不是说大了）。

**我的判断：论证可用，但要按「减弱版」使用，不能按「隐藏」使用。**

- **成立的部分**：抽牌子项的类比是硬的 —— 手牌区连点开都看不到，战报念卡名就真的是「比桌面更公开」，这一条毫无争议。充能子项**不能**沿用这个类比（同样是这两张 `星轨斥候 / 星轨弓手`，我在浮窗里点开就看得到），工程师没硬套，而是把依据退回到 Era 的明写口径（「`deck → cost` 时对手只记『充能 N 张』」）—— 需求本身就是依据，不需要再从「谁更公开」推一遍。**这一步是正确的处理**，也正是这一段最容易糊弄过去、但实际没糊弄的地方。
- **要打折的部分**：「战报比桌面更公开」在充能这条上**不成立**。准确的说法是「战报比桌面**更主动**」：它消除的是「不点也能知道」，不是「能不能知道」。所以这条修复的价值是**不再白送**，不是**藏住了**。「隐藏对手充能卡名」这个简称会让人高估它，报告/ADR 里建议写成「不再被动推送对手的牌库顶流向」，并保留两句已知限制：① 费用区浮窗点开仍可见；② 同回合内被支付的牌会以 `X：费用区 → 弃牌区` 回到战报（§15.6）。
- **一句话结论**：论证的事实前提已经修正到位，逻辑从「更公开」降级成「更主动」，**站得住但只能撑起一个较小的结论**；撑不起「信息已经藏住」。ADR-0065 补充段（`logs/DECISIONS.md:1673-1683`）现在的写法（「战报是自动推送，不得把需要主动点开才看得到的私有流向直接刷到眼前」+「主动点开仍能看到对手充了什么牌属已知限制」）与我的判断一致 —— 我核过原文，不是我替它总结的。
  - 两处小的事实校正（不影响结论，供写 ADR 的人顺手改）：① ADR 说「手牌区是 `content='count'`」，实际手牌区**根本不是一个 `ZoneBox`**，而是纯文本 `<section>对方手牌 N 张</section>`（`TableScreen.tsx:1876-1878`），比 `count` 还更彻底；② ADR 的已知限制只写了「主动点开仍可见」，**没写** §15.6 那条「同回合被支付的牌会被战报重新点名」。

### 15.6 本轮新发现：`cost → graveyard` 会把刚隐藏的卡名说回来（残留风险，非缺陷）

同一局里，电脑充能之后进入抽牌/主要阶段，战报新增：

```
阶段：重置 → 抽牌
电脑 抽了 1 张
电脑 抽了 1 张
draw:completed
阶段：抽牌 → 主要
霜律新兵：费用区 → 弃牌区      ← 刚被隐藏的两张之一，名字回来了
电脑 消耗 1 张费用
霜律长枪兵 登场
```

归属推导（不靠「看起来像」）：电脑该回合进充能阶段**之前**费用区为空；自动收入 2 张（即那两条 `电脑 充能 1 张`）；抽牌抽到的两张进的是**手牌**，不会进费用区。所以此刻从费用区离开的 `霜律新兵` 必然是那两张之一。代码路径是 `log.ts:191` 的兜底分支（`cost → graveyard` 不在任何特殊分支里，走 `${name}：费用区 → 弃牌区`）。

为什么不判缺陷：① Era 的表里「离手即公开」，且弃牌区本身 `content='float'` 可查；② 只在该牌真的被支付/弃置时发生，不构成「白送」；③ 要真藏住，得让「费用区里的牌在对手眼里没有身份」，属服务端脱敏范畴（§10 #1）。但它把边界说清了：**这是「事件级」隐藏，不是「状态级」隐藏** —— 任何「隐藏已实现」的表述都要带上这个限定。
