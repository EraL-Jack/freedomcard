## 3. 三个取舍

### 3.1 默认值必须是「现状」（散列），不能是「固定第一套」

要求里写的是「可选」，不是「改默认」。把默认改成固定一套，等于把原本能撞到三套的
玩家静默降级成只看到一套 —— 却没有一个人会报 bug，因为「看起来能用」。

### 3.2 schema 用 `z.string()` 而不是 `z.enum`

定稿写明「非法 slug 走缺省（不拒建房）」。`z.enum` 会把非法值变成 400，
玩家看到「参数不合法」而不知道是哪个字段 —— 而 `opponentDeck` 只是偏好，
**建房失败的成本远高于「对手换了个人」**。白名单校验下沉到房间层，落空即散列。

### 3.3 控件并进按钮行，不单独占一行

见 §4 —— 这不是审美选择，是 `home-layout.spec.ts` 逼出来的。

## 4. 一次真实的红：新控件把「编辑卡组」顶出首屏

第一版把下拉放成独立一行（`text-xs` 标签 + 全宽 select ≈ 66px），全量 E2E 当场红：

```
Error: 桌面视口下首页整体溢出高度
Expected: <= 0
Received:    44
```

**这条红恰恰是本需求的验收口径之一**（「多一行不挤压按钮」）的桌面版。
1366×768 只剩 22px 余量，任何独立一行都放不下，缩小字号也救不回来。

修法与 issue #116（「赛制 + 时限并成一行」）同源：**下拉与按钮并成一行**，
行高由按钮决定（下拉更矮），新增高度为 **0**。

> 顺带把选择结果写进按钮文案（`人机对战（对手：炎刃）`）—— 下拉只有 96px 宽、
> 只放短词，若按钮不跟着变，玩家没有地方确认自己选的是哪一套。E2E 已守这条。

## 5. 红绿证据（注入法）

| 断言 | 注入 | 红 |
| --- | --- | --- |
| 协议保留 `opponentDeck`（单测） | 字段名改成 `opponentDeckTypo`（zod 静默 strip） | `expected undefined to be 'frost'` |
| 选霜律 → 对手是霜律（E2E） | 同上 | `Expected substring: "霜律裁决官" / Received: "…星轨观测者…"` |
| 首页不溢出（E2E） | 下拉放成独立一行 | `Expected: <= 0 / Received: 44` |

第二条是最有价值的一条：它把「**字段名写错 → 客户端传了、服务端永远收不到 →
界面正常但行为错**」这条本仓库踩过三次的坑（`payload` / `deck` / `commander`），
第一次钉成了自动化断言。任何新增协议字段都该补一条「保留」用例。
