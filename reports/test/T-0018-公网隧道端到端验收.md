## 1. 结论

游戏已能从公网完整跑一局。真实浏览器、真实公网路径、日本节点中转，**全量 20/20 通过（4m 16s）**。

这条链路此前只有「本机生产形态 20/20」（T-0017），缺的正是**跨网这一层**：隧道是否透传 WebSocket、
延迟是否可接受、有没有哪个环节依赖回环才成立。现在这三件事都有了实测答案。

## 2. 链路构成

| 环节 | 实际情况 |
| --- | --- |
| 客户端 | Playwright Chromium，`baseURL=http://frp-cup.com:57732` |
| 隧道 | SakuraFrp `TCP` 隧道，节点 `frp-cup.com`（日本），客户端 `frpc 0.51.0-sakura-15` |
| 限速 | 10 Mibit/s（服务端下发的该隧道限速） |
| 回源 | `127.0.0.1:3100`（**不是 `localhost`**） |
| 服务 | Fastify 单端口：页面 + `/socket.io` 同源 |
| 协议 | 全站 HTTP，Socket 走 `ws://`（同源，无混合内容问题） |

### 3.2 房间流程（第一轮）

`4 passed (32.6s)` —— 建房 / 加入 / 满员拒绝 / 重连 / 离开 / 三档视口全通。

### 3.3 全量（第一轮）

**19 passed / 1 failed (5.1m)**。

失败项：`combat.spec.ts:84 攻击对方指挥官`，卡在 `helpers.ts:37` 等 `ready` 按钮，
`timeout: 10_000` 到点。同一用例**单跑通过（29.4s）**，全量里另外 18 条也通过。

判定为**公网延迟下的等待边界**，不是功能缺陷。依据：
1. 同一条用例本地生产形态通过（T-0017）；
2. 单跑公网通过；
3. 失败点是「等界面出现」，不是业务断言。

修法：把 `helpers.ts` 里写死的 10s / 15s 换成可配置的 `WAIT`
（`E2E_WAIT_MS` 覆盖，本地仍 15s），因为公网单步要 3~33s。

## 4. 延迟对比（同一套用例）

| 形态 | 总耗时 | 单条典型 |
| --- | --- | --- |
| 本机生产（T-0017） | 2m 0s | 0.4 ~ 24s |
| 公网日本节点 | 4m 16s | 3 ~ 33s |

**约 2 倍**。其中依赖「多步往返」的用例（战斗、拖拽、回合推进）最慢（22~33s），
纯静态观察类（表单校验、视口）几乎不受影响（2.9~3.1s）——
说明开销主要来自每次交互的往返 RTT，而不是带宽。

## 6. 复现与恢复

```bash
# 1) 起服务（正式形态，不带种子）
cd app/scripts && serve-public.cmd

# 2) 起隧道（新版客户端，2023 自带的那份无法命令行启动）
app/.tmp/frpc.exe -f <访问密钥>:<隧道ID>

# 3) 验证
cd app/packages/client
PUBLIC_URL=http://frp-cup.com:57732 E2E_WAIT_MS=30000 \
  pnpm exec playwright test --config=playwright.public.config.ts
```

**注意**：隧道地址与端口由服务端分配，隧道重建后可能变化，以 `frpc` 日志里
`使用 >>host:port<< 连接你的隧道` 那行为准。

## 7. 遗留

- 服务与隧道都是**手动拉起**的进程：关窗口、重启电脑都会断。恢复就是上面两步。
- 隧道限速 10 Mibit/s，给几个人玩够用；人数上来会先卡在首屏 JS（465 kB）。
- `app/.tmp/` 已加入 `.gitignore`，穿透客户端二进制不入库。
