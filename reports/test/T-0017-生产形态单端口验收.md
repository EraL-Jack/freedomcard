## 4. 公网通道的失败与排除

同一天用**同一套用例**指向公网隧道地址，4/4 失败，全部卡在「服务端已连接」不可见。

排除过程：

| 检查 | 结果 | 说明 |
| --- | --- | --- |
| `GET /`（公网） | 200 | 入口页可达 |
| `GET /assets/index-D9PD6kQF.js` | **502** | 465 kB 的 JS 拿不到 |
| `GET /health` | **502** | 连健康检查也挂 |
| 本地 `127.0.0.1:3100/health` | 200 | 服务本身正常 |
| `socket.io` 握手（隧道初期） | 200 + `upgrades:["websocket"]` | 通道刚建好时是通的 |
| `socket.io` 握手（20 分钟后） | 502 `no tunnel` | 通道自行失效 |

**判定：失败发生在通道层，不是游戏。** 依据是同地址早期 200、后期全 502，
且本地同端口 4/4 通过。免费隧道（`localhost.run`）承载 465 kB 首屏包时稳定性不足，不适合作为发布通道。

### 3.2 多房间并发（D-179，2026-10-20 补）

此前所有 E2E 都是 `workers=1` 串行 —— 服务端**从未被多个房间同时访问过**。
用 `--workers=4` 让四个进程并行跑不同 spec：

| 模式 | 结果 | 耗时 |
| --- | --- | --- |
| `workers=1`（默认） | 29/29 | 2m 10s |
| `--workers=4` | **29/29** | **43.5s** |

说明两件事：

1. **房间隔离正确**：四个房间同时建房、开局、出牌、认输，没有串房或状态污染；
2. **加速约 3 倍**，说明服务端在这点并发下没有明显瓶颈。

边界：`workers` 是**文件间**并行，单个 spec 内部仍串行（房间里两方的时序必须可控）。
真正的同房间并发（两人同时出牌）由引擎的 `seq` 幂等与 `pendingChoice` 串行化保证，另有单测覆盖。
