## 3. 三个取舍

### 3.1 #155 为什么不用「补一份快照」

客户端把 `game:snapshot` 当作**新起点**，收到即 `queueRef.current = []`。
每次操作补快照 = 每操作一次掐断一次动画，而逐条播放是 Era 明确要的节奏。
改用只带一个数的 `game:timer`：语义上是「状态推送」，代价上不碰播放队列。

### 3.2 #155 为什么不用「归零时提示已超时」

那是把矛盾遮住：服务端还在接受操作，界面却说超时了。
issue 自己也写「建议 1 或 2，别用 3 糊过去」—— 本轮选了 1 的形状、2 的代价。

### 3.3 #156 为什么改文案层而不是引擎

推荐方案 A 要引擎不再产出打脸的 `combat:resolved`。但旧 `replay.json` 里记着这条事件，
引擎不产出它，回放校验会在第一步分叉（D-159 的 hash 链逐条比对）。
所以引擎零改动，客户端按「目标是否在 `commander` 区」改文案 —— 回放格式与 core 风险都为 0。

## 5. 一条预期内的红

全量首跑 `combat.spec.ts` 打脸用例红在 `toContainText('裁决')` —— 它正是在断言
**本轮要删掉的那句话**。按新口径改写为：

```ts
await expect(log).toContainText('直击指挥官');
await expect(log, '打脸不该出现「裁决 X vs 0」').not.toContainText('vs 0');
```

第二条比原来**更强**：它把 #156 的 bug 本身钉成了断言（改回去就红）。
