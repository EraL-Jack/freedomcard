## 1. 结论

这是从 T-0008 起就挂在「已知缺口」里的一条：规则允许在待定选择期间认输，界面却点不到。
修法是界面让位于规则 —— 底部操作区抬到浮层之上，并把此刻**必然被拒**的按钮藏掉。

判定**可发布**：纯界面层级与可见性调整，不触碰引擎、协议与回放。

## 2. 缺口成因

| 层 | 行为 |
| --- | --- |
| 引擎 | `baseGuard` 在 `pendingChoice` 非空时**只放行** `effect:choose` 与 `concede` |
| 界面 | `ChoiceOverlay` 是 `fixed inset-0 z-50` + 半透明底，把底部操作区整块盖住 |
| 结果 | 规则允许认输、玩家点不到；必须先「放弃」退出选择才行 |

可见这条缺口的本质不是「没做」，而是**两层口径不一致**：引擎认为可以，界面认为不行。

## 3. 改动

| 位置 | 改动 |
| --- | --- |
| `footer`（底部操作区） | 加 `relative z-[60]`，压在浮层 `z-50` 之上，按钮重新可点 |
| 派生量 `choiceOpen` | 我方有挂起选择时为真；用它隐藏「推进阶段」「结束回合」 |
| 文档 | `README §11.5` 补一条验收判据（浮层期间可认输、推进/结束回合不显示） |

为什么把「推进阶段 / 结束回合」藏掉而不是留着：这两个 Intent 在 `pendingChoice` 期间
**必然被守卫拒**，留着就是「点了没反应」—— 与 Era 2026-10-19「不可操作的按钮不展示」相悖。
「认输」则相反：它是守卫明确放行的两个动作之一。

## 5. 未被自动化覆盖的部分

| 项 | 原因 |
| --- | --- |
| 「浮层期间点认输」这条实际点击链 | 需要在 E2E 里构造出一个确定的待定选择（依赖固定种子的具体牌序），成本高；本轮的保证来自 z-index 与 `pointer-events` 的静态推理 |
| 浮层与操作区在小屏上的视觉重叠 | 只做了桌面 Chromium 验证，移动端需 Era 实机看一眼：如果底部按钮压住浮层内容，需要给浮层加底部内边距 |
