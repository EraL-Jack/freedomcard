## 2. 做了什么

`app/packages/server/src/tools/replay-verify.ts`，一个只读工具，三步判定：

1. 用记录里的 `setup` 重建开局状态，`stateHash` 必须等于 `initialHash`；
2. 逐条重跑 `intents`，第 i 步哈希必须等于 `hashChain[i]`；
3. `--events` 时再按 JSON 深比较每步产出的**事件序列**。

退出码：`0` 一致 / `1` 有差异（指出第几步、哪个哈希） / `2` 文件不可用。

底层复用 `core.replay`（早就写好了，缺的一直是「读文件 + 重建 + 比对」这一层）。

## 4. 过程中发现的坑（值得记）

第一版把时间源写成 `startedAt + step * 1000`（起点 + 步长），结果：**开局哈希对得上，第一步 `game:start` 就分叉**。

原因：`startRule` 把 `ctx.now` 写进了 `state.startedAt`，而原局的 `ctx.now` 是真实时钟 ——
与 `startedAt`（Recorder 创建时刻）差了 631ms。用固定步长重放，状态自然不同。

修法：**时间源取记录里该步第一个事件的 `at`**（原局真实时间），回放立刻一致。

这条已写进 `README-运行说明.md` §7.2，避免下次又按「起点 + 步长」写。

## 7. 补充：BO3 多局（D-175，同日）

首次全量扫描时发现 **4 份历史记录不可重放**，症状一致：
`第 3 步被拒绝：game:start —— 对局已开始`。

根因：`markStart` 每局都会调，而 `intents/events/hashChain` 是继续往同一数组里 push 的 ——
BO3 记录里就出现了两个 `game:start`。

修法：`ReplayRecord` 增加 `rounds`，`markStart` 先把上一局归档再清空三数组；CLI 改为逐局重放。

复验：跑 BO3 三局用例产生新记录（`rounds: 2` + 顶层 1 局），
`replay:verify --events` → **3 局共 7 步逐帧一致**。

> 修复前的 4 份历史文件仍然不可重放 —— 数据本身已经混了，无法回溯修复。

至此本文 §5 里的「BO3 多局覆盖」一项已覆盖。
