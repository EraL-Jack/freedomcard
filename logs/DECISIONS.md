## ADR-0001 · 采用 pnpm monorepo + 前后端同构共享层

- 状态：已采纳
- 日期：2026-10-12
- 背景：规则逻辑必须在客户端与服务端行为一致（否则必然 desync），且后续要持续扩展规则。
- 决策：使用 pnpm workspaces，拆 `shared` / `core` / `server` / `client` 四个包；`core` 为纯 TS 纯函数包，前后端同构复用同一份规则代码。
- 理由：
  1. 规则只有一份实现，从根本上消除双端逻辑漂移。
  2. 包级依赖可视，违反分层（如 `core` 引 `server`）会在编译期报错。
  3. 单测只需跑一遍 `core`，成本最低。
- 被否方案：
  - 前端独立、后端独立各写一份规则 → 双份维护，必然不一致。
  - 单包大杂烩 → 无法阻止逻辑泄漏到组件里。
- 影响：所有跨包引用走包名（`@app/core`），禁止相对路径跨包。

## ADR-0002 · 采用服务器权威 + 客户端只发意图

- 状态：已采纳
- 日期：2026-10-12
- 背景：需要联网实时对战、弱客户端（网页，含移动端），且要防作弊、支持断线重连与回放。
- 决策：客户端只提交 `Intent`，服务端校验并执行规则、产出 `GameEvent[]` 并广播；客户端只做 `reduce` + 渲染。服务端每次广播附带 `serverSeq` 与 `stateHash`。
- 理由：
  1. 弱客户端不需要跑规则，省电省算力，移动端体验可控。
  2. 作弊面收敛到服务端；回放、观战、重连由同一事件流自然获得。
  3. `stateHash` 可实时发现双端分歧，把「隐性 bug」变成「可观测事件」。
- 被否方案：
  - 客户端权威（P2P 同步）→ 易作弊，移动端算力不一致导致分歧，无权威回放。
- 影响：
  - 客户端禁止本地结算；所有网络 payload 必须在 `shared` 定义并由 Zod 校验。
  - 客户端必须有 `desync` 上报通道。

## ADR-0003 · 事件溯源 + 纯函数规则 + 插件注册表（原子化基石）

- 状态：已采纳
- 日期：2026-10-12
- 背景：需求明确要求「各操作原子化构建、相互解耦，便于后续规则扩展」。
- 决策：
  1. 状态只能由 `reduce(state, event)` 演进，不可直接改写。
  2. 规则处理器固定签名 `(state, intent, ctx) => Result<GameEvent[], Rejection>`，纯函数，无 IO / 时间 / 随机副作用。
  3. 所有规则集中在注册表 `rules[type]`，一个机制一个文件；新增机制 = 新增文件 + 注册一行。
  4. 随机走种子 RNG，时间只取服务端事件时间戳。
- 理由：
  1. 纯函数可单测、可组合、可回放，是「解耦」的技术实现手段。
  2. 插件注册表满足开闭原则：扩展不修改既有代码。
  3. 确定性让「同种子同序列 ⇒ 同结果」成为可验证的断言，而非口头承诺。
- 判定标准：任何规则扩展若改动到既有规则文件的**内部实现**，视为架构违规，必须重构。
- 影响：新增卡牌 / 关键词 / 阶段 / 模式均按 `docs/02` 第 4.4 节流程执行。

## ADR-0004 · 交付件变更日志 + 测试报告 + 用户反馈报告三件套

- 状态：已采纳
- 日期：2026-10-12

- 决策：
  1. `logs/CHANGELOG.md` 为 append-only，条目含 11 个必填字段，覆盖全部交付件改动。

  2. 客观测试与主观反馈分离，避免「测试通过就等于好玩」的误判。

## ADR-0009 · 刷新技术栈版本线

- 状态：已采纳（Era 于 2026-10-12 拍板 TypeScript 5.9.3；其余按建议值）
- 日期：2026-10-12
- 背景：`docs/02` 原锁定 Node 20 / TS 5 / React 18 / Vite 5 / Tailwind 3。可行性论证（D-215）实测发现：Node 20 已于 **2026-04-30 EOL**（Node.js 官方发布页与 endoflife.ai）；Tailwind 4 已移除 `tailwind.config.js`，配置方式与 v3 完全不同；多个依赖只写包名未锁版本。按旧版本线搭骨架必然返工（R-01 / R-02 / R-03 / R-20）。
- 决策：版本线刷新为 —— Node `>=22.12.0`（推荐 24 LTS，Docker 用 `node:24`）、pnpm `12.11.2`、TypeScript `5.9.3`、React `^19.3`、Vite `^8.3`、Tailwind `^4.3` + `@tailwindcss/vite`、`socket.io` `^4.8`、`fastify` `^5.12`、Zod `^4.6`、Zustand `^5.0`、Immer `^11.1`、Vitest `^5.0`、Playwright `^1.64`。所有依赖必须锁版本，禁止只写包名；ESLint 用 flat config。
- 理由：
  1. Node 20 EOL 无可辩护；Vite 8 要求 Node ≥ 22.12，本机 22.22.2 与 24.14.0 均满足。
  2. Tailwind 4 的配置方式变更属「写法级」差异，按 v3 写必然重做样式层。
  3. TypeScript 选 5.9.3 而非 7.0.2：7.x 为原生编译器重写版，ESLint / Vitest 等周边兼容性未经本项目验证；Era 拍板选稳妥线。
  4. 未锁版本会导致不同时间安装得到不同结果，环境不可复现 —— 与「结论必须可复现」的要求直接冲突。
- 被否方案：
  - 沿用原版本线 → 骨架推倒重来，返工成本最高。
  - TypeScript 7.0.2 → 生态兼容性风险，Era 否决。
- 影响：`docs/01` §2、`docs/02` §2、`prompts/01` 第 0 条与第 7 条；`pnpm why` 输出一致性纳入脚手架验收。
- 备注：本 ADR 与文档修改同轮落地，但文档先于本记录写入，**未严格遵守「先 ADR 再动工」**；后续必须纠正顺序。

## ADR-0010 · 确定性架构三补（RNG 游标 / 幂等续接 / 规范化哈希）

- 状态：已采纳
- 日期：2026-10-12
- 背景：D-215 第 5 节论证出三处机制真空 —— RNG 游标与「规则函数纯」相互矛盾（R-06）、Intent `seq` 在重连后如何续接未定义（R-08）、状态哈希缺少规范化序列化约定（R-09）。三者分别会导致回放不可复现、「重连成功但操作全被丢弃」、假 desync 刷屏。
- 决策：
  1. **RNG 游标存于 `GameState.rngCursor`**：handler 从 `ctx.rng` 取值并把消耗写入事件，reducer 依据事件推进游标；禁止把 RNG 状态藏在闭包或模块变量里。
  2. **幂等续接**：服务端按 `playerId` 记录 `lastSeq`；重连时随快照下发，客户端从 `lastSeq + 1` 续发，禁止用本地计数归零重来。
  3. **规范化哈希**：状态哈希必须对规范化序列化结果计算（对象键排序、数组顺序固定、`undefined` 统一处理）。
- 理由：
  1. 把游标放进 state 并由 reducer 推进，是让「纯函数」与「可复现」同时成立的最小改动。
  2. `lastSeq` 下发能把一个极难自查的 bug 变成可断言的行为（已写入 `prompts/03` 验收：重连后连发 3 次操作须全部结算）。
  3. 规范化序列化把「假 desync」消除在源头，避免真问题被噪声淹没。
- 影响：`packages/core`、`packages/server` 快照结构、`docs/02` §4.3 与 §5、`docs/01` §5、`prompts/03`、`prompts/05`、测试报告模板。
- 备注：补记 —— 相关内容已于 v0.1.3-docs 先行写入文档，本 ADR 补齐决策留痕；后续须先写 ADR 再动工。

## ADR-0011 · 确定性架构再补（超时入事件流 / 幂等归属 / 回放粒度 / 并发前提）

- 状态：已采纳
- 日期：2026-10-12
- 背景：第二轮可行性论证（`docs/08`，D-217）在补做构建实测与架构深审后发现四处机制真空 —— 回合超时如何进入事件流（`R2-03`）、`(playerId, seq)` 幂等去重表的归属（`R2-04`）、`replay.json` 的记录粒度（`R2-14`）、单房间 Intent 处理链的并发前提（`R2-13`）。前两条若不定义，执行方只有两种写法可选，而**两种都会破坏既有架构约束**。

- 决策：

  1. **超时以「系统 Intent」进入事件流**。服务端会话层是唯一读时钟的地方；它发现超时后构造 `{ type: 'end_turn', actor: 'system', reason: 'timeout', playerId, seq }`，喂给与玩家完全相同的链路（`applyIntent → reduce → stateHash → 写 replay → 广播`）。禁止在 `core` 内读时钟，禁止会话层绕过引擎直接改 `GameState`。
  2. **幂等去重归 Room 会话层**，不进 `GameState`，也不由 `core` 实现。Room 持有 `Map<playerId, lastSeq>`。
  3. **回放粒度 = 种子 + Intent 序列（含系统 Intent）+ hashChain**，记为 `replays/<roomId>-<ts>.json`。
  4. **单房间 Intent 处理链禁止 `await`**：`applyIntent → reduce → stateHash → 写 replay → 广播` 必须同步完成；确有异步需求（持久化等）放在整条链之后。

- 理由：

  1. **超时三选，只有系统 Intent 不违规**：在 `core` 里读时钟 → 破坏纯函数，回放不可复现；会话层直接改状态 → 绕过引擎，`stateHash` 断裂，客户端 reduce 不出同一结果且极难定位；系统 Intent 则让引擎保持纯函数，事件流完整，回放天然包含超时事件。
  2. **提炼出一条普适判据，用于未来所有新增状态的归属判断**：
     > **凡影响游戏结果的外部状态，必须入 `GameState`；凡不影响结果、只保证传输可靠性的状态，一律不入。**
     >
     > RNG 游标决定洗牌结果 → 必须入 state（`ADR-0010` 结论正确）；seq 去重表不影响任何游戏结果 → 归会话层。据此判据，去重表若入 state 会让快照随回合线性膨胀并污染哈希；若由引擎外部持有则破坏 `applyIntent` 的纯函数性质 —— 两条路都不成立，只能放会话层。
  3. **记 Intent 而非 Event**：Intent 序列可重跑规则引擎，同时验证 handler 与 `reduce`；Event 序列只能验证 `reduce`，对超时等服务端生成的行为覆盖不足。系统 Intent 必须入列，否则回放缺步、终局哈希对不上。
  4. **并发属于「论证为低风险，但前提必须写死」**：Node 单线程下无 `await` 的处理链天然原子，两玩家同时出牌不会撞状态。但一旦有人插入异步（哪怕一个 `await redis.get()`），竞态会以「旧测试通过、高并发偶发」的形式出现，属于最难查的缺陷类型。把前提写明，比事后排查便宜得多。

- 影响：`prompts/02`（引擎不实现幂等、系统 Intent 同链路）、`prompts/03`（超时构造、去重归属、replay 定义、禁止 `await`）、`docs/02` §5、`prompts/05` 与测试模板（`M1-03` 幂等改在 Room 层验证、新增超时验证项）。
- 备注：本文档修改与本 ADR 落地于同一轮（v0.1.5-docs）。此为第三次出现「文档先于 ADR」的情况 —— 前两次为 `ADR-0009`、`ADR-0010`。三轮均为同一成因：论证发现缺陷后先改了明显的文档不一致，再补决策。**此顺序问题需在后续 `prompts/01` 执行时严格纠正：先 ADR，再动工。**

## ADR-0012 · 对局状态结构与区域模型

- 日期：2026-10-13
- 状态：已接受（前置：`docs/06` A 组输入 + Era 2026-10-13 澄清「无独立充能区」）
- 背景：

  A 组规则输入到位，`applyIntent` / `reduce` 从 `TODO(slot)` 转为可实现。但 `GameState` 此前只有一个 `rngCursor`（`shared/src/types.ts` 明令禁止在规则输入前出现业务字段），现在必须定稿状态结构 —— 这是**破坏性**的：结构一旦定，后续所有规则处理器、快照协议、客户端渲染都依赖它。

  定稿前唯一悬着的破坏性问题是 `docs/01` §1.3 第 1 条「充能区 ↔ 费用区是否同一区域」。Era 已确认：**没有独立的充能区，`docs/06` X-2 里的「充能区」就是费用区。**

- 决策：

  1. **区域建模为 `zones: Record<Zone, CardInstance[]>`**，8 个区域，与 `docs/06` B2 布局逐项对应：

     | Zone | 对应 B2 布局 | 说明 |
     | --- | --- | --- |
     | `deck` | 卡组区 | 有序，牌顶在数组首 |
     | `hand` | 手牌 | 无序 |
     | `commander` | 指挥官区 | X-1：第一个充能阶段揭示后直接置入，恒 0 或 1 张 |
     | `board` | 随从区 1·2·3 | 上限 `BOARD_SLOTS = 3` |
     | `spell` | 法术区 | 法术与持续法术的结算落点 |
     | `cost` | 费用区 | **三种来源共用一个区**（见下） |
     | `graveyard` | 弃牌区 | |
     | `exile` | 除外区 | |

     **不设 `charge` 区。** 增设一个 `charge` 区会让「同一张卡到底在哪个区」产生二义，且 Era 已明确否定。

  2. **费用区的完整语义**（本次澄清的直接产物）：

     - 来源①：**充能阶段**，把场上或手牌任意数量的随从置入费用区（X-2）
     - 来源②：**指挥官受伤时**，每 1 点伤害执行一次「从卡组顶展示 1 张（如有效果则触发），置入费用区」（A5 补充 1）
     - 消耗：支付 `cost` 时，把**相应数量的卡**从费用区送入弃牌区；数量不足则无法支付（A5 补充 2）

     即：费用区的卡**可能是随从、法术或任意卡**，它是「一堆可作为费用的卡」，不是某种特定牌。界面上只显示数量（B2-3 明确要求），点击可展开全貌。

  3. **卡牌定义与实例分离**：`CardDef`（静态卡池定义，含 `cost` / `power` / `damage` / `keywords`）与 `CardInstance`（场上的一张具体卡，含 `uid` + `defId`）分开。理由：同名卡 3 张上限是「定义」层面的约束，而休眠态、攻击次数等是「实例」层面的状态，混在一个对象里会让「同名 3 张」的校验与「这张卡本回合攻击过没」互相污染。

  4. **字段最小集，结构留扩展位**：字段只落 Era 已给的 `cost` / `power` / `damage`（`damage` 取值范围仍 `TODO(slot)`），另留 `keywords: string[]`（现仅 `'taunt'`）与 `attrs: Record<string, unknown>`。理由：`docs/06` A6-3 明确「可拓展，暂无输入」且 Era 说明会另行给字段清单 —— 届时只加字段、不改结构。

  5. **六阶段固定字面量**：`'charge' | 'reset' | 'draw' | 'main' | 'battle' | 'end'`，顺序即 `docs/06` A4-1 所给顺序，均不可跳过（A4-2）。阶段推进 = 状态机，不得由客户端指定目标阶段。

  6. **最高费用曲线常量化**：`MAX_COST_CURVE = [1, 3, 5, 10]`，按「第 n 回合」取 `min(n, 4)` 索引。写成一张表而非公式 —— Era 给的是离散值，写成公式就是替他发明规则。

  7. **`rngCursor` 保留在 `GameState` 根层**（ADR-0010），不随本 ADR 改变。

- 理由：

  1. **区域列表必须能逐项对上 B2 布局**，否则界面会出现「状态里有这个区但屏幕上没地方放」或反之。`docs/06` B2 列了 8 个区域名，本 ADR 就是那 8 个，一一对应，没有我自行添加的。
  2. **「充能区 = 费用区」这个澄清的价值在于它排除了一个错解**：若误建两个区，充能阶段放进去的随从就永远无法用于支付（或需要额外规则打通），资源循环直接断裂 —— 这是核心玩法，错了整个引擎要重写。故本条单独列为第 2 点并写清三种来源。
  3. **定义与实例分离**是为了让「卡组构成校验」（31 张、同名 3 张、指挥官 1 张）与「运行时状态」各管一段，前者改不影响后者。
  4. **曲线写成表**：离散值来自 Era，插值是我猜的，不猜。

- 影响：`shared/src/types.ts`（新增玩法类型）、`core/src/`（规则处理器按本结构实现）、`prompts/02` 与 `prompts/04` 的实现基准、`docs/02` §5 状态结构章节。
- 备注：本 ADR 是首个在**动工之前**写就的决策记录 —— 此前 `ADR-0009` / `0010` / `0011` 均为「先改文档后补 ADR」，该顺序问题在 `ADR-0011` 备注中已被点名，本条起纠正。

### ADR-0012 补充 · 卡组构成 31 = 主卡组 30 + 指挥官 1（2026-10-13）

- 背景：`docs/06` A6-5 写「卡组 31 张」、A10-4 写「牌库 30 张」，两数对不上。该数直接进卡组校验规则，猜错会让 Era 自己组的牌都进不去，故挂为 `docs/01` §1.3 #2 未决项。
- Era 原话：「是的30+1，主卡组30张+1个指挥官」。
- 决策：
  1. `MAIN_DECK_SIZE = 30`（随从 / 法术 / 持续法术，同名 ≤ 3）、`COMMANDER_COUNT = 1`，`DECK_SIZE` 改为二者之和（31），**不再作为独立魔数存在**。
  2. **指挥官开局直接进指挥官区**，不进主卡组、不参与洗牌与抽牌。故「牌库用尽时把弃牌区洗回」的重洗范围只覆盖主卡组循环，不含指挥官。
  3. 卡组校验**分别校验构成**而非只校验总数：`主卡组 == 30 && 指挥官 == 1`。总数对但构成错（如 31 张里没有指挥官）必须拒绝。
- 理由：把 31 写成单一常量会让真正参与洗牌与抽牌的「30」消失，之后每处抽牌逻辑都要写 `DECK_SIZE - 1` —— 典型的隐式耦合。拆成两个常量后语义自明，也避免日后「31 里到底含不含指挥官」再问一次。
- 影响：`shared/src/constants.ts`、`shared/src/index.ts`。

### ADR-0013 · 战斗结算与触发时机（2026-10-13）

- 背景：ADR-0012 之后 `rules/attack.ts` 仍是占位实现，卡在一条硬缺口上 —— 随从**没有生命值字段**，A6 字段表只有 `cost` / `power` / `damage`，三者都不是生命，无法回答「随从挨多少点会死」。该条同时是 `docs/09` 假设清单「已排除（不能猜）」清单的第一项。
- Era 原话：「只对比力量值，攻击方力量值大于被攻击方，被攻击方破坏；小于的话攻击方自己破坏；等于的话双方破坏。此外，在攻击时和被攻击时都可能有触发的效果」。
- 决策：
  1. **不引入生命值字段**。战斗是纯 `power` 比较的一次性裁决，三分支：`atk > def` → 防守方破坏；`atk < def` → 攻击方破坏；`atk == def` → 双方破坏。本作不存在「生命值」这个概念，ADR-0012 遗留的该阻塞项就此消解。
  2. **`CardDef.damage` 不参与战斗结算**。Era 给的裁决式子里没有任何伤害数值的位置；该字段的取值范围与含义仍是 `TODO(slot)`。
  3. **破坏 = 移入弃牌区**（`graveyard`），不进 `exile`。理由：A9 补充 2 的「弃牌区洗回卡组」依赖它形成资源循环；`exile` 目前没有任何触发条件，送进去等于永久移除，是更重的语义，不能默认选。
  4. **攻击不改变 `health`**。A3-1 唯一判负条件是血空，但 Era 未给「一次攻击造成多少伤害」「打指挥官是否掉血」。本次只裁破坏，不发明掉血。
  5. **指挥官被破坏 → 只破坏，不判负**。`TODO(slot)`：A3-1 只承认血空，指挥官被破坏是否判负 Era 未给，故不得自行写入 `game:ended`。
  6. **攻击目标范围**：对方 `board`（随从）或 `commander`（指挥官）。嘲讽按 A7 字面执行 —— A7 写的是「对手**随从**攻击时必须优先选择此目标」，故只要对方场上有嘲讽随从，随从攻击的目标必须落在嘲讽集合内；**多个嘲讽时由攻击方任选其一**（「任选」不构成需要裁决的冲突，故 A7-2 未定不阻塞）。
  7. **触发时机固定为**：声明 → `trigger:attack` → `trigger:defend` → **快照双方 `power`** → 裁决 → 破坏 → 攻击方休眠。**本批不执行任何效果**（A7 效果清单未给），触发点以显式事件产出，供后续效果系统与客户端动画挂载。
  8. **效果不能中断攻击**。取消 / 替换 / 重定向类机制均未定义，故触发后必定进入裁决。
- 理由（为什么顺序这么定，以及它为什么重要）：
  1. **power 快照必须排在触发之后**。若将来出现「攻击时 +N 力量」这类效果，快照在触发前就会用旧值裁决，整个战斗模块要重写。顺序写死在这里，后续加效果只需在触发点插入，不必动裁决逻辑。
  2. **§1 里「不引入生命值」是消解而非回避**：Era 给的裁决根本不需要生命值，硬补一个字段反而是发明规则。
  3. **§4 / §5 是本 ADR 的克制点**。攻击不掉血、指挥官死了不判负，这两条看起来「不完整」，但它们都指向 Era 未给的输入；写成默认值的代价是整条胜负链路被污染。宁可留 `TODO(slot)`。
- 假设（登记进 `docs/09`）：A-08 破坏入弃牌区；A-09 触发顺序先攻后守、快照在触发之后；A-10 效果不中断攻击；A-11 多个嘲讽任选其一；A-12 无随从时可打指挥官。
- 未决（不猜，等 Era）：~~指挥官被破坏是否判负~~（ADR-0014 已解）；~~攻击是否掉血与掉多少~~（ADR-0014 已解）；`damage` 字段含义；触发效果的清单与是否可取消攻击。

### ADR-0014 · 指挥官伤害与胜负结算（2026-10-13）

- 背景：ADR-0013 §4 / §5 刻意留了两个 TODO —— 攻击不掉血、指挥官被破坏不判负。原因是 A3-1 唯一判负条件是血空，而「一次攻击造成多少伤害」Era 未给。
- Era 原话：「对指挥官造成伤害会受到对应伤害值的伤害，扣除对应血量，血量清空游戏结束」。
- 决策：
  1. **伤害只作用于指挥官**。随从**没有血量**概念（ADR-0013 §1），打随从仍是纯力量值对比 → 破坏，不掉血。
  2. 攻击指挥官且裁决结果为防守方输（`defender` / `both`）→ 对指挥官造成 **伤害值** 点伤害：`health -= damage`；`health <= 0` → `game:ended`，胜者为攻击方。
  3. **伤害值来源**：取攻击方卡定义的 `damage` 字段；**该字段缺失时暂用 `power`**（假设 H13）—— 理由：A6 字段表里 `伤害值` 那一行是空的（取值范围未给），而 `power` 是明确给定的；在 Era 确认前用 power 兜底，改动代价只是一个表达式。
  4. **联动 A5 补充 1**：指挥官每受 1 点伤害 → 从卡组顶展示 1 张卡，「如有效果则触发对应效果」（效果清单未给 → 不执行），然后置入费用区。卡组空则按 A9 补充 2 把弃牌区洗回。
  5. 若裁决结果为攻击方输（`attacker` / `both`）→ 攻击方破坏入弃牌区，**不对指挥官造成伤害**（打不过就没打中）。
  6. 血量下限：扣血结果**不写负数**，`health:changed` 的 `value` 取 `Math.max(0, ...)`。
- 理由：
  1. **§1 是本 ADR 的关键分界**。之前纠结「指挥官被破坏是否判负」，现在 Era 的输入表明指挥官的根本不走「破坏」这条路 —— 它掉血，血空才结束。ADR-0013 §5 的 TODO 就此解除。
  2. **§5 的「打不过就不掉血」是沿用 ADR-0013 的三分支**：裁决说攻击方自己破坏，那这一击自然没有落到指挥官身上。不做「打不过也掉 1 点」这类发明。
  3. **§4 是 Era 早就给过、只是之前无处接线的规则**。伤害有了落点，这条联动就能实现了 —— 它同时是指挥官方的**资源来源**（受伤 → 费用区进牌）。
- 假设（登记进 `docs/09`）：~~H13 伤害值缺失时以 `power` 兜底~~（**已由 X-5 作废，改为默认 1**）；H14 每点伤害触发一次展示（含重复卡）；H15 血量不为负。
- 未决（不猜，等 Era）：`damage` 字段的**取值范围**（默认值已定）；效果清单；是否可取消攻击。
- 影响：`core/src/rules/attack.ts`（新增指挥官伤害分支与 `unit:damaged` / `card:revealed` 事件）、`core/src/ops.ts`（新增 `takeFromDeck` 原语）、`core/src/reducer.ts`（新增事件分支）、`docs/06` X-4、`docs/01` §1.1 / §1.3、`docs/05` A3 / A9、`docs/09` H13–H15。
- 影响：`core/src/rules/attack.ts`（由占位变为实现）、`core/src/reducer.ts`（新增 4 个纯记录事件）、`shared/src/constants.ts`（新增 `KEYWORD_TAUNT` 与 2 个拒绝码）、`docs/09`（新增 5 条假设、移除 1 条已消解项）。

## ADR-0015 区域命名别名与首批卡牌样例入库

- 日期：2026-10-13 20:39（动工前写就）
- 背景：Era 提供首批卡牌样例（`ETCG=炎刃.docx`，5 张）。样例卡面文本里出现了「**伤害区**」这一叫法，而 `docs/06` B2 的布局里**没有**这个区域；此前 Era 已确认 X-2 的「充能区」即「费用区」。
- 决策：
  1. **「伤害区」=「费用区」=「充能区」，三者同一**（Era 2026-10-13 原话：「就是费用区」）。`Zone` 仍只有 `'cost'` 一个值，**不新增 `damage` 区域**。别名只出现在文档与注释里，不进代码标识符 —— 否则会出现「同一个区域两个枚举值」的伪区分。
  2. **卡面文本入库，效果不入库**：`CardDef` 新增 `text?: string` 存原始卡面文本（用于 UI 展示与人工核对），**不解析、不执行**。效果系统（`A7` 关键词表 + 触发时机）仍未给，故所有效果保持 `TODO(slot)`。
  3. **指挥官力量值曲线只记数据、不实现**：样例卡「力量值 0-1-3-5，力量值提升，在每回合充能阶段执行」写入 `attrs.powerCurve`，但**第几回合对应第几档未给**，故不在充能阶段执行任何提升逻辑。
  4. **样例池不构成合法卡组**：5 张卡受「同名上限 3」约束最多只够 15 张主卡组，不足 A6-5 要求的 30 张。故 `CARD_POOL` 虽不再是空对象，但**仍标注为不完整**，卡组校验照旧严格（总数 30 + 指挥官 1）。
- 理由：
  1. **别名必须显式登记，不能靠「我猜是一个东西」**。这次样例证明了区域命名在 Era 的输入里并不统一，若不在文档里钉死，下次再出现第四个名字时无从判断。
  2. **文本入库但不解析**是区分「数据」与「规则」的边界：抄卡面是转录（安全），把卡面翻译成效果是发明（禁止，且猜错要重写）。
  3. **曲线不实现**同理 —— 转录四个数字安全，推断「第 2 回合变 1」是发明。
- 影响：`shared/src/types.ts`（`CardDef.text`、`Zone` 注释）、`server/src/cards.ts`（首批 5 张样例）、`docs/06`（X-6 条目 + 补充第 7 条）、`docs/01` §1.1 / §1.3、新增 `docs/10-卡牌样例.md`。
- 未决（等 Era）：指挥官力量曲线的**回合映射**；法术 / 持续法术的效果定义；`damage` 的取值范围；`pendingChoice`（D4）—— 样例卡「**可以**被除外」是可选动作，需要玩家选择，这条现在有真实使用场景了。

## ADR-0016 指挥官力量值曲线的推进时机与档位映射（2026-10-13）

- 日期：2026-10-13 20:55（动工前写就）
- 背景：ADR-0015 §3 把样例卡「力量值 0-1-3-5，力量值提升，在每回合充能阶段执行」记进了 `attrs.powerCurve`，但刻意**不实现**——「第几回合对应第几档」Era 未给，猜错会让所有指挥官战力整体偏移一档，属于已排除（不能猜）清单里的最后一项。
- Era 原话：**「是初始0然后每个充能阶段成长，第一回合就会变到1」**。
- 决策：
  1. **曲线即档位序列，不按回合号换算**。`powerCurve = [0,1,3,5]` 的语义是：初始取第 0 档（值 0），此后**每经过一次充能阶段推进一档**。故映射结果为：开局 0 → 第 1 回合充能阶段后 1 → 第 2 回合后 3 → 第 3 回合后 5。
  2. **档位入状态**：`PlayerState` 新增 `commanderPowerIndex: number`，初始 `0`。它是玩家级字段而非卡级字段——指挥官本就不进主卡组、没有实例序号（ADR-0012），与 `commanderDefId` 同级。
  3. **推进点有且仅有两个**，且必须都接线，否则第一回合会漏：
     - `start.ts`：揭示指挥官之后（开局后正处第一回合的充能阶段，等价于 X-1 所述「第一个充能阶段」，与 H5 同一口径）；
     - `phase.ts` 的 `advanceOnce`：进入 `charge` 阶段时（即上一回合结束 → 下一回合）。
     - 两处共用新文件 `rules/commander-growth.ts` 导出的 `growCommander`，避免同一机制散落两份。
  4. **走到底即封顶，不循环、不报错**：`index` 取 `min(index + 1, curve.length - 1)`。第 4 回合及以后力量恒为 5。
  5. **档位无变化时不产出事件**（已封顶时静默跳过）——充能阶段每回合都过，否则事件流里会堆满无意义的重复记录。
  6. **只在己方充能阶段推进**：推进对象是当前行动方（开局时是双方各自一次）。对手回合的充能阶段不影响我方指挥官。
  7. **无曲线的指挥官不成长**：`powerCurve` 缺失时力量恒取 `CardDef.power` 定值。这是为了让既有夹具（如测试里的 `cmd`，power 5）语义不变，也兼容未来「力量固定的指挥官」。
  8. **战斗裁决改读当前力量值**：`attack.ts` 里原先直接取 `def.power`，现在改为 `unitPower(state, cards, uid)`——指挥官位于 `commander` 区且定义了曲线时按档位取值，其余按定值。这是本 ADR 唯一一处对既有规则文件的内部修改。
- 理由：
  1. **§1 的「按档位推进」而非「按回合号查表」是关键**。Era 说的是「每个充能阶段成长」，不是「第 N 回合变成多少」——两者在曲线耗尽后行为不同，且前者天然解释了「初始 0、第一回合到 1」。如果按回合号查表，开局时（turn 1）就会直接取 1，与「初始 0」矛盾。
  2. **§3 的双接线点是最容易漏的地方**。`createInitialState` 的初始阶段就是 `charge`，第一回合是「已经处在充能阶段」而没有「进入」动作，只改 `advanceOnce` 会导致先攻方永远停在 0。
  3. **§8 是对 ADR-0013 的必要修正而非违背**：ADR-0013 §1 说战斗「只比较力量值」，本条没有改变裁决规则，只是把「力量值」的读取从静态定义改为「当前值（指挥官可能已成长）」。不改的话指挥官会永远按 0 参战，样例卡的曲线就是死数据。
- 假设（登记进 `docs/09`）：H16 只在己方回合的充能阶段推进；H17 曲线走到底后封顶保持末档。
- 影响：`shared/src/types.ts`（`CardDef.powerCurve` 由 `attrs` 提升为一等字段、`PlayerState.commanderPowerIndex`）、`shared/src/constants.ts`（`INITIAL_COMMANDER_POWER_INDEX`）、`core/src/state.ts`、`core/src/ops.ts`（新增 3 个力量值原语）、`core/src/reducer.ts`（`commander:grown`）、`core/src/rules/commander-growth.ts`（新增）、`core/src/rules/start.ts` / `phase.ts`（各加一行接线）、`core/src/rules/attack.ts`（改读当前力量值）、`server/src/cards.ts`、`docs/06` X-7、`docs/01` §1.1 / §1.3、`docs/09`、`docs/10`。

## ADR-0017 回合超时自动结束回合的接线（2026-10-13）

- 日期：2026-10-13 21:20（动工前写就）
- 背景：ADR-0010 定义了 `TURN_TIMEOUT_MS = 30_000` 并明令「**禁止与 `RECONNECT_GRACE_MS` 混用」；ADR-0011 又定了超时**必须以系统 Intent 入事件流**、与玩家操作走同一条链路。但两者都只到决策层 —— 全仓唯一的定时器是房间清理的 `pruneTimer`，`TURN_TIMEOUT_MS` **定义了却从未被任何代码引用**（`docs/01` §1.3 #4 记为「待接线」）。本 ADR 补的正是这一层。
- 决策：
  1. **计时单位是回合，不是阶段**。一个回合内只要有任何**被接受**的 Intent 就重新计时；整个回合都无操作才触发超时。与 `TURN_TIMEOUT_MS` 的注释口径一致（ADR-0010）。
  2. **只有被接受（accepted）的 Intent 才续命**，被拒绝（rejected）或重复丢弃（dropped）的**不重置计时** —— 否则玩家发一串非法操作就能无限拖时间，这是把超时机制做成摆设的最常见方式。
  3. **计时器由会话层持有并驱动**：新增 `server/src/room/turn-timer.ts`，由 `RoomRuntime.timer` 持有；`arm` / `clear` 的时机由 `index.ts`（唯一允许读时钟的地方）决定。
  4. **超时动作 = 构造系统 Intent 后走标准链路**：`{ type: INTENTS.turnEnd, actor: 'system', playerId: <当前行动方>, seq: rt.serverSeq + 1, reason: 'timeout' }` → 交给 `submitSystemIntent`（跳过 seq 去重）。
     ⚠️ **禁止在超时回调里直接改 `GameState`** —— 那样客户端 reduce 出的状态与服务端不一致，`stateHash` 必然比对失败，且只在联机时才暴露。
  5. **停止计时的三种情形**：房间销毁（随 `sweepRuntimes` 一起清理）、对局结束（`winner !== null`）、座上无人可行动。
  6. **时限取值**：沿用架构常量 `TURN_TIMEOUT_MS = 30_000`（假设 H18）。它与 `RECONNECT_GRACE_MS`（同为 30s，但语义是**席位保留**）数值相同纯属巧合，**不得互相引用或合并**。
  7. **掉线玩家照常计时**（假设 H19）：不计时会让对局永久卡死。对手若要判胜，走 A3-3 的既有路径，与本机制互不干扰。
- 理由：
  1. **§1 与 §2 是本 ADR 的核心**。若按阶段计时，六阶段每回合各给 30s，等于 6 倍时限，且「阶段不可跳过」的语义会被超时架空；而若让被拒绝的操作也续命，超时保护当场失效。
  2. **§4 是架构铁律的直接应用**：core 是纯函数 + 事件溯源，任何绕过引擎直接改状态的做法都会让 `stateHash` 失去意义 —— 它是双端一致性唯一的校验手段。
- 假设（登记进 `docs/09`）：H18 回合时限暂取 30s；H19 行动方掉线照常计时。
- 影响：`server/src/room/turn-timer.ts`（新增）、`server/src/index.ts`（会话层接线）、新增单测、`docs/01` §1.3 #4、`docs/09`、`logs/CHANGELOG.md`。
- 未决（等 Era）：回合时限的**实际取值**（现为架构默认 30s）；`docs/06` C2-1 / C2-2 / C3-1。

## ADR-0018 卡池补全与开局桥（2026-10-13）

- 日期：2026-10-13 21:40（动工前写就）
- 背景：卡池只有 Era 首批 5 张样例（4 张非指挥官 × 同名上限 3 = 12 < 30），**组不出 A6-5 要求的合法主卡组**。后果是 `startRule` 的卡组校验必然拒绝，会话层与引擎之间的「开局桥」接不上，联机对战跑不起来。Era 2026-10-13 授权：**「其他卡组内容先由你生成补充完整」**。
- 决策：
  1. **补全到 12 种非指挥官卡**（每种 ≤ 3 → 36 张可选项，足以组出 30 张主卡组，留有余量）。
  2. **数值遵循单一可解释规则**：无效果补偿的随从取 `power = cost + 1`；带关键词或有效果的卡按「补偿」下调。规则写死在 ADR 里，Era 审阅时可直接改数值而不必猜我的意图。
  3. **不引入新关键词**，仅用 A7 已定义的 `taunt`。
  4. **效果一律不执行**，只存 `CardDef.text`（沿用 ADR-0015 §2）—— 补齐的是**数值**，不是玩法。
  5. 新增 `server/src/deck-pool.ts` 存放 **Demo 用占位主卡组**（30 张），与卡池定义分离：卡池回答「卡是什么」，默认卡组回答「这局用什么」。Era 给正式卡表后只替换后者。
  6. 占位身份必须**显式标注**（文件头 + `text` 字段），避免日后误当作 Era 的正式输入。
- 理由：
  1. **卡池是联机可玩的硬卡点**。规则引擎、会话层、超时机制都齐了，唯独没有合法卡组可开局，整条链路就停在最后一步。

## ADR-0019 开局桥：房间满员且全员准备后建立对局（2026-10-13）

- 日期：2026-10-13 21:50（动工前写就）
- 背景：会话层（socket handlers）与规则引擎（core）都已就绪，但**两者之间没有桥** —— `runtimeOf` 用 `seats: []` 建立空状态，`room.phase` 因此永远停在 `'lobby'`，`startRule` 的「开局需要 2 名玩家」校验必然拒绝。这同时是 ADR-0017（回合超时）迟迟无法端到端生效的原因：超时要求房间处于 `playing` 且有行动方。ADR-0018 补齐卡池后，本桥的最后一个前置依赖消失。
- 决策：
  1. **新增会话事件 `room:ready`，而不是让客户端直接发 `game:start` Intent。**
     理由：`seats`（座位顺序）与 `seed`（随机源）共同决定先后手与洗牌结果，属服务端权威。若由客户端直接发开局 Intent，等于把座位顺序与种子交给客户端 —— 可伪造先后手、可预测牌序。
  2. **`Seat` 新增 `ready: boolean`**，建房 / 加入时置 `false`。它是**房间层事实**（玩家是否已准备），不是玩法字段，不违反 `room/types.ts`「只描述传输层事实」的纪律。
  3. **开局条件**：房间满员（无空位）**且**所有在座玩家均已 ready。满足后由服务端执行：
     - 用「房间座位顺序 + 默认主卡组 + 默认指挥官」调用 `core.createInitialState` 建立真实 `GameState`；
     - 以 `actor: 'system'`、`reason: 'all-ready'` 构造 `game:start` Intent → `submitSystemIntent`（走标准链路，洗牌 / 掷骰 / 发牌全部由引擎产出事件）；
     - 广播房间与快照；
     - `rt.timer.arm()` 开始本回合计时（ADR-0017）。
  4. **幂等**：运行时置 `seeded = true`，重复 `room:ready` 不重复开局（两名玩家同时点准备是常态）。
  5. **卡组来源**：当前取 ADR-0018 的占位卡组；卡组编辑（B1）落地后改为玩家提交。
  6. `room.phase` 开局成功后置 `'playing'`；对局结束（认输 / 血空）置 `'ended'` 并 `timer.clear()`。
- 理由：
  1. **§1 是权威边界而非风格选择**。`seats` 与 `seed` 必须由服务端决定，这是"服务器权威 + 客户端只发意图"（ADR-0002）的直接推论。
  2. **§3 复用 `submitSystemIntent`** 与 ADR-0011 一脉相承：开局也是一条系统 Intent，客户端拿到的仍是一串标准事件，可直接 `reduce`，**不需要为开局写任何特例分支**。
  3. **§4 幂等是必须的**：两名玩家几乎同时点准备时会各触发一次 `room:ready`，不设阀门就会开局两次、状态被推走两遍。
- 影响：`shared/src/constants.ts`（新增 `roomReady` 事件名）、`server/src/room/types.ts`（`Seat.ready`）、`server/src/room/room.ts`（`setReady` / `allReady`）、`server/src/index.ts`（接线与广播）、新增单测、`docs/06` X-9、`docs/01` §1.3 #4、`logs/CHANGELOG.md`。
- 未决（等 Era）：正式卡表；卡组编辑（B1「支持多个卡组保存」）的交互；`damage` 的取值范围。

### ADR-0020 补充 · 实现中新增的三条决策（2026-10-13 22:20）

实现期间遇到三个原 ADR 未覆盖的界面层问题，补记在此（都是工程问题，不涉及玩法）：

1. **卡池迁到 `shared`**（`shared/src/cards.ts`，经子路径 `@app/shared/cards` 导出）。
   客户端要渲染卡名 / 费用 / 力量值，就必须拿到卡定义 —— 而卡池原先只在服务端。
   它是**数据**而非玩法规则，放共享层不违反纪律。
   ⚠️ 客户端必须走**子路径**，不得从 `@app/shared` 根导入 —— 根入口会经 `schema.js` 拉入 zod（实测首屏 +24 kB gzip）。

2. **客户端的 `reduce` 起点是服务端下发的快照，且顺序不能反**。
   `reduce` 是增量的，没有起点状态就无法消化事件。故 `startGame` 必须
   **先**广播快照（尚未开局的初始状态），**再**提交开局 Intent。
   若反过来，开局那一批事件会被客户端丢弃，表现为「开局日志凭空消失」。

3. **计时截止时刻随快照下发**。
   B2-5 要求「回合数与计时居中显示」，而截止时刻是服务端时钟的产物（ADR-0017：
   会话层是唯一允许读时钟的地方）。客户端不自行推算，避免两端时钟不同步时各说各话。
   由于快照要先于计时器 `arm`，故 `startGame` 会**广播两次**快照 —— 第二次才带上有值的 `turnDeadline`。

- 影响：`shared/src/cards.ts`（新增）、`shared/package.json`（新增 `./cards` 子路径）、`server/src/cards.ts`（改为 re-export）、`client/package.json`（新增 `@app/core` 依赖 —— `reduce` 需要）、`client/e2e/game.spec.ts`（新增联机开局端到端用例）。

## ADR-0021：E2E 用固定随机种子，而非关闭洗牌

- 日期：2026-10-13
- 状态：**已接受**
- 触发：Era 提出「你想固定卡牌顺序可以不洗牌测试」—— E2E 需要确定牌序才能写确定断言。

### 背景

E2E 里先后手由掷骰决定、起手牌由洗牌决定，两者都是随机的。
后果是同一条用例每次跑到的手牌构成不同，「充能哪张 / 出哪张」无法硬编码，
断言只能写成条件分支 —— 要么 flaky，要么弱化成「不报错就算过」。

### 决策

1. **固定随机种子，不关闭洗牌**。引擎 RNG 是种子化纯函数（ADR-0010），
   `seed + Intent 序列` 唯一决定结果，故固定 seed 即可确定牌序与先后手。
2. 种子来源：`GAME_SEED` 环境变量；未设置时回落到 `Date.now() >>> 0`。
3. 注入点：`playwright.config.ts` 的 `webServer.env`，只在 E2E 生效。

### 为什么不用「不洗牌」

「不洗牌」要改的是 `start.ts` 的**正式逻辑**，等于为测试在生产代码里开一条
不走洗牌的分支 —— 而洗牌一旦不在 E2E 路径上，就再没有任何自动化测试覆盖它。
固定 seed 保留完整链路：**洗牌照跑，只是结果确定**。

同理也不用「测试专用不洗牌开关」：任何 `if (isTest)` 都会让被测代码与生产代码
分叉，测过的不是真正跑的那条。

### 代价

- E2E 断言与具体 seed 值绑定：改卡池或默认卡组配比会让断言失效。
  故断言只写**由规则保证的不变量**（如「费用区张数 +1」「随从区出现卡」），
  不写具体卡名。
- 生产**不得**设置 `GAME_SEED`，否则每局牌序相同。代码注释里已写明。

### 落地

- `server/src/room/session.ts` 新增 `nextSeed()`
- `server/src/index.ts` 两处 `Date.now() >>> 0` 改调 `nextSeed()`
- `client/playwright.config.ts` 的 `webServer` 加 `env: { GAME_SEED }`

## ADR-0023 卡牌效果系统：发动 Intent、待定选择与回合内临时态（2026-10-18）

- 日期：2026-10-18 13:55（动工前写就）
- 背景：样例卡的 `text` 早已转录入卡池（ADR-0015），但按「不发明需求」一律不结算，
  导致 Era 实测「指挥官效果没法发动」。Era 2026-10-18 授权：
  **「所有有效果的卡牌，你直接补充需要的规则即可，不需要我来填写」**，
  并给定三条口径——`【2】`= 支付费用区 2 张卡；「每回合一次」**在自己回合开始时重置**；
  「选择一个随从」类效果需要目标选择，引入 `pendingChoice`。
- 决策：
  1. **两个新 Intent**：
     - `effect:activate`（payload `{ uid, effect }`）——发动卡面效果，`uid` 是效果来源卡，
       `effect` 是效果编号（如统领的 `'1'`/`'2'`）。
     - `effect:choose`（payload `{ choice }`）——回答待定选择，`choice` 是选项 id
       （卡 uid / 子效果编号 / `'pass'`）。
  2. **`GameState.pendingChoice`**：效果需要玩家选择时挂起，含
     `{ playerId, kind, sourceUid, options: string[], meta? }`。
     挂起期间**只允许**该玩家的 `effect:choose` 与任意时刻的认输/离开，
     其余 Intent 一律拒绝（`PENDING_CHOICE`）——与「超时回合」同级的全局守卫，
     加在引擎入口而非各规则里。超时系统链路的兜底动作（自动抽牌/结束回合）
     不受影响：系统 Intent 不受 pendingChoice 阻塞。
  3. **回合内临时态**（「本回合」词缀的统一实现）：
     - `CardInstance` 新增 `tempPower` / `tempDamage` / `attackRefresh`（均为可选），
       `unitPower` 在定值/曲线基础上**叠加** `tempPower`；`attack.ts` 的伤害 =
       `(def.damage ?? 1) + (tempDamage ?? 0)`；`attackRefresh` 置位时攻击后不进入休眠。
     - `PlayerState` 新增 `effectsUsed: string[]`（每回合一次记帐，键 `${uid}:${effect}`）与
       `turnTriggers: TurnTrigger[]`（军师类「本回合获得效果」的触发器）。
     - **清理时机**：临时态与触发器在**回合切换**（`turn:changed`）时清空；
       `effectsUsed` 在进入**己方充能阶段**时清空（Era 口径：自己回合重置，
       与指挥官成长同一接线点）。
  4. **效果注册表** `core/src/effects/`：一卡一文件（`blade-lord.ts` 等），
     注册表按 `defId` 派发；新增带效果的卡不动既有文件（与规则注册表同纪律）。
  5. **统领效果 Ⅰ 的分步结算**：支付【2】→ 按除外区「炎刃」数量解锁档位
     （1/3/5/7/9）→ 弹出效果菜单（`pendingChoice.kind='blade-lord-1'`），
     每选一项目最多 3 项、每项一次；需目标的子效果再链一层目标选择。
     任何时候可选 `pass` 提前结束。
  6. **号令法术**：出牌结算时展示卡组顶 7 张（`cards:revealed` 事件），
     若其中有斥候先问「是否除外斥候」（其卡面触发），再让玩家从
     力量值 ≤ 除外区炎刃数的随从中选一个召唤（随从区满则无可选项，只能 pass），
     未选中的**洗回卡组**（假设 H21，卡面未说去处，取卡牌游戏通行做法）。
  7. **军师（bladeTactician）**：每回合一次发动 → 挂 `on-blade-summon` 触发器，
     本回合内每当己方「炎刃」随从登场（出牌或效果召唤），该随从 `tempPower+1`，
     触发次数上限 = 发动时除外区炎刃数。
  8. **斥候（bladeScout）**：仅在「从卡组展示」时机出现可选除外（目前唯一来源是号令）；
     「本应置入伤害区」分支暂不触发（当前机制里没有把展示卡置入伤害区的路径，
     登记为留白，不发明）。
- 理由：
  1. **pendingChoice 全局守卫**而非各规则自查 —— 漏一处就可能在选择挂起时
     推进阶段导致状态机错位；入口拦截一处搞定。
  2. **临时态挂在卡实例上**而非旁表 —— 事件溯源友好：`unit:modified` 事件
     带字段即可被客户端 reduce 复现，无需额外索引。
  3. **效果与规则引擎同层**（纯函数、事件产出），**不进 reducer**：
     选择分支是 Intent 驱动，不是事件回放能自动展开的。
- 假设（登记进 `docs/09`）：H21 号令未选中的卡洗回卡组；H22 统领Ⅰ的子效果目标
  不限阵营（卡面只说「一个随从」）；H23 「本回合攻击后重置」= 本回合内每次攻击后都不休眠；
  H24 军师离场后其已挂的触发器不回收（卡面未说离场失效），回合末统一清空。
  **2026-10-19 Era 逐条拍板**：H21 维持（回到卡组并洗牌）；H22 改为**限己方**；
  H23 修订为**「一回合一次，攻击后重置」**（卡面描述同步改，生效一次即消耗，
  由 `attack.ts` 在免休眠时发 `unit:modified{attackRefresh:false}` 收回）；H24 维持。
  落地见 D-127。
- 影响：`shared/src/types.ts`（`pendingChoice` / `CardInstance` 临时态 / `TurnTrigger` /
  `effectsUsed`）、`shared/src/constants.ts`（新错误码）、`core/src/rules/effect.ts`（新）、
  `core/src/effects/*`（新）、`core/src/rules/play.ts`（号令接线 + 登场触发钩子）、
  `core/src/rules/attack.ts`（tempDamage / attackRefresh）、`core/src/rules/phase.ts` 与
  `turn-end.ts`（清理接线）、`core/src/reducer.ts`（新事件）、`core/src/ops.ts`（unitPower 叠加）、
  `client`（发动按钮 + 选择浮层 + 目标发光）。

## ADR-0024 · 核心规则切换为「8 血版」（docs/16）

- 日期：2026-10-19
- 状态：已接受（Era 在 GitHub 提交 `docs/16-核心规则条文-8血版.md` 并指示「看看怎么实现」「动手」）
- 背景：15 血 / 无费用校验 / 无前排 / 指挥官不能攻击的旧规则，实测节奏拖沓且快攻与
  大怪都缺少约束。`docs/13~15` 用 6,000–8,000 局模拟收敛出一套「不加伤害上限、
  用规则和数值控节奏」的条文，`docs/16` 是其中可直接实现的一版。
- 决策（逐条对应 `docs/16` §10 差异清单）：
  1. **初始血量 8**，血量下限 0（不为负）。
  2. **起手**：先手 5、后手 6；先手第一回合抽牌阶段抽 **0** 张（可出牌、不可攻击）。
  3. **充能收入**：每次进入己方充能阶段，从卡组顶取 **2 张**直接置入费用区（强制）。
  4. **`maxCost` 必须校验**：按**各自回合数**（`chargeCount`）取 `[1,3,5,10]`，
     语义是「本回合所有支付的总张数上限」，0 费不占额度。
  5. **随从费用 −1（最低 0）**；法术与持续法术按卡面值。
  6. **前排规则**：对方随从区有随从时，己方随从不能宣告攻击对方指挥官；
     对方空场才能打脸。嘲讽优先于前排。
  7. **打脸门槛**：攻击者力量 ≥ 敌方指挥官当前力量才能宣告。
  8. **打脸伤害按力量分档**：1–3 → 1，4–6 → 2，7+ → 3；卡面 `damage` 为**例外覆盖**。
  9. **指挥官攻击**：每个己方战斗阶段一次，固定对敌方指挥官 **1 点**伤害；
     不比较力量、不受前排限制、不吃伤害加成。指挥官不能攻击随从。
  10. **指挥官力量按轮次同步**：轮次 = `ceil(全局回合数 / 2)`，
      双方 `powerIndex = min(轮次, 曲线末档)`，即第 1 轮 1、第 2 轮 3、第 3 轮起 5。
  11. **40 轮未分胜负判和**（实现为全局回合 > 80）。
- 实现要点：
  - 「各自回合数」用 `PlayerState.chargeCount`（拿到回合即 +1），不用全局 `turn`，
    否则后手白拿一档。
  - 「本回合已消耗张数」新增 `PlayerState.usedCostThisTurn`，由 `cost:spent` 事件累加，
    出牌与效果支付（统领【2】）共用同一记帐。
  - 指挥官攻击单独成规则文件 `commander-attack.ts`，与随从攻击共享伤害/展示链路
    （指挥官的受伤展示→费用区逻辑抽到 `combat.ts` 公共函数）。
- 影响：`shared/src/constants.ts`、`shared/src/types.ts`、`core/src/rules/{start,phase,play,attack,
  commander-attack,commander-growth}.ts`、`core/src/reducer.ts`、`core/src/ops.ts`、客户端血量/
  费用/指挥官攻击入口。
- 破坏性：**是**（规则口径变更；旧对局回放的结算结果不再等价）。

## ADR-0026 · 赛制可选 BO1/BO3（D-132）

- 日期：2026-10-19
- 状态：已接受（Era：「在建房界面选择 Bo1 还是 bo3」）
- 背景：`docs/16` §1.3 明确「座位偏差由赛制消化，不由规则硬压」——删掉打脸门槛后
  先手胜率仍约 56.5%，条文要求用 BO3「双方各先手一次」消化，而不是继续削先手。
- 决策：
  1. **建房时选择** `format: 'bo1' | 'bo3'`，缺省 BO1（老客户端不带该字段仍可用）。
  2. **系列赛状态放在房间层**（`wins` / `gameNo` / `awaitingNext` / `firstPlayers` /
     `seriesWinner`）—— 它跨越多局 `GameState`，不属于任何单局状态。
  3. **BO3 三局两胜**：拿满 2 胜结束；平局不计分但消耗一局。
  4. **先后手**：第 1 局掷骰；第 2 局由第 1 局的后手先攻（各先手一次）；
     第 3 局重新掷骰（登记假设 H33）。实现为 `start` Intent 的
     `payload.firstPlayerId`，**只接受系统来源**，玩家带上该字段一律忽略（防伪造）。
  5. **局间节奏**：小局结束不发新快照，房间进入 `awaitingNext`，由**房主**点
     「开始第 N 局」（登记假设 H36）。自动续局会让玩家看不清结算。
  6. **离场 = 判负整个系列赛**（`forfeitSeries`），不留「等待下一局」，否则留下的人
     会卡在空白页（D-122 同类问题）。

  `MatchFormat`、房间入站字段）、`server/src/{index.ts,room/{types,room}.ts}`、
  客户端 `HomeScreen`（赛制选择）、`useRoom`（`nextGame`）、`TableScreen`
  （比分条 / 结算面板 / 下一局按钮）、E2E helpers 与 `game.spec`。
- 破坏性：**否**（新增字段均可缺省）。

## ADR-0028 · 指挥官伤害可被加成（D-137 / H34 确认）

- 日期：2026-10-19
- 状态：已接受（Era 拍板：「指挥官的 1 点可以被伤害加成类效果提升」）
- 背景：`docs/16 §9 #9` 原裁决为「不会，固定值不进入伤害修正」；
  `docs/17` 星轨侍僧却写「本回合你的指挥官伤害值 +1」。两者冲突，曾以假设 H34 挂起。
- 决策：
  1. **基础值仍为 1**（`COMMANDER_ATTACK_DAMAGE`），但它**进入伤害修正**，
     最终伤害 = `1 + PlayerState.commanderDamageBonus`。
  2. `commanderDamageBonus` 是**玩家级**字段，承载所有「你的指挥官伤害值 +N」类效果；
     单卡是否可叠加由**效果自身**限制（侍僧：`effectsUsed` 键 `star:acolyte`，不可叠加）。
  3. 边界：`CardInstance.tempDamage` 是**随从实例**的伤害修正（统领 7 档「选择 1 个己方随从，
     本回合对指挥官伤害 +1」），只加该随从打脸，不转移给指挥官；
     「造成 N 点伤害」类固定直伤（星陨）同样不吃加成。
  4. 结算顺序不变：指挥官的「攻击时」效果（展示）先于伤害，展示获得的加成对本次攻击生效。
- 影响：`docs/16`（§5.6 / §6.1 / §6.2.1 / §7 / §9 #9 / §10）、`docs/18`（§3.1 / §3.3）、
  `docs/09`（H34 转已确认）、`core/src/rules/{commander-attack,index}.ts`（注释）、
  `core/src/rules/rules.test.ts`（+2 条）。
- 破坏性：**否**（实现早已按卡面落地，本次仅确认口径并补齐文档/测试）。

## ADR-0029 · 冻结限未冻结单位 + 第四类法术定名（D-139 / D-140）

- 日期：2026-10-19
- 状态：已接受（Era 拍板：「h31 不算，建议描述改为冻结一个未冻结单位」；
  「持续法术留场，不过这个类型应该叫设置法术，意思是设置在场上」）
- 决策：
  1. **冻结目标必须是未冻结单位**（H31 已确认）。对已冻结单位再次冻结**不产生任何「被冻结」**：
     不发 `unit:frozen`、不加霜痕、不触发裁决官Ⅱ / 执法者、不刷新状态。
     卡面统一写「冻结 1 个未冻结的敌方随从」。
  2. `freezeUnit` 是唯一执行点：目标已冻结即返回空（兜底旧回放与异常入站）。

     由 `freezeUnit` 逐张跳过。
  3. **缚锁者是卡面例外**：卡面自带「若该随从已处于冻结状态，改为抽 1 张」，
     保留已冻结候选并走抽牌分支 —— 例外写在卡面，玩家可读。
  4. **第四类法术中文名定为「设置法术」**：设置在场上，出牌后留在法术区；
     普通法术结算后进墓地（H30 已确认）。
  5. **代码标识符保留 `continuous`**：`CardType`、协议与回放均不改名；只有卡面、客户端显示与文档统一。
     理由：改名会波及 schema、回放兼容与全部测试，收益仅为字面一致。
- 影响：`core/src/effects/{primitives,frost-troops,frost-arcana,frost-commander}.ts`、
  `shared/src/{cards,types}.ts`、`client/src/{CardTile,TableScreen}.tsx`、
  `core/src/effects/growth.test.ts`（+4 条）、`docs/{01,06,09,10,12,16,17,18}`。
- 破坏性：**是**（冻结链强度下降 —— 重复冻结不再刷霜痕 / 裁决官Ⅱ；旧回放结算不再等价）。

## ADR-0031 · 选择链排队：效果召唤的登场选择延后触发（D-145 / H28）

- 日期：2026-10-19
- 状态：已接受（Era 拍板：「H28 效果召唤也能触发，在上一轮所有待结算的效果结束后，再在下一轮时点触发」）
- 背景：`GameState.pendingChoice` 只有一个槽位。效果召唤常发生在选择链内部
  （统领Ⅰ 的菜单 / 号令揭示后召唤），此前只能跳过登场效果里「需要选择」的部分，
  否则第二个 `choice:pending` 会覆盖第一个。这导致卫士 / 老兵等登场效果在效果召唤时静默丢失。
- 决策：
  1. **新增状态 `GameState.pendingChoiceQueue: PendingChoice[]`** —— 排队尚未挂起的待定选择。
  2. **新增两个事件**：`choice:queued`（入队，payload 与 `choice:pending` 同构）与
     `choice:dequeued`（出队，shift 队首）。
  3. **入队判定**：`summonEntryEvents` 派发登场效果时，若当前 `state.pendingChoice` 非空，
     把结果中的 `choice:pending` 改写成 `choice:queued`；自动部分（磨牌 / 成长 / 全体冻结）仍当场结算。
  4. **出队点唯一**：`effectChooseRule` 结算完一次回答后，若结果里**没有**新的 `choice:pending`
     且没有 `game:ended`，且队列非空 → 追加 `choice:dequeued` + `choice:pending(队首)`。
     即「上一轮所有待结算效果结束后，下一时点触发」。
  5. **删除 `summonEntryEvents` 的 `allowChoice` 开关** —— 跳过分支不再存在，
     所有召唤路径（出牌 / 统领Ⅰ / 号令）共用同一套排队行为。
- 边界：
  - 队列不跨对局清理（对局结束后不再受理 Intent，残留无害）；
  - 判和 / 认输产生 `game:ended` 时不出队；
  - 队列中的选择仍校验 `playerId`，与直接挂起完全同构，客户端无需区分。
- 影响：`shared/src/types.ts`、`core/src/{state,reducer}.ts`、`core/src/effects/{index,blade-lord}.ts`、
  `core/src/rules/effect.ts`、`client/src/log.ts`、`core/src/effects/effects.test.ts`（+2 条）。
- 破坏性：**是**（效果召唤的场景里，此前被跳过的登场选择现在会真的弹出来，结算序列变化）。

## ADR-0035 · 展示卡在结算期间停在展示区（D-149）

- 背景：D-146 定稿为「先置底、再结算」，等价于「整批先离场」。但实现上「离场」被写成了
  「翻开的同一条事件流里立刻置底」—— 从状态上看，卡片在效果结算时**已经在牌库底**。
  Era 2026-10-20 补一句：「H35 用现行就行，但是效果执行的时候放在展示区」。
- 决策：引入第九个区域 `reveal`（展示区），把「离场」与「归位」拆成两步：
  1. 翻牌 = `deck → reveal` + `card:revealed`；
  2. 效果结算（星轨 +1 / 星轨环抽牌 / 各卡「展示时」）；
  3. 归位 = `reveal → deck`（末尾，按翻开顺序）。
- 等价性：第 1 步之后卡片已不在牌库，所以「展示时抽 1 张」取到的一定是下一张 ——
  与 D-146 要防的重复触发完全一致。区别只在于**结算期间的状态**：
  卡片在展示区而非牌库底，客户端因此能如实渲染，且不需要客户端自己攒「展示回执」。
- 边界：
  - `reveal` 是瞬时区域 —— 不跨 Intent、不进 B2 六排布局，双方各占一格；
  - 焚典 / 号令 / 受伤展示**不经过**展示区（它们不把卡抽离牌库，H26 已确认选牌期间卡仍在卡组）；
    客户端仍用回执把它们显示在展示区，行为不变；
  - `deck:put-bottom` 兼容从卡组取卡（旧回放）；
  - 进出展示区不产生日志行。
- 影响：`shared/src/types.ts`、`core/src/{state,reducer}.ts`、
  `core/src/effects/{primitives,index,star-arcana}.ts`、`client/src/{TableScreen,useRoom,log,labels}.ts`。
- 破坏性：**是**（事件流与 `stateHash` 变化；结算结果与终态不变）。

## ADR-0036 · 展示节奏放在客户端，服务端不加人为延迟（D-151）

- 背景：Era 2026-10-20「卡片应该在结算期间停留，而不是闪一下就没了」。D-149 之后，
  展示卡确实在状态里停在 `reveal` 区，但整批事件（翻牌 → 结算 → 归位）走同一条流，
  客户端逐条 reduce 不停顿，玩家看到的是**一闪而过**。
- 决策：停顿只加在客户端表现层（`useRoom.pump`）：
  - 每张卡进展示区后停 `REVEAL_FLIP_MS = 180ms`（逐张揭牌）；
  - 归位事件（`deck:put-bottom`）**应用前**补足 `REVEAL_HOLD_MS = 900ms` 的最短可见时长。
- 为什么不放在服务端：服务端是权威结算，人为插入延迟会让 Intent 处理链变慢，
  并且把「观感」变成协议的一部分 —— 观感属于 B7，改起来不该牵动回放与哈希。
- 为什么不放在 CSS 动画：动画只影响视觉，不移除 DOM 时卡片仍会「瞬间消失」；
  停顿发生在 `reduce` 之前，才能真正推迟归位。
- 边界：停顿是**串行**的（`pump` 单线程），事件多时总时长会叠加；展示批次最多 4 张，
  实测约 1.6s，在可接受范围。若将来出现 10 张以上的批量展示，需要改成「整批固定时长」而不是逐张累加。
- 影响：`client/src/useRoom.ts`、`docs/09`（H37）、`README §11.6`。
- 破坏性：**否**（纯表现层）。

## ADR-0038 · 一条连接只占一个席位；回收责任在连接层（D-181）

- 背景：回答 X-20 / 限流问题时量内存，发现单连接建 2000 间房后内存不回落。
  根因不在 `prune()`，而在「谁负责把席位标记为可回收」这一层没人负责：
  `socket.data.playerId` 是**单个值**，每次建房被覆盖，旧席位永远留着 `connected: true`，
  而 `prune()` 只回收 `connected: false` 的席位。
- 决策：
  1. **不变量**：一条 socket 连接同一时刻只占一个席位。写入新席位前必须释放旧席位
     （`releaseSeatOf`）—— 建房、加入成功后、重连换席位三处统一走它。
  2. **`prune()` 的契约保持不变**：只回收「已标记断线」且超宽限期的席位。
     不能让它顺手回收 `connected: true` 的席位 —— 那会把正在对局中的玩家踢掉。
  3. **释放时机**：`create`/`join` 在**成功之后**释放（失败时保留原席位，玩家不至于两头空）；
     `reconnect` 只在席位不同时释放。
- 为什么不是「让 prune 兜底」：`prune` 无法区分「连接层忘了释放」与「玩家正连接着」——
  两者在状态里长得一模一样。把责任放在写入点，才是唯一能判定的地方。
- 后果：同一浏览器标签再建房会**立即**销毁上一个房间（原先会留下一个孤儿房间）。
  这正是产品语义；副作用是多人共用一个 socket 的场景不再可能 —— 本项目也没有这种用法。
- 遗留（不在本 ADR 解决，需 Era 口径）：连接数、单连接操作频率、全局房间总数仍无上限，
  以及穿透部署下按 IP 限流失效（见 `docs/20` §8.2）。
- 影响：`server/src/index.ts`（`releaseSeatOf` + 三处调用）、`room.test.ts`（+2 条契约测试）。
- 破坏性：**否**。

## ADR-0039 · 限流按「连接 + 全局」，不按 IP（D-182）

- 背景：建房 / 加入 / Intent 三层都没有频率上限。Era 2026-10-20 确认按推荐值落地。
- **关键约束（决定了架构）**：走 frpc TCP 隧道时，远端用户 → 隧道节点 → 本机 frpc → `127.0.0.1:3100`，
  服务端拿到的对端地址是 frpc 那一端。**所有公网客户端都是 `127.0.0.1`**，
  按 IP 的令牌桶会把所有朋友算成同一个人，一个人手快、其他人一起被限。
- 决策：
  1. **按连接限流**（key = `socket.id`）：建房 10/分、加入 20/分、Intent 20/秒；
  2. **全局上限**：房间 2000、连接 5000；
  3. **不做按 IP**，等将来真的上 VPS 直连（能拿真实 IP）再说；
  4. 超限**回人话不断线** —— 断线会让正常玩家以为是自己的网掉了。
- 实现细节（踩过的点）：
  - 固定窗口而非滑动窗口：只挡「脚本级」洪泛，精度差几秒无意义，内存是滑动窗口的 1/N；
  - **连接断开必须 `forget(socket.id)`**，否则限流表自己变成内存泄漏；
  - **Intent 超限必须走 `game:events` 的 rejected 分支**：客户端 `socket.emit(gameIntent, intent)`
    没带 ack 回调，只回 ack 玩家什么都看不到；
  - **被限流的 Intent 不写进回放** —— 没有状态变化，记进去会让记录与实际不符。
- 阈值判据：真人建房一次几十秒、点击上限约 5 次/秒；脚本实测 0.3~0.5 ms/间（约 2000~3000 次/秒）。
  取「宽到真人永远碰不到、窄到脚本立刻撞墙」。
- 影响：`server/src/room/rate-limit.ts`（新增）、`index.ts`（三处闸门 + 连接上限 + 断开清理）、
  `shared/constants.ts`（`RATE_LIMITED` 码与文案）、`room.ts`（`count()`）。
- 破坏性：**否**（正常操作频率远低于阈值；E2E 29/29 全过）。

## ADR-0040 · 回放保留 7 天 + 500 MB，启动与每日各清一次（D-182）

- 背景：每个房间销毁时落一份 JSON，**此前没有任何删除逻辑**。实测 8 天 903 份 / 12.7 MB，
  约 113 份/天；按此速率一年约 4.1 万份 / 590 MB。磁盘不会被写满，但**文件数没有上限**
  会拖慢备份与全盘扫描，且尖峰（被刷出十万间房）无法回收。
- 决策：`keepDays = 7` + `maxBytes = 500 MB`，**启动扫一次、之后每 24 小时一次**。
  两条规则依次生效：先按保留期删，再按总量从最旧删。
- **保护窗口（不可配）**：最近 1 小时内写过的文件**绝不删**。原因很具体 ——
  清理与落盘都是异步的，删到「正在写」的那份就是静默丢数据，而这类丢数据没有任何报错。
- 为什么把「算」与「删」分开：`planReplaySweep` 是纯函数（输入文件清单与策略，输出待删清单），
  边界条件（保留期临界、总量临界、保护窗口）全部可用单测钉住；IO 只在外层两个函数里。
- 失败处理：单文件删除失败只计数不中断，整体失败只记日志 —— 与 D-176 同一个取舍：
  后台维护不能把服务拖死。
- `REPLAY_SWEEP_DRY_RUN=1` 只算不删。**首次上线就是这样跑的**：扫到 919 份、待删 0 份；
  正式模式再跑一次结果相同，**没有删掉任何一份回放**。
- 影响：`server/src/room/replay-maintenance.ts`（新增）、`index.ts`（启动 + 24h 定时器，`unref()`）、
  `README-运行说明.md` §7.3。
- 破坏性：**否**。

## ADR-0041 · 回放「观看」入口默认关闭，记录链路不变（D-183）

- 背景：Era 2026-10-20 —— 公网走 SakuraFrp 隧道，**每月流量有限**。
  回放观看若真做起来，每次复盘都要把一份 `replay.json` 从服务器传到浏览器
  （BO3 完整局实测几 MB），点几下就能吃掉可观配额。
- 决策：结算面板的「查看回放」按钮**常显但置灰**（`disabled`），
  由 `client/src/features.ts` 的 `REPLAY_VIEW_ENABLED = false` 控制；
  服务端记录链路（`Intent → ReplayRecorder → app/replays/*.json`）**一行未改**。
- 为什么用「常显的置灰按钮」而不是干脆不画：
  1. Era 的指令是「置灰」，不是「移除」——入口本身要可见，才知道这个功能存在；
  2. 将来开放只改一个常量，不用回头补 UI；
  3. 置灰按钮带 `title` 说明原因，避免用户以为是坏了。

  且是回放校验（M8）与问题复盘的唯一依据；关掉它省不下流量，只丢证据。
- 顺带确认没有旁路：静态服务根目录是 `client/dist`，`app/replays/` 在其之外；
  服务端没有任何读回放的 HTTP 路由 —— 公网取不到回放文件，唯一入口是本地 CLI。
- 影响：`client/src/features.ts`（新增）、`TableScreen.tsx`（GameOverPanel 末尾一个按钮）、
  `e2e/game.spec.ts`（断言可见 + disabled + 文案）、`README-运行说明.md` §10。
- 破坏性：**否**（纯 UI 新增；E2E 29/29、单测 278 全过）。

## ADR-0042 · 删除「阵营」，一套卡组自带指挥官（D-184）

- 背景：Era 2026-10-20 —— **「我的设计里不存在阵营之分，卡池可以混选，我建议删掉阵营限制，
  根据卡组选择就行了。卡组编辑的时候还要有个地方选指挥官。」**
  此前（D-235）建房 / 加入要选阵营，服务端据此装配「阵营对应的 30 张 + 该阵营指挥官」，
  自建卡组只能覆盖主卡组那 30 张 —— 与 Era 的模型不符（他从没打算限制混搭）。
- 决策：
  1. **删掉阵营这一层**：`Faction` 类型、`FactionSchema`、`room:create` / `room:join` 的 `faction`
     字段、主界面两个阵营下拉。
  2. **一套卡组 = 30 张主卡 + 1 位指挥官**：`SavedDeck.commander`、`room:deck` 也带 `commander`；
     服务端 `validateCommander` 校验（必须存在且 `type === 'commander'`）。
  3. **编辑器顶部选指挥官**：三位指挥官横排（炎刃军统领 / 霜律裁决官 / 星轨观测者），
     点击切换、高亮当前选中。详情里**不显示 ±** ——
     指挥官不占主卡组，摆两个必然无效的按钮只会让人以为坏了。
     **2026-10-20 更新（D-185）**：右上角那个「看效果」按钮被 Era 否掉了（「太挫」），
     改成**选中的再点一次打开详情**；入口仍在不丢功能，只是不再单占一个按钮。
  4. **缺省回退改为确定性**：`defaultDeckSetup` 不再按座位轮换三套；只给指挥官 → 用它自带那套，
     都没给 → 第一套基础卡组。轮换是阵营时代的产物，会让两席「默认」就不同。
- 为什么合成「一套」而不是并列两个字段各自生效：
  玩家心智里「我带的这套牌」本来就包含指挥官。并列会允许「霜律指挥官 + 炎刃 30 张」这种
  界面说不清的组合 —— 规则上合法（卡池不限体系），但它应该由玩家**主动**选出来，
  而不是因为两个字段各自缺省、服务端随便补出来。
- 兼容处理（三处都不能漏）：
  1. 老客户端仍带 `faction`：`z.object()` 会 strip，**不报 400**（schema.test 钉住）；
  2. 旧 localStorage 卡组没有 `commander`：补默认指挥官，**不丢那 30 张**；
  3. 旧 `replay.json`：`setup` 里本来就有 `commanders`，结构与语义都没变，回放不受影响。
- 一个容易踩的点：`RoomDeckSchema` 必须显式声明 `commander`。`z.object()` 对未声明键是 strip，
  漏了就是「客户端换了、服务端还用旧的」，界面上完全看不出（`payload`、`deck` 各踩过一次）。
- 影响：`shared/src/{types,schema,default-decks,index}.ts`、`server/src/{deck-pool,index}.ts`、
  `server/src/room/{types,room,session}.ts`、`client/src/{decks,HomeScreen,DeckScreen,TableScreen,useRoom,types}.ts`、
  测试 6 个文件、`README-运行说明.md` §9 / §10 / §11、`docs/01` §1.2、`docs/11` X-18、`docs/16` 模拟表。
- 破坏性：**是（协议）** —— `faction` 字段删除。但入站是 strip 而非拒绝，老客户端只是失去
  「按阵营分配」的行为，不会 400；对局照常开始。新客户端与旧服务端组合不兼容（`commander` 会被旧
  schema strip → 回落默认卡组），因此**前后端必须一起更新**（本项目同端口同源发布，天然一致）。

## ADR-0043 · 「展示」收敛为 core 里唯一一个动作 `revealAction`（D-234）

- 背景：Era 2026-10-21 —— **「算展示，展示这个动作需要单独提取出来」**。
  此前「展示」在代码里有**两套实现、两种含义**：
  1. `effects/index.ts` 的 `starRevealEvents()` —— 技能展示（星图凝视等）：翻开 → 进展示区 →
     星轨 +1 → 星轨环抽牌 → 逐张「展示时」→ 回牌库底。**完整展示**。
  2. `effects/primitives.ts` 的 `revealFromDeck()` —— 指挥官受伤用：只把牌从卡组挪到展示区再归位，
     **不触发星轨、不触发「展示时」**。同一个词，行为却不同。
  更糟的是第三、四、五处（焚典 / 号令 / 受伤）各自手写 `card:revealed` 事件，新增一个展示来源
  就得再抄一遍顺序，漏一步就是「展示了但没算星轨」这种只有对着日志才看得出的错。
- 决策：core 只保留**一个**展示入口 —— `effects/index.ts` 的
  `revealAction(at, state, owner, ctx, { n | uids, reason, settle })`，
  固定五步：① 取 uid（按张数取卡组顶 / 或调用方指定）→ 逐个 `deck → reveal` + `card:revealed`
  → ② 星轨观测者 Ⅱ 按张数 `star:mark` → ③ 星轨环每回合首次展示抽 1 → ④ 逐张派发 `onReveal`
  → ⑤ 按 `settle` 归位（`bottom` 牌库底 / `cost` 费用区 / `graveyard` 弃牌区）。
  `revealFromDeck` 删除；`starRevealEvents` 退化为 `settle: 'bottom'` 的薄封装。
- 五种来源全部改走它：
  | 来源 | 张数 | 归位 | 触发星轨 / 展示时 |
  | --- | --- | --- | --- |
  | 技能展示（星图凝视等） | 由卡面定 | 牌库底 | 是 |
  | 焚典 | `CREMATION_REVEAL` | 牌库底 | 是 |
  | 号令 | `ORDER_REVEAL_COUNT` | 牌库底 | 是 |
  | **指挥官受伤** | 每 1 点伤害各 1 张 | **费用区** | **是（本次改口径）** |
- 关键口径变化：指挥官受伤**从「只翻开」变成「真展示」**——受 1 点伤害也会触发星轨 +1
  与「展示时」效果（含连锁：受伤展示翻出的卡若有展示时效果，照样结算）。
  理由：Era 的指令是「算展示」，那么它就该和别的展示走同一条路；若保留「不触发的展示」，
  就是在 core 里留第二套语义，等于没提取。
  代价：`growth.test.ts` 一条既有断言从 `starTrack === 7` 变 `8`（多出的 1 层来自受伤展示），
  已在用例注释里写明来由。这是**规则层的实质变化**，不只是重构。
- 为什么把「归位」做成参数而不是三个函数：归位是展示的**最后一步**，前四步完全一致；
  拆成三个函数会让「新加一个展示来源」又要选函数，而源与归位并非一一对应（受伤也是 1 张/次）。
- 为什么 `ensureDeckSize` 放在动作内部：牌库不够时把弃牌区洗回，是**展示能不能成立**的前置条件，
  放在调用方就一定有调用方忘写（原先只有星图凝视写了）。
- 影响：`core/src/effects/{index,primitives,blade-arcana,blade-order}.ts`、`core/src/combat.ts`、
  五个 `commanderDamageEvents` 调用点（`rules/attack`、`rules/commander-attack`、
  `effects/{frost-arcana,star-arcana,star-troops}`）、`effects/growth.test.ts`、
  `docs/16 §5.7`、`docs/17 §2.1.1`。
- 破坏性：**否（协议）/ 是（规则语义）** —— `GameEvent` 类型与协议字段一个没动，回放仍可重放；
  但「指挥官受伤」现在会产生额外的 `star:mark` 与展示时效果，历史回放重跑会得到不同的
  `stateHash`。本项目回放只用于**当次**校验（`replay:verify` 对比录制时的 hash），
  不做跨版本回放，故不影响既有文件。

## ADR-0044 · 人机对战：AI 是服务端的一个「系统 Intent 玩家」（D-242）

- 背景：Era 2026-10-21 —— **「我想要开人机局，跟人机对战，这样我不用开两个窗口测试了」**。
  这是**测试工具**需求（自己跟自己打太麻烦），不是要做一款 AI 游戏。
- 三个可选落点：

  | 方案 | 做法 | 为什么不选 |
  | --- | --- | --- |
  | 客户端本地 AI | 前端算出一手，冒充对手发 Intent | 客户端无权提交别人的 Intent（服务端按 `playerId` 校验席位），要实现就得开后门 —— 等于把「弱客户端」这条铁律拆了 |
  | 离线单机模式 | 引擎整个跑在浏览器里 | 与现有联机链路是两套东西：回放、限流、断线、房间全要重写；而且测不出联机问题 |
  | **服务端 AI 席位**（采纳） | 服务端在房间里占一个 `playerId = 'ai'` 的席位，用**系统 Intent** 走与真人完全相同的链路 | — |

- 决策：
  1. **AI 是一个真实席位**（`AI_PLAYER_ID = 'ai'`，`AI_NICKNAME = '电脑'`），
     不是「客户端模拟」也不是「旁路改状态」。它 `connected` 恒为 `true`、`ready` 恒为 `true`、
     **不登记 `byPlayer`**（没有 socket、不会重连、不参与 `prune` 回收）。
  2. **落子走 `submitSystemIntent`**（`actor: 'system'`，`reason: 'ai'`）——
     与超时兜底、掉线判负同一条链路。于是事件流、`stateHash`、回放记录全部天然正确，
     客户端**不需要为 AI 写任何特例**：它看到的只是一串普通的 `GameEvent`。
  3. **一拍一条 Intent，间隔 `AI_STEP_DELAY_MS = 600ms`**。不在服务端内部把「抽牌+出牌+攻击」一次推完：
     那样要么绕过引擎自己推演（破坏 `stateHash`），要么把多条 Intent 混成一条（回放对不上）。
     600ms 也让玩家看得清对面在做什么。
  4. **决策是 core 里的纯函数** `decideAiMove(state, aiId, cards, now)` —— 不读时钟（`now` 由会话层传入）、
     不碰 IO，因此可以像规则一样被单测精确摆局面验证，并有「自对弈跑完整局」的用例兜住死循环。
  5. **被拒必须兜底**：AI 的启发式不保证每步合法（例如某张法术当前无合法目标）。
     服务端在 `out.kind !== 'accepted'` 时直接补一条 `phase:advance`，
     绝不原地重试 —— 否则同一拍会无限发出同一条必被拒的 Intent，对局停死。
- 强度定位：**能完整打完一局的启发式**，不是博弈 AI。铺场出最贵的随从、攻击打掉最弱的敌方随从、
  前排挡不住就打脸、每战斗阶段用一次指挥官攻击。不做算斩杀 / 留牌 / 攒技能。
  要调强度只需要改 `decideAiMove`，不影响任何其它层。
- 房间层配套：
  - `room:create` 新增可选 `solo: true`；为 true 时**容量强制 2**（规则只验证过 2 人）。
  - 真人离开 → 房间销毁：`leave` / `prune` 的「空房」判定放宽为「只剩 AI」，
    否则每进一次人机房就泄漏一间（与 D-181 同类）。
- 影响：`shared/{constants,schema,index}.ts`、`core/src/{ai,ai.test}.ts`、
  `server/src/{index,room/room,room/room.test}.ts`、`client/src/{HomeScreen,useRoom}.tsx`、
  `client/e2e/solo.spec.ts`。
- 破坏性：**否** —— `solo` 是可选字段（老客户端不带即纯双人房）；其余全是新增。

## ADR-0045 · 回合时限是「房间级事实」，不是全局常量（D-244 / H18）

- 背景：`TURN_TIMEOUT_MS = 30s` 从 ADR-0010 起就是一个全局常量。Era 2026-10-21 要求
  「时长建议在建房能选择，30-60-180-999」—— 于是「多久算超时」不再有唯一答案。
- 候选：

  | 方案 | 做法 | 否决理由 |
  | --- | --- | --- |
  | 全局配置（env） | 改 `TURN_TIMEOUT_MS` 或加环境变量 | 一间服务器只有一个值，玩家选不了；且 env 已被测试占用 |
  | 单局属性（`GameState`） | 写进对局状态 | 它是「这间房怎么打」的约定，跨局不变；进状态会让 BO3 第 2 局无端多一个字段差异 |
  | **房间属性**（采纳） | `Room.turnTimeoutMs` + `TurnTimer.setTimeoutMs` | — |

- 决策：
  1. **`Room.turnTimeoutMs` 是权威来源**，随 `publicView` 下发给双方（对手也要知道这局给多久）。
  2. **协议只认白名单**（`TURN_TIMEOUT_OPTIONS`），非法值**回落默认而不是 400** ——
     拒绝一个手误的 `120000` 等于让人建不了房，代价远大于「档位不自由」。
  3. **`TurnTimer.setTimeoutMs` 在计时中调用直接抛错**。计时中改时限只有两种结局：
     当前回合截止时刻莫名跳动，或只对下一回合生效（同一局前后规则不一致）。
     建房一定发生在 `arm()` 之前，所以拒绝违规用法是安全的。
  4. **优先级：环境变量 > 房间档位 > 默认值**。环境变量唯一的用途是 E2E 放宽
     （播放队列 + 慢速渲染会吃掉真实秒数），生产不得设置。
- 影响：`shared/{constants,schema,index}.ts`、`server/src/{index,room/room,room/types,room/turn-timer}`、
  `client/src/{HomeScreen,TableScreen,useRoom,types}`、`client/e2e/{form,room}.spec.ts`。
- 破坏性：否（字段可选；默认值 30s → 60s 是行为变化，已记 CHANGELOG 与 `docs/09` H18）。

## ADR-0046 · shared 拆成「类型 / 常量 / 协议」三入口，首屏不碰 zod（D-250 / T-03）

- 背景：`@app/shared` 的根 `index.ts` re-export 了 `schema.ts`，于是**任何**从根导入
  （哪怕只为一个类型）都会把 zod 拖进依赖图。client 自己早就改走 `@app/shared/constants`，
  但 `core`（client 的直接依赖）有 43 处从根导入 —— 首屏一直在为一份「服务端才用」的校验库付费。
- 关键事实：`shared/src/types.ts` 是**纯类型文件**（零 import、零运行时导出），
  所以 `import type ... from '@app/shared/types'` 编译后完全消失，是零成本的正确落点。
- 决策：
  1. `shared/package.json` 增加 `./types` 子路径出口。
  2. `core/src/**` 与 `client/src/**` 的导入按符号分派：**类型 → `/types`、常量 → `/constants`、
     卡池 → `/cards`**。服务端继续用根导入（它本来就要 schema）。
  3. 目录规约：**新增符号先想清楚它属于哪一类** ——
     - 只是类型 → `types.ts`；
     - 与玩法无关的常量 / 纯函数 → `constants.ts`；
     - 需要 zod 的入站校验 → `schema.ts`（只有 server 可以运行时 `parse`）。
     往 `types.ts` 塞运行时值会把这条防线打穿。
- 结果：生产构建 gzip **144.53 → 121.16 kB（−23.37 kB）**，同期还净增了引导与音效代码。
- 影响：`shared/{package.json,src/index.ts}`、`core/src/**`、`client/src/**`。
- 破坏性：否（纯模块边界）。

## ADR-0047 · 点击必须有即时、可见、有兜底的反馈

- **状态**：已采纳（2026-10-21）
- **背景**：Era 连续两次报「点击没反应」（D-255 断线静默排队 / D-256 提示画在屏幕外）。
  两次都不是规则或协议错误，但**玩家无法区分「没点上」「服务器拒了」「网络断了」**，
  只能反复点击，反而把自己撞进限流。
- **决策**：凡是「玩家点击 → 等服务端回应」的交互，必须同时满足三条 ——
  1. **即时**：点击后同一帧内界面要有变化（按钮变文案并禁用），不等服务端。
  2. **可见**：结论必须渲染在**视口内**，且不随滚动丢失（`sticky`）。测试用
     `toBeInViewport()` 断言，**不能用 `toBeVisible()`** —— 滚出屏幕的元素对它也算 visible。
  3. **有兜底**：ack 超过 8 秒未回 → 明确说明并给出「重试 / 刷新」两条出路，
     不允许无限等待。
- **附带约束**：`localStorage` 写入、`socket.emit`、ack 回调都必须能容错
  （写入可能抛错、`res` 可能是 `undefined`）；服务端对**校验失败也要打日志**，
  否则「玩家说没反应、服务端查不到记录」无法收敛。
- **代价**：每个请求型交互多 3 个状态（busy / 结论 / 超时）与约 40 行模板；
  换来的是玩家永远知道「现在发生了什么」。
- **适用边界**：对战桌的 `Intent` 是 fire-and-forget（服务端广播 `GameEvent[]`），
  不套 ack 这套，但**断线横幅**（D-255）承担同样的职责。

## ADR-0048 · 开局换牌是「游戏开始之前」的阶段，不属于任何回合

- **状态**：已采纳（2026-10-21）
- **背景**：Era 指出「换牌这个动作不是在第一回合做，而是在游戏开始之前做」。
  旧实现（X-17）把换牌挂在**各自第一个充能阶段**，理由是「后攻方要等一回合才轮到自己」。
  代价是：开局直接进第一回合，换牌按钮藏在操作条里、30 秒后消失 —— 玩家根本不知道有这个阶段。
- **决策**：
  1. `Phase` 新增 `'mulligan'`，`game:started` 之后停在这里；**不进 `PHASE_ORDER`**
     （六阶段进度条属于一个回合，换牌不属于）。
  2. 换牌**双方同时**进行，各自确认一次即锁定；**双方都确认**才发 `mulligan:closed`
     进入第一回合充能阶段。先攻方的 `chargeCount` / `firstChargeAt` 由该事件写入。
  3. `mulligan:closed` 由**最后一个确认的人**在规则层触发，不由服务端事后补事件 ——
     保证回放与实时走同一条路径。
  4. 时间窗（`MULLIGAN_WINDOW_MS`，30s）**只拦「换牌」不拦「跳过」**。
     否则窗口一过双方都关不掉阶段，整局卡死。
  5. 计时器分两套：换牌阶段用固定窗口 + 「替未确认方提交跳过」；
     回合用房间档位 + `turn:end`。`buildTimeoutIntent` 在 `mulligan` 阶段返回 `null` 自守。
  6. 守卫**手写**，不用 `baseGuard` —— 它含「必须轮到你行动」，与「双方同时」冲突。
- **代价**：`Phase` 联合类型变宽，所有 `switch (phase)` 需补分支；
  改动前的回放文件按新 reducer 重算会与记录的 `stateHash` 分叉（保留期 7 天，不迁移）。
- **替代方案与否决理由**：
  - 「保留旧挂点，只把按钮做显眼」→ 治不了根本问题：第一回合已经在走了，
    Era 要的是「开始之前」这个语义。
  - 「一个客户端一个客户端轮流换牌」→ 需要额外的轮次状态，且双方都要等对方，
    体验比同时选更差，规则收益为零。
  - 「换牌超时不处理，等人来点」→ 一个人不开页面就整局卡死。

## ADR-0049 · 出牌是两段式；顶替事件必须先于登场事件

- **状态**：已采纳（2026-10-21）
- **背景**：Era 要求「费用使用时需要支持选择哪些卡」「随从召唤支持选择位置，该位置有随从
  可以直接顶替，被顶替的卡进弃牌区」。这两条都把「出牌」从一次点击拆成了两个决策。
- **决策**：
  1. `play` Intent 新增两个**可选**字段 `costUids` / `slot`。不传即旧行为
     （费用按顺序取前 N、落最小空槽）—— AI 与老客户端不被迫改。
  2. 随从区的**存储仍是紧凑数组**，另用 `CardInstance.slot?: number` 记「摆在哪一格」；
     `boardSlotFor(dst, want)` 优先用事件指定的槽，被占/非法才退回最小空槽。
     改成稀疏数组会打穿几十处 `for (const c of board)`。
  3. **指定了位置就不再报 `BOARD_FULL`** —— 满场顶替是正常操作。
  4. **顶替必须先产「旧卡离场」事件，再产「新卡登场」事件**。
     reducer 是逐事件落地的：顺序反了，新卡找空槽时旧卡还占着格子，会被挤到别处。
     这是本 ADR 唯一的硬约束，写在这里而不是注释里，因为它是**跨文件的隐式契约**。
  5. 客户端交互固定为「位置 → 费用」两段：费用区比该付的多才弹选择面板
     （没得挑时多一次点击只是噪音）；拖拽到具体格子等同于选该位置。
- **代价**：一次出牌最多 3 次交互；`play` 路径的 E2E 需要统一 helper（`commitPlay` / `confirmPay`），
  否则「漏掉选位置」会表现成「点了出牌卡还在手上」——D-256 已经证明这种坑会反复出现。
- **约束（踩过的）**：格子点击必须挂在**最外层**（`onSlotClick`），不能只挂在卡片上 ——
  空格子没有卡片节点，挂上去就等于「空位点不了」。

## ADR-0050 · 选择链的收尾由规则层兜底，不靠每个效果模块自觉

- **状态**：已采纳（2026-10-21）
- **背景**：issue #88（炎刃骑士死锁）。每张卡的效果模块在回答选择时要自己发
  `choice:cleared`，漏一次就是灾难：`pendingChoice` 永远挂着，界面上的选择面板关不掉，
  玩家任何别的操作都被「请先回答选择」挡住；而选项是挂起那一刻的快照，
  残留的卡还能再点一次，于是「除外 +1」能无限叠加。
- **决策**：
  1. `effectChooseRule` 统一收尾：回答返回的事件里若**既没有**新的 `choice:pending`、
     也**没有** `choice:cleared` / `game:ended`，就自动补一条 `choice:cleared`。
  2. 效果模块**仍然应该**自己写 `choiceCleared`（表达意图、事件流里位置更准）；
     兜底只在漏写时生效，且检测到已有收尾时不会重复补。
  3. 顺带把「陈旧选项」堵死：回答前校验目标卡仍在预期区域；`exileCard` 对已在除外区的卡
     返回空而不是产出「exile → exile」的空移动。
- **理由**：与 `promoteQueuedChoice`（队列唯一出队点）同一思路 ——
  **一个机制的收尾只放一处**。这类「漏一行就死锁」的契约不该靠 N 个模块自觉，
  且它坏掉时的表现是「整局卡住」，不是一条显眼的报错。
- **代价**：事件流里可能出现一条「模块没写、规则层补的」`choice:cleared` ——
  语义完全相同，回放与 hash 不受影响。
- **替代方案**：① 只修骑士那一个模块 → 下次加卡照旧会漏；
  ② 用类型系统强制 `choose` 返回值必须含 `choice:cleared` → TS 无法表达
  「事件数组里必须含某类型」，成本远高于收益。

## ADR-0051 · 卡牌详情走「长按 / 右键 / 详情按钮」，不再用卡面角标

- **状态**：已采纳（2026-10-21）
- **背景**：issue #87。原入口是卡面右上角 16×16px 的「?」，还压在卡外侧。
  64px 宽的卡上，这 16px 既难点中又容易误触（点歪 = 选中卡片）。
  Era 明确要求「修改方案」，不是「把按钮做大一点」。
- **决策**：
  1. **长按 400ms** 为触屏主路径（卡牌游戏通用手势），命中区 = 整张卡；
  2. **右键** 为桌面快捷入口；
  3. 选中手牌后，卡上方的浮动操作组里加「详情」按钮（正常按钮尺寸）；
  4. 删除角标按钮，以及 `onDetail` 从 TableScreen 穿到 CardTile 的四层回调链。
- **实现约束（踩过的）**：
  - 长按挂在**桌子根节点的 `pointerdown` 委托**上，标记是 `data-card-uid` ——
    挂在卡片按钮上就没法覆盖「对手的卡 / 置灰的手牌 / 五区缩略」。
  - 长按与拖拽共用同一次 `pointerdown`：移动 >10px 取消长按；
    长按触发后必须压掉随后补发的 `click`，否则「看详情」会顺带选中手牌。
  - 长按没有视觉提示，操作条必须常显一句「长按卡牌看详情」。
- **代价**：长按在慢速触摸设备上有 400ms 的延迟感；桌面用户不学长按也有右键兜底。
- **替代方案**：① 把「?」做到 24px → 仍然压在卡上挡住卡名/数值，且没有解决误触；
  ② 双击 → 与「快速连续操作」冲突，且移动端双击语义不稳定；
  ③ 点卡名打开详情 → 与「点卡选中」冲突，玩家会频繁误开。

## ADR-0052 · `PHASE_ORDER` 之外的阶段，每个入口都要显式挡

- **状态**：已采纳（2026-10-21）
- **背景**：D-262。D-259 引入 `phase = 'mulligan'` —— 它发生在「游戏开始之前」，
  不属于任何回合，因此**必须**留在 `PHASE_ORDER` 之外（否则六阶段进度条多一格，
  且 `turn` 语义会被污染）。但项目里所有「是不是该推进了」的判定都用
  `PHASE_ORDER.indexOf(phase)`，而对 `mulligan` 这个调用返回 `-1`：
  - `-1` 不满足 `idx >= 0`，于是 `advanceOnce` 落到末尾的
    **「结束阶段之后 → 进下一回合」** 分支，`mulligan` 被当成「回合已经打完了」；
  - 表现是开局直接 `turn + 1` 进第二回合充能，玩家从没见过换牌界面。
- **决策**：
  1. **不在 `PHASE_ORDER` 里的阶段，是「非回合阶段」**，任何以 `indexOf` 判阶段
     位置/推进的函数都必须在最前面显式挡掉它，不得依赖 `-1` 的兜底语义。
  2. 「推进」函数（`advanceOnce`）对它返回 `[]` —— 空操作，让
     `turnEndRule` 的循环自然收尾；「入口」函数（`phaseRule` / `turn-end`）
     对它返回明确错误 —— 让玩家看见「这里不能推进」。
  3. 服务端调度 AI 时，换牌阶段不看 `activeSeat`（双方同时进行），
     改看「这个 AI 自己确认了没有」。
- **理由**：`indexOf` 的 `-1` 在语义上同时表示「不在列表里」和「什么都没找到」，
  而这两个含义在这里对应完全相反的行为（不推进 vs. 推进到下一回合）。
  让 `-1` 落到 `else` 分支，等于把一个「不该存在的情况」当成「最末尾的情况」处理。
  这类 bug 不会抛错、不会写日志、状态还自洽 —— 只能靠实机发现。
- **代价**：每加一个非回合阶段，都要在 3~4 个入口重复一次守卫。
  接受这个成本：重复是显式的，而 `-1` 兜底是隐式的。
- **替代方案**：① 把 `mulligan` 塞进 `PHASE_ORDER` 并在所有遍历处特判 → 更糟，
  六阶段进度条与 `PHASE_ORDER.length` 相关的代码全部要改；
  ② 把 `advanceOnce` 的 `idx === -1` 改成抛错 → 会让 `turnEndRule` 的空步收尾失效，
  且超时链路也要跟着改；③ 用 `Phase | 'mulligan'` 的类型区分「回合内阶段」与
  「非回合阶段」两个类型 → 方向正确，但会牵动 `state.phase` 的全部使用者，
  留作后续重构（当前以注释 + 守卫表达同一约束）。

## ADR-0053 · 「搬牌」必须写成事件，纯函数返回的新牌堆不算数

- **状态**：已采纳（2026-10-21）
- **背景**：issue #91。`takeFromDeck` 在卡组抽空时把弃牌区洗回（docs/16 §11），
  返回 `{ events, deck, graveyard, taken }` —— `deck` / `graveyard` 是**算对**的，
  但事件流里只有 `rng:advance` + `deck:shuffled`。而 reducer 的 `deck:shuffled`
  只在**现有 deck** 里按 order 重排，不搬牌。结果：玩家点抽牌，弃牌区一张没动、
  手牌一张没加，界面毫无反馈。
- **决策**：
  1. **跨区域移动必须产 `card:moved`**。任何「我帮你把牌从 A 挪到 B」的语义，
     都要落成事件，不能只体现在返回值里。
  2. 洗回时的顺序：`rng:advance` → `deck:shuffled`（**紧邻**，游标与洗牌成对）→
     `card:moved` × N（按洗好顺序）。此时 deck 为空，逐张 append 的最终顺序
     恰好等于 order，两者一致。
  3. 实现细节类位移可以**在展示层合并**（`client/log.ts` 把 `graveyard→deck`
     折叠成一条「把弃牌区 N 张洗回卡组」），但**不能在事件层省略**。
- **理由**：本项目是事件溯源 —— **事件流是状态的唯一真相**，返回值只是给调用方
  继续推演用的中间量。一个「返回值对、事件流缺」的函数看起来完全正常：
  TS 不报错、纯函数单测能过、日志一片干净，只有玩家点下去才发现什么都没发生。
  这类缺陷的检测成本远高于预防成本。
- **代价**：洗回会产生 N 条事件（15 张 = 15 条），回放文件略大。可接受：
  一次对局洗回 2~3 次，量级在几十条，且日志侧已折叠。
- **替代方案**：① 让 reducer 的 `deck:shuffled` 顺手把弃牌区的对应 uid 搬进来 ——
  事件更少，但一个事件改两个区域，将来「只洗牌不搬牌」的场景会被误伤；
  ② 只改 reducer 不改事件 —— 同上，且回放看不出牌是怎么回去的。

## ADR-0054 · 缩略卡的尺寸不能由「自己撑出来的父级」反算

- **状态**：已采纳（2026-10-21）
- **背景**：issue #92。390px 下区域里的卡横向溢出、压到隔壁区。`compact` 卡走
  「高由格子决定、宽按 5:7 反算」，但它的**两层包装都是 shrink-to-fit**，
  于是卡上的 `w-full` / `max-w-full` 的百分比基准就是卡自己 —— 循环引用，
  约束等于不存在。格子内容宽 63px，卡算出 81px。
- **决策**：
  1. **宽度必须从包装层定下来**：`CardOf` 外套与 `CardTile` 内层都要
     `w-full min-w-0`（`min-w-0` 破掉 flex 子项默认的 `min-width:auto`，
     否则内容最小宽度会顶掉 `max-width`）。
  2. **内层补 `items-center`**：flex 默认 `align-items: stretch` 会把卡高拉满，
     覆盖 `aspect-ratio` 推导出的高度（这正是「宽度改对之后卡变成窄条」的原因）。
  3. **窄屏宽度驱动、宽屏高度驱动**（`h-auto w-full max-h-full` + `sm:h-full sm:w-auto`）：
     窄屏时宽度是稀缺资源；宽屏时保持「填满格子」（桌面观感不变）。
- **理由**：`aspect-ratio` + 百分比宽度的组合里，**谁定谁**必须明确。
  一旦基准落回元素自身，浏览器不会报错，只会安静地溢出。
- **代价**：390px 下缩略卡变小一号（63×88 而不是 81×114），卡名更容易被截断 ——
  但换来「不压住隔壁区域的数值」，后者会让玩家**读错信息**，优先级更高。
- **替代方案**：① 只给容器加 `overflow-hidden` —— 卡仍按 81px 排版，只是被裁掉边缘，
  等于把问题藏起来；② JS 量容器算尺寸 —— 引入 resize 监听与首帧跳动，
  纯 CSS 能解决就不该上 JS。

## ADR-0055 · 牌桌只放「对局进行中必须一直可见」的东西

- **状态**：已采纳（2026-10-21）
- **背景**：issue #92 的第二阶段（Era 明确「用浮窗显示堆叠区内容，而不是直接在牌桌上显示」）。
  牌桌是 `h-dvh` 的固定高度网格，六排按 `flex-1` 均分；而堆叠区（弃牌 / 除外 / 费用 / 法术）
  的张数**随对局单调增长且没有上限**。两者注定不相容 —— 任何「排得更紧」的优化都只是
  把问题推后。上一版（D-264）就错在这里：只把卡压小了一号，卡多了一样塞不下。
- **决策**：
  1. **牌桌只常显「对局进行中必须一直可见」的信息**。堆叠区只留「区名 + 张数 + 入口」，
     内容进浮窗。
  2. **按信息性质分三态**（`ZoneBox.content`，互斥枚举）：
     `'cards'` 直接铺（指挥官 —— 攻击目标，收起来就没有攻击入口）、
     `'float'` 点开浮窗（弃牌 / 除外 / 费用 / 法术）、
     `'count'` 只显示张数、不给看（卡组 —— 顺序是隐藏信息）。
  3. **用枚举而不是两个布尔**。`hideCards + inspectable` 允许「藏起来又看不见」这种
     无意义组合，加第三种区域时极容易配错。
  4. **浮窗 `createPortal` 到 `document.body`**。留在区域容器内部会让 `zone-*` 里数得到
     浮窗的卡（DOM 语义就错了）；祖先一旦有 transform / filter / contain，`fixed`
     还会退化成相对祖先定位。
- **理由**：界面元素的**容量**必须 ≥ 它承载的数据的**上限**。堆叠区没有上限，
  所以它不该是「牌桌上的一个格子」，而应该是「一个可持续增长的集合的入口」。
  这条判据可以直接复用到以后的区域设计（比如新增「流放区」「已施放法术堆」）。
- **代价**：多一步点击（看弃牌区要先点开）；浮窗遮住牌桌，看牌与操作不在同一视野。
  后者是真实成本 —— 如果 Era 需要「边看边打」，应改成可拖动的浮层面板（暂未做）。
  **→ 2026-10-21 Era 确认「居中就好」**：不做可拖动面板，居中模态即最终形态（D-266）。
  上面这句保留原文以留痕，结论以本行为准。
- **替代方案**：① 区域内部横向滚动 —— 15 张卡横滑，卡面 63px 宽，卡名全被截断，
  等于没看到内容；② 只显示最近 N 张 + 「更多」 —— 玩家会问「为什么我的弃牌区只有 5 张」，
  计数与内容对不上比看不到更糟；③ 缩小卡面继续塞 —— 就是 D-264 的死路。

## ADR-0056 · 换牌窗口只有一个裁决者（服务端计时器）

- **状态**：已采纳（2026-10-21，修 issue #99 / D-267）
- **背景**：换牌窗口原先由**两处**同时判定：
  1. `core/rules/mulligan.ts` 按固定 `MULLIGAN_WINDOW_MS`(30s) 拒「窗口后换牌」；
  2. `server` 的 `armMulliganTimer` 到点替未确认方提交跳过。

  两处写同一个数，看起来「一致」，但 Era 2026-10-21 要求**换牌时长跟随回合时限**
  （「不要固定值」），而回合时限是**房间配置**（建房选 30/60/180/999 秒）。
  一旦窗口要跟着档位走，core 就拿不到这个值 —— 它是纯函数，`RuleContext` 里只有 `now` 与卡池。
- **决策**：**窗口只由服务端计时器裁决**。
  1. `core` 的换牌规则**不读时间**，只回答「阶段还开着吗」；`MULLIGAN_EXPIRED` 错误码一并删除。
  2. 窗口时长计算集中在 `room/mulligan-timeout.ts` 的 `mulliganWindowMs`：
     **环境变量 > 房间档位 > `MULLIGAN_WINDOW_MS` 默认值**，与回合计时器完全同口径。
  3. 到点后计时器替未确认方提交 `{ returns: [] }`，阶段关闭；此后再提交换牌得到的拒绝是
     `WRONG_PHASE`（「当前已不是开局换牌阶段」）。
- **理由**：规则层拿到窗口值只有两条路，都不划算 ——
  塞进 `RuleContext`：回放重验（`replay:verify`）必须拿到**同一个值**，否则会出现
  「实时接受、重放拒绝」，而回放文件里没有记录当时的窗口；塞进 `GameState`：改动状态结构、
  影响 `stateHash`，为一个时长改哈希链不值得。
  服务端计时器本来就是「时间」的唯一权威（ADR-0017 的精神：时钟只在会话层读），
  它一个裁决者就够了。
- **代价**：窗口过期后、计时器真正触发前的**几毫秒**里，换牌请求仍会被接受（状态还是 `mulligan`）。
  这属于「谁先跑到」的竞态，结果无害：玩家少换一张或多换一张都在合理范围，且不会出现
  「接受了一半」——提交是原子的。相比之下，原来的双裁决会直接让阶段关不掉，代价大得多。
- **替代方案**：① 把窗口写进 `GameState`（改哈希链，见上）；② 保持 core 判窗口，
  并在 replay `setup` 里记 `turnTimeoutMs`（可行，但等于把配置塞进回放格式，
  以后加任何房间级时长都要再改一次回放 schema）。

## ADR-0057 · 界面判定只认「已落地」的事件批次

- **状态**：已采纳（2026-10-21，修 issue #101 / D-268）
- **背景**：客户端为了动画把服务端事件**逐条** reduce 并按相位停顿（`FX_MS`，
  `phase:changed` 750ms、`turn:changed` 1100ms）。一个回合边界在事件流里是两条：
  `phase:changed(… → charge)` 与紧随其后的 `turn:changed`。两条之间出现一帧
  「阶段已是下一回合的充能、`activeSeat` 还是上一家」—— **从未真实存在过**的局面。
  界面照着它渲染，结束回合的一方先看到「你的回合 · 充能阶段：点手牌里的随从…」。
- **决策**：**归属类判定（谁在行动、该做什么）只信「整批事件已落地」的状态。**
  1. 播放队列对外暴露 `turnPending`：批次里含 `turn:changed` 时，**入队即置位**，
     应用该事件时复位；队列播空仍未复位则强制清除（防悬挂）。
  2. 阶段指引与顶栏归属收进纯函数 `turnGuidance(state, me, turnChangePending)`：
     `turnChangePending` 时不给指引、文案显示「回合切换中…」。
  3. 这条纪律**只约束「解释性 UI」**（该做什么、谁的回合）。棋盘、区域、手牌照旧
     逐条播放 —— 动画本来就是让玩家看见「过程」，过程里出现中间态是设计的一部分。
- **理由**：事件流把回合边界拆成两条是**正确**的（`turn:changed` 与相位推进是两件事，
  回放与日志都需要分别看见它们）。错误在于消费端把「时序上的中间态」当成
  「语义上的合法状态」。若反过来改引擎顺序（`turn:changed` 提前），中间帧会变成
  「第 N+1 回合 · 阶段 结束」—— 同样不存在的局面，只是没那么误导；而且会牵动
  回放、日志与既有事件序列测试的预期，收益为零。
- **代价**：`turnPending` 是客户端自造的派生状态，必须保证**一定能落下**，
  否则顶栏永久停在「回合切换中…」并停掉所有指引（比原 bug 更糟）。
  故 `pump` 的 `finally` 里有一条「队列空即复位」的兜底，且快照重置时一并清除。
- **替代方案**：① 改引擎事件顺序（见上，否决）；② 给回合边界单发一个复合事件
  （改协议 + 回放格式，代价远大于收益）；③ 播放期间干脆整体冻结 UI 直到整批落地
  （会吃掉所有动画节奏，且与本项目「让玩家看见过程」的取向冲突）。

## ADR-0058 · 种子 → 随机游标只有一个派生入口，且要记进回放

- **状态**：已采纳（2026-10-21，修 issue #103 / D-269）
- **背景**：引擎早就种子化（ADR-0010：`seed + Intent 序列` 唯一决定结果），
  服务端也一直在产**每局不同的**种子（`nextSeed()` 取 `Date.now()`，ADR-0021）。
  但 `createInitialState` 把随机游标写死成 `0`，`seed` 只是存进状态供记录 ——
  种子与随机流之间那条线从来没接上。结果是每局洗牌都从同一游标出发，
  牌序、先后手、起手完全相同。Era 的报法是「每次进游戏都是固定起手，没洗牌吗」。
- **决策**：
  1. `seed → 游标` 的派生**只有一处**：`core/rng.ts` 的 `initialRngCursor(seed)`。
     它用 FNV-1a 而不是 `seed >>> 0`：服务端种子来自毫秒时间戳，相邻值极多，
     哈希能把它们打散；顺带让 `seed = 0` 不会退化成历史上的坏值 0。
  2. `createInitialState` 用 `opts.rngCursor ?? initialRngCursor(opts.seed)`。
     可选入参**只有一个用途**：回放重建。
  3. `SeedSetup` 记录 `rngCursor`，随 `replay.json` 落盘。回放因此不依赖派生算法 ——
     以后换算法，老文件仍按当时记录的游标重跑。
  4. `replay:verify` 对**没有该字段的历史文件**补 `0`：D-269 之前真实游标就是 0，
     这是兼容，不是默认值。补了它，历史回放不会被这次修复判成损坏。
- **理由**：把「配置/派生」与「记录」分开，是这个项目反复吃过的教训（ADR-0056 的双裁决）。
  游标既可以从种子算，也可以被记录 —— 两个来源必须在**同一个类型**里明确先后，
  否则回放与实时开局会静默分叉（「实时接受、重放分叉」是最难查的一类）。
  这里的选择是「记录优先、派生兜底」，因为记录是事实，派生是规则。
- **代价**：
  1. `InitialStateOptions` 多了一个可选字段，读代码的人要知道「什么时候会传」——
     已在注释里写明「只有回放重建会传」。
  2. 历史回放里的 `initialHash` 与「用 seed 重新派生」的结果必然不同。这是**正确**的：
     那些局当时真的用了游标 0。靠 `replay:verify` 的兼容补 0 才对齐。
- **替代方案**：
  ① 直接 `rngCursor: opts.seed >>> 0`（更短，但相邻毫秒种子洗出的牌序相关性没被打散）；
  ② 不记录游标、每次由 seed 派生（改动最小，但今天这次改算法就会让所有历史回放失效，
     且无法区分「文件录错了」与「算法变了」）；
  ③ 在 `game:start` 事件里塞 seed 再派生（要改事件 schema 与哈希链，收益为零）。

## ADR-0059 · 「选择一个随从」按效果极性分治，不用一条规则盖住整张卡

- **状态**：已采纳（2026-10-21，修 issue #105 / D-270；修订 H22）
- **背景**：统领Ⅰ 的 3/5/7/9 四个档位卡面都写「选择一个随从」。H22（2026-10-19）
  把四档统一限成己方，理由是「给自己选才合理」。但 5 档是**破坏** ——
  限己方等于只能自杀，Era 在现场直接撞上：菜单第 3 项列出的全是自家随从。
- **决策**：
  1. 候选范围按**效果极性**决定，不按卡面措辞：增益类（3 力量 +1 / 7 伤害 +1 / 9 攻击后重置）
     = 己方；破坏类（5）= 双方场上。
  2. 力量值门槛（5 档「力量 ≤ 除外区炎刃数」）对双方用**同一口径**：卡面值，
     不吃临时加减 —— 与 1 档召唤、号令一致。差别只在于「谁能被选」。
  3. 候选跨双方时，客户端负责**说清是谁的**（`choiceSideLabels`：只在真的跨边时标注
     「我方 / 敌方」，单边列表不加噪声）。
  4. 这条只适用于统领Ⅰ。其它卡的「选择敌方随从」类效果（冻结、审判）本就是显式敌方，
     不因这条放宽。
- **理由**：把「四档共用一句注释」换成「逐档写明」，是这次真正的修复 ——
  共享注释会让下一读者继承一个自己没验证过的前提。极性分治的好处是**可解释**：
  为什么 5 档能选对方、3 档不能，答案不是「因为 Era 说了」，而是「破坏对己方无意义」。
- **代价**：5 档的目标列表可能比 3/7/9 长一倍；玩家有误点自家随从的可能。
  由两步确认（先选子效果、再选目标）与「我方 / 敌方」标注兜住。
- **替代方案**：① 四档都放开成双方（最贴卡面字面，但增益档会列出对手随从，
  多出一屏无意义选项）；② 维持全限己方、把 5 档从菜单里删掉（等于改卡面）；
  ③ 5 档只给对手（把「也能破坏自家」这条玩法删掉，与卡面「选择一个随从」不符）。

## ADR-0060 · 没有决策点的阶段由引擎瞬穿，客户端只跟着播

- **状态**：已采纳（2026-10-21，修 issue #109 / D-271）
- **背景**：抽牌在 2026-10-18 改成「玩家点卡组触发」。先攻首回合该抽 0 张
  （`FIRST_TURN_DRAW = 0`，8 血版口径），这个阶段因此**没有任何可做的事** ——
  界面仍亮「点击抽牌」、`phaseRule` 仍拒绝「推进阶段」，玩家只能点一个空按钮。
  reset 阶段此前已有同类问题的解法：进阶段即瞬穿、事件流保留。
- **决策**：
  1. **判断「这一拍有没有决策点」只在引擎里做**：`advanceOnce` 进 draw 后若
     `drawCountFor(state) === 0`，补一条 `draw:completed` 再继续推进。
     抽几张这件事仍然只有 `drawCountFor` 一处定义（也因此把它搬到 `phase.ts`，
     避开 `draw.ts → phase.ts` 的反向依赖）。
  2. 客户端**不复制**这条规则：`canDraw` 与抽牌提示都调用引擎导出的 `drawCountFor`。
     前端要判的只是「服务端真的在这个阶段吗」，而张数是同一个函数算的。
  3. 为什么客户端还要判一次：事件**播放**有个时间窗（`phase:changed` 每条停 750ms），
     瞬穿那一批中间会出现 `phase === 'draw'` 的帧。那一帧里服务端早已在主要阶段，
     若给按钮，玩家点下去必然换回 `WRONG_PHASE` —— 属于「界面在说谎」。
     这与 ADR-0057（归属判定只信已落地批次）是同一类处理：**中间帧不提供动作入口**。
- **理由**：把「停下来等人点」与「没人可点就别停」都放在状态机里，客户端只负责播放与渲染，
  是 ADR-0002（弱客户端）的直接推论。反过来做（前端按张数隐藏按钮）会让规则出现第二份实现 ——
  这个项目已经因为「注释/实现符号相反」踩过 4 次，不能再开一处。
- **代价**：`advanceOnce` 多了一条递归分支（与 reset 同构，深度最多再进一层）；
  `drawCountFor` 的物理位置从 `draw.ts` 搬到 `phase.ts`，读代码的人要跟着走一步
  （已在两处注释里写明原因）。
- **替代方案**：① 前端按 `FIRST_TURN_DRAW` 隐藏按钮（规则两份，且服务端仍会在阶段里等）；
  ② 保留停顿但把按钮换成「本回合不抽牌，继续」（多一次点击，Era 明确否掉）；
  ③ 把「首回合抽 0 张」改成抽 1 张（改规则，不在本单范围）。

## ADR-0061 · 拖拽落点判断搬进纯函数，前端只做手势 → Intent 的映射

- **状态**：已采纳（2026-10-21，修 issue #108 / D-272）
- **背景**：拖拽出牌（B3-1）原本写在 `TableScreen.onDragUp` 里，用 `data-drop` /
  `data-drop-slot` / `data-drop-uid` 三个 DOM 标记手写分支。它只覆盖了「拖随从上场」，
  法术这条路径**两个自然落点都是坏的**：法术区没注册落点，随从格又必然带一个非法 `slot`。
  根子不在漏写一行，而在**这段判断没法测** —— 组合情况只能靠人肉点。
- **决策**：
  1. 落点语义抽成 `selectors.dragDropIntent(input)`：输入是「拖的什么 + 落在哪」，输出是
     `{kind:'play'|'charge'|'attack'|'none', slot?, targetUid?}`。组件只负责取 DOM 标记。
  2. **法术与设置法术在落点层就视为「没有位置」**：落到法术区正常出牌；落到随从格
     也按无位置出牌（忽略格子号），**不把非法 slot 传给规则层** ——
     `play.ts` 的守卫保留，前端只是不制造非法请求。
  3. 高亮跟着牌型走：拖随从亮随从区（与充能阶段的费用区），拖法术亮法术区。
     统一高亮随从区等于在暗示「法术也往这儿拖」。
- **理由**：这是「把可判定的分支从组件里拿出来」的第三次（前两次是 `actionability`、
  `turnGuidance`）。好处是可以精确构造组合，而不是等 E2E 撞。规则合法性一条都没搬过来 ——
  这里判的只是「这个手势想干什么」，能不能干仍由服务端裁决（ADR-0002）。
- **代价**：`onDragUp` 多一次 `CARD_POOL` 查表（拖手牌时）；`dragDropIntent` 需要知道牌型，
  故调用方必须传 `cardType`（忘传时按「非随从」处理 —— 会忽略位置，比带非法 slot 安全）。
- **替代方案**：① 只给法术区加 `dropKey` 就收工（拖到随从格仍报错，Era 报的第二个现象还在）；
  ② 放宽 `play.ts` 允许法术带 slot（把守卫拆了换拖拽通过，等于让前端错误合法化）；
  ③ 在组件里再写一遍分支并加 `isSpell` 判断（仍然无法单测，下次还会漏）。

## ADR-0062 · 静态托管：资源缺失必须 404，缓存按「有没有内容哈希」分档

- **状态**：已采纳（2026-10-21，修 issue #107 / D-273）
- **背景**：SPA 回退被写成「所有未命中的 GET 都回 index.html」。开发态无感，
  生产态一旦缺资源（隧道丢包、重建空窗），服务端就把 `index.html` 当 CSS/JS 发回去：
  `200` + `text/html`，浏览器按 MIME 拒绝解析且**不重试、不报错** —— 页面静默无样式。
- **决策**：
  1. **回退只给路由**：路径不带扩展名、不在 `/assets/`、不是 `/socket.io`、不是 `/health`
     才回 `index.html`；其余 404 + `application/json`。判据落在
     `server/src/static-serve.ts` 的 `isSpaRoute()`（纯函数、可单测）。
  2. **缓存按内容哈希分档**：`/assets/*`（Vite 产物，名字里带 hash）→ `immutable, max-age=31536000`；
     `index.html` → `no-cache`；其余不给策略（沿用默认）。
  3. **构建不许有「没有资源的空窗」**：`build:atomic` 先把新产物构建到 `dist.new`，
     增量复制进 `dist`，**最后**才覆盖 `index.html`（它是「加载哪套资源」的指针），
     并保留上一代资源一版。
  4. **客户端兜底**：`link`/`script` 的 error 事件 → 顶部红条提示刷新。样式全内联 ——
     坏的可能正好是样式表，不能指望 CSS 渲染提示。
- **为什么不用目录 rename 做原子切换**：本机（Windows）对**有内容的目录**改名返回
  `EPERM`，第一次试跑直接把 `dist/` 弄丢了几分钟。复制 + 换指针同样没有空窗，
  且不依赖平台语义。
- **代价**：`dist/assets` 里会多留一代旧文件（下一次构建清掉）；`build:atomic` 比
  `vite build` 多一次复制（~400 kB，可忽略）。`build` 脚本保留原样，测试与 CI 用。
- **替代方案**：① 只改 notFoundHandler、保留默认缓存（少一半收益，隧道那条路径仍在）；
  ② 只加长缓存不改回退（缺资源仍是 200 HTML，问题不变）；
  ③ 用 nginx 托管静态（要额外进程与配置，本机与隧道方案都不划算）。

## ADR-0063 · 手牌宽度由「固定卡宽 + 横向滚动」改为「flex 均分 + 上限封顶」

- **状态**：已采纳（2026-10-21，修 issue #113 / D-277）
- **背景**：手牌是固定宽（`w-16 shrink-0 sm:w-20`）+ 外层 `overflow-x-auto`。390×844 下
  手牌区内容宽约 372px，后手 6 张 = 6×64 + 5×4(gap-1) = 404px，**横溢出 32px**，
  最后一张被裁在滚动区外。滚动本该兜住它，但卡上有 `pointerdown` 拖拽判定，
  手指横滑会被当成「拖牌出牌」，**实际滑不动**；也没有任何「右边还有一张」的提示
  （`clientWidth 372 / scrollWidth 404 / overflow-x visible`）。
- **决策**：
  1. 卡位改为 `flex-1 min-w-0` 的**均分单元**，宽度由父级 flex 行决定，`max-w-16 sm:max-w-20`
     封顶（窄屏 6 张各约 58px、8 张各约 43px；桌面仍以 80px 封顶，视觉与改前一致）。
  2. `CardOf` 新增 `fluidWidth`，与浮窗网格用的 `fluid` **分开两个 prop**：两者都落到
     `w-full min-w-0`，但一个由 `grid-cols-N` 定宽、一个由 `flex-1` 均分 —— 合并会让
     「改手牌行」与「改浮窗网格」变成同一处，互相牵连。
  3. `overflow-x-auto` 保留，但降级为**兜底**（手牌多到均分都不可读时才用得上）。
- **为什么不在「滚动」上继续修**：要让触屏横滑可用，必须让卡在横滑时不启动拖牌判定，
  等于给同一个手势定义两种含义（手指往右 = 滚动还是出牌？）。手牌张数是可枚举的
  （30 张牌组、每回合抽 1、上限 8 张量级），宽度能算出来就不该让玩家去滑。
- **代价**：手牌 ≥10 张时单卡降到 34px 以下，卡名与数值开始不可读（实测未出现在 8 血
  8 张的节奏里；真出现时的下一档是「扇形叠压」，需要美术定形，另立需求）。
- **替代方案**：① 手牌区加边缘渐隐 + 半张卡露出（提示能滑，但滑不动的问题没解）；
  ② 按张数在 JS 里算宽度（把布局知识搬进状态，SSR/首帧都会闪）；
  ③ 选中后再滚动定位（issue 原文已否：等于「先猜着点一下才能看见」）。

## ADR-0064 · 瞬时提示条不进 fixed 层，不覆盖任何常显信息

- **状态**：已采纳（2026-10-21，修 issue #114 / D-277）
- **背景**：`notice`（「已开人机房」「请先点击卡组抽牌」「已自动重连」）写成
  `fixed left-1/2 top-16 z-50`。`top-16` = 64px，恰好压在回合数 / 阶段 / 计时那一行上
  （实测提示条 y 64~102、计时 y 63~83），换牌与充能阶段**唯一的时间信号被整个盖住**。
  同类问题已复发一次（#99 / D-267 换过一个位置）。
- **决策**：
  1. 提示条改为**在流内独占一行**，位置固定在「阶段动作提示条」下方、顶栏上方；
     出现时把桌面整体下推约 30px，消失时回弹。
  2. 顶栏加 `flex-wrap` + 每段 `whitespace-nowrap`：挤不下时**整段换行**，
     不把词拆开（原来 390px 下会被压成「开 局」「阶段 换 / 牌」）。
  3. 窄屏折叠成长资源 `my-growth`（`hidden sm:inline`）：390px 顶栏放不下，
     该数值在区域与卡面详情里仍可查；桌面不变。
- **判据（后续同类改动照此办）**：任何 `fixed` 提示都不得覆盖**当前阶段唯一的决策依据**
  （计时、当前阶段名、可操作对象）。宁可让布局抖一下，也不能让玩家读不到状态。
- **代价**：提示条出现/消失会使牌桌位移约 30px（4s 内自行消退，或点一下立即关掉）。
- **替代方案**：① 固定右对齐避开计时（移动端没有右侧空间，仍会挤压）；
  ② 放到底部操作条上方（那里已是「出牌/充能」按钮与选位提示的密集区）；
  ③ 用 toast 队列 + 遮罩穿透（要引入新依赖与层级体系，收益不抵成本）。

## ADR-0065 · 抽牌是私有信息：战报按视角分叉，且默认 fail-closed

- **状态**：已采纳（2026-10-22，修 issue #136 / Era 拍板「对手只记『抽了 1 张』，自己抽牌仍显示卡名」）
- **背景**：`log.ts` 的 `deck → hand` 一行对**双方**一律输出卡名，于是开局第一秒战报就
  逐张念出对手起手（「电脑 抽到 霜律审判」），而同一块桌面上对手手牌区写的是
  「对方手牌 N 张」。同一份信息一半隐藏一半公开，玩家没法判断哪条规则是真的。
  卡池只有 45 张、同名上限 3，牌名信息量极大：知道对手刚抽到「霜律终裁」等于知道
  下回合不能让他铺满冻结随从 —— 这不是「多知道一点」，是**信息泄露**。
- **决策**：
  1. `describeEvent` 增加第 4 参 `viewer: string | null`，**`null` = 未知视角，按
     「看不到对手手牌」处理（fail-closed）**。将来新增调用点忘记传视角时，
     宁可少显示，也不要泄露。
  2. `deck → hand` 仅当 `playerId === viewer` 输出「抽到 <卡名>」，否则输出「抽了 1 张」。
  3. **公开区一律不动**：打出 / 展示（`card:revealed`）/ 置入费用区 / 被破坏 仍念卡名。
     「只藏抽牌」必须与「对手整段静音」区分开 —— 后者会毁掉战斗战报，已有 3 条单测钉死。
- **为什么在表现层收口，而不是在协议层脱敏**：客户端本来就是靠事件流 `reduce`
  重建**全量**状态（含对手手牌），这是「服务端权威 + 客户端只 reduce 事件」架构的基础。
  要在协议层藏，就得给对手的 `card:moved` 摘掉 `uid/defId`，客户端将无法重建对手手牌，
  重连回放、状态哈希与顶替选位等一整套依赖状态的判定都会受影响。
  **代价**：DevTools 里仍能看到对手手牌 —— 这是第一版的已知限制，记进 T-0031 残留项；
  真要防作弊得另立需求（服务端下发脱敏快照 + 客户端按「未知牌」建模）。
- **判据（后续同类改动照此办）**：**战报 / 横幅 / 详情不得比桌面更公开**。
  桌面上已经只显示「N 张」的信息，任何呈现层都不许把它展开成具体卡名。
- **代价**：起手同时抽 5 张时会连出 5 条「电脑 抽了 1 张」（`draw:completed` 事件
  不带张数，逐张 `card:moved` 各成一行）。合并成「抽了 5 张」需要给引擎事件加 `count`
  字段，属协议变更，本轮不做 —— 观感问题，不泄露信息。
- **替代方案**：① 双方都不念卡名（issue 选项②，Era 未选：自己的抽牌也变模糊，新手更糊涂）；
  ② 服务端脱敏事件（见上，架构代价大）；③ 战报里把对手抽牌整行吞掉（连节奏感都没了，
  玩家会以为对手没抽牌）。


### ADR-0065 补充（2026-10-22 02:55）：充能子项与判据修正

**1. 充能（`deck → cost`）同批收口。** Era 2026-10-21 23:47 在 issue #136 给的口径表
不只抽牌：

| 事件 | 自己 | 对手 |
| --- | --- | --- |
| `deck → hand` | 显示卡名 | 只记「抽了 1 张」 |
| `deck → cost`（充能） | 显示卡名 | **只记「充能 1 张」** |
| `deck → 展示` | 显示卡名 | 显示卡名（展示是公开动作） |
| `hand → 弃牌 / 除外 / 场上` | 显示卡名 | 显示卡名（离手即公开） |

原话：「充能那一行请一并收口 …… 只修抽牌会留下同款问题。」两条子项共用同一个
`viewer` 参数，口径只有一处；`viewer` 为 `null` 时两条都走对手分支（fail-closed）。

**2. 判据修正 —— 原来那句「战报不得比桌面更公开」用得不准。** 初版写成
「桌面上已经只显示『N 张』的信息，呈现层不许把它展开成具体卡名」，用在**手牌**上成立，
但用在**费用区**上不成立：对手费用区是 `content='float'` —— 框内只写张数，
**点开浮窗能看到卡面**（`TableScreen.tsx` 的 `ZoneBox` 三态注释与 `inspectable` 判定）。
精确表述应是：

> **战报是自动推送，不得把「桌面上需要主动点开才能看到」的私有流向信息，直接刷到玩家眼前。**

手牌与费用区**隐藏的严格程度本就不同**：手牌区是**纯文本** `section`（`TableScreen.tsx`
里直接渲染「对方手牌 N 张」，**连 `float` 都不是**，比 `count` 更彻底），
费用区是 `float`（主动可查看）。但两者都不允许战报被动推送卡名。
「主动点开仍能看到对手充了什么牌」是**已知限制**，与「服务端未脱敏、DevTools 可见」同类，
不在本次收口范围内。

**2b. 本次是「事件级隐藏」，不是「状态级隐藏」（QA 复验补的一条硬边界）。**
只藏「牌库顶 → 私有区」这两条位移事件的**即时文案**。卡本身仍进了客户端状态，
后续只要发生一条**目标区公开**的位移，卡名就照常印出来。已实测的路径：

- `cost → graveyard`（费用区卡进弃牌区，`log.ts` 的兜底位移分支）：上一回合被藏掉的
  「电脑 充能 N 张」里的那几张，进弃牌区时会以「XX：费用区 → 弃牌区」**把卡名说回来**；
- 这条**不是新漏洞**，而是本次收口范围的边界：弃牌区本身就是 `float` 可查看的公开区
  （点开浮窗就能看到全部弃牌的卡面），战报在这里念卡名并没有比桌面更公开。

结论：**别把本次修复理解成「对手的牌名从此不可知」**。它只保证「牌库顶流向私有区的那一刻
不被自动播报」。真要状态级隐藏，得走 ADR 里列的那条大改（服务端脱敏 + 客户端按未知牌建模）。

**3. `hand → cost` 不隐藏。** 判定条件必须带 `from === 'deck'`：从**手牌**主动充能是
玩家自己的动作、目标区可查看，按 Era 表格的「离手即公开」精神仍念卡名。把隐藏扩大成
「对手所有进费用区的都不念」会误伤「手牌充能」与「场上 → 费用区」两类公开动作。

**4. `viewer` 的写入时机。** `meRef` 原本只在 passive effect 里同步，比 `setMe` 晚一拍。
正常链路（建房 / 加入 / 人机局 / 双端）在 `setMe` 与开局之间隔着「点准备」一整轮渲染，
窗口不存在；但**刷新重连**的 ack 与首个事件批可能落在同一个 JS 任务里，
`pump()` 会读到 `meRef = null` → fail-closed → 自己的抽牌也退化成「抽了 1 张」。
故在 `acceptIdentity` 与重连处把 `meRef.current` 与 `stateRef.current` **同批同步**写。
方向本来是安全的（过度隐藏不泄露），但它是一个可见的行为退化，修它只花一行。

## ADR-0066 · 先攻第一回合抽 1 张（取代 ADR-0024 第 2 条的一半）

- 日期：2026-10-22
- 状态：已接受（Era 2026-10-21 拍板「先手抽 0 改成抽 1」；2026-10-22 校正口径
  「我要求抽 0 自动推进抽阶，不是跳过抽阶」「抽 0 自动推进，非抽 0 就手动，就这么简单」）
- 变更 ID：D-287 / issue **#139**；条文依据 `docs/16` §1 + §2.3.1 + §15 C-05
- 取代关系：**ADR-0024 决策 2 的「先手第一回合抽 0 张」作废**，改为 1 张；
  该条其余部分（先手 5 / 后手 6 起手、先手首回合不可攻击）**继续有效**。
  另注：同一决策里的「先攻首回合自动充能 0 张」（D-227）不受影响。

### 背景

8 血版本按 ADR-0024 给先手少抽一张作为「先动」的补偿，实测两个问题：

1. **先手反而更弱** —— 少一张手牌换来的是「多出一次充能窗口」，而 8 血节奏下
   首回合能打出的东西受 `maxCost = 1` 限制，少的那张牌在第二回合才变成实际劣势。
2. **首回合多出一个没有决策点的抽牌阶段** —— 抽 0 张却仍停在 `draw`，
   界面亮「点击抽牌」、点了什么也不发生（issue #109 的由来）。

### 决策

1. `FIRST_TURN_DRAW` 由 **0 改为 1**（`packages/shared/src/constants.ts`）。
   `drawCountFor` 是唯一张数来源，改常量即整链路生效，**不改任何调用方**。
2. **保留**「抽 0 张的抽牌阶段自动推进」这条分支（`phase.ts` 的 `advanceOnce`）：
   - 它守的是「无决策点阶段不停顿」这个**通用**能力，不是首回合特例；
   - 删除它等于把能力删掉，将来改数值或加特殊模式还要重写一遍；
   - 校正 Era 的原话：他要求的是「抽 0 自动推进」**不是**「跳过抽阶」。
3. 把判定抽成纯谓词 **`shouldAutoAdvanceDraw(count)`** 并在 core 导出。
   理由：#139 之后正常对局再也构造不出 0 张的局面，内联 `count === 0` 就成了
   「只能靠临时改常量才跑得到」的死代码 —— 谓词让它永远有直接测试。

### 后果

- **抽牌阶段的动画不许被吞**：事件流仍是 `phase:changed → draw:completed → phase:changed`，
  客户端按 `FX_MS['phase:changed'] = 750` 逐条播放，玩家能看到「抽牌阶段」那一拍。
- 先手强度上升（起手 5 + 首回合 1 = 6，与后手同为 6 但先动）。
  **只能靠 BO3 消化，不许加座位补偿**（Era 口径，同时写进 #139 的风险段）。
- AI 侧无额外改动：`ai.ts` 的抽牌决策读 `drawCountFor`，抽 1 时会正常点一次。

## ADR-0067 · AI 的技能门槛由效果模块回答，不由 AI 复制规则

- 日期：2026-10-22
- 状态：已接受
- 变更 ID：D-288 / issue **#137**
- 关联：ADR-0002（弱客户端 / 服务端权威）、ADR-0023（效果系统）、ADR-0066（先攻抽 1）

### 背景

AI 在 #137 之前**从不发动指挥官技能、从不用手牌充能**：`decideAiMove` 里根本没有
`effect:activate` / `charge:put` 两条分支。补这两条分支时，第一反应是把「付得起 2 费
且资源达到最低档」这类条件直接写进 `ai.ts` —— 这是错的，因为门槛是**卡面规则**：

- 统领Ⅰ的档位按「除外区炎刃数量」分 1/3/5/7/9；
- 裁决官Ⅰ的档位按霜痕 3/6/9；
- 观测者Ⅰ的展示张数按星轨 3/6；
- 而 **#138** 就要把这些档位整体前移（霜痕 3→2 等）。

在 `ai.ts` 抄一份，等于同一条规则维护两处；#138 落地时必然漏改其中一处。

### 决策

1. `EffectModule` 增加**可选**钩子 `aiCouldUse(state, ctx, owner): AiUseHint | null`。
   - 返回 `null` = 「现在发动没有意义或付不起」；
   - 返回 `{ via: 'activate', effectId }` → AI 发 `effect:activate`；
   - 返回 `{ via: 'attack-reveal' }` → 星轨观测者那种「挂在指挥官攻击上的付费前置」，
     AI 在 `commander:attack` 里带 `payload.reveal = true`。
2. 钩子**只读**：不产生事件、不改状态。玩家点按钮时的权威校验仍由 `activate` /
   `onCommanderAttack` 自己做（`usedGuard` + `payCostCards`）。
3. 「付得起吗」抽成 `canPayCost(p, n)`，内部直接调用 `payCostCards` 拿结果判断 —— 
   **不重写一套费用判断**（这个项目已经因「两处都对的契约拼起来会漏」栽过 4 次）。
4. `ai.ts` 只负责**时机**：主要阶段 → 战斗阶段（指挥官攻击时带不带 reveal）→ 充能阶段。

### 后果

- #138 改档位常量时，AI 自动跟随，不需要动 `ai.ts` 一行。
- 新增带主动技能的角色（第 4 个阵营）只需在效果模块实现 `aiCouldUse`，
  AI 无需改动 —— 与 ADR-0023「新增卡只加文件与注册行」同一条纪律。
- 钩子是可选方法：现有 35 个效果模块不受影响。

### 附带决定：技能先于出牌

`maxCost` 是「本回合所有支付的总张数上限」，技能与出牌共用 `usedCostThisTurn`。
issue #137 建议把技能放在「主要阶段末尾」，实测 120 局发动率 **0**（牌出完额度也见底）。
改为**先问技能、再用剩余额度出牌**；`effectsUsed` 保证每回合只发动一次。
代价是「技能抢了随从的额度」，但在 2 费档位上（技能固定 2 费）实测先手胜率从 41.7% 升到 49.8%，
没有证据表明这个顺序更差；#138 重测基线时一并复核。

> **2026-10-22 更正（D-289 / issue #143）**：本条里「充能（`deck → cost`）与抽牌同批收口」
> 那一支**作废**。理由有两条：
> 1. **依据是伪造的** —— 原文写「Era 2026-10-21 23:47『充能那一行请一并收口』」，
>    那条答复不存在。Era 批的只有抽牌；充能是我自己在 #136 评论里加的，还写进了
>    以「拍板结果」开头的表里（与 D-283 同类错误，同类错误第 2 次）。
> 2. **与规则相反** —— `docs/16 §7.5`（C-06）定的是「只看牌在哪个区」，
>    费用区属**公开区**，所以对手看得见是哪张牌。
>
> 取而代之的是 ADR-0068 的「按区域查表」。抽牌那半（决策 1、2）**继续有效**。

## ADR-0068 · 战报可见性按「区域」查表，不再逐事件枚举

- 日期：2026-10-22
- 状态：已接受
- 变更 ID：D-289 / issue **#143**；条文 `docs/16 §7.5`（C-06）
- 取代：ADR-0065 的「充能同批收口」那一支（见该条末尾的更正说明）

### 背景

同一条「这张牌对手能不能看见」在两天里被判断错了两次，每次都写在 `log.ts` 的
`card:moved` 分支里：

1. **#136**：`deck → hand`（抽牌）念卡名 —— 漏了，改成只记张数（正确）；
2. 同一批顺手把 `deck → cost`（回合充能）也藏了 —— **错了**，而且依据是伪造的
   （见 ADR-0065 的更正）；
3. **#143**：要改回来。

两次错误都出在「按事件枚举流向」这种写法上：每加一个动作就要再判断一次
「这条流向算不算公开」，而判断依据散落在注释里，没有单一可查的表。

### 决策

`log.ts` 增加一张**区域可见性表**（`docs/16 §7.5` 的代码化）：

| 分类 | 区域 | 对手可见 |
| --- | --- | --- |
| 隐藏区 | `hand`、`deck` | 不可见（连牌名都不可见） |
| 公开区 | 其余全部（`board` / `cost` / `graveyard` / `exile` / `commander` / `reveal` / `spell`） | 可见（含牌名） |

`card:moved` 的判定改成两条：

1. **两端都是隐藏区** → 对手只记张数（`抽了 1 张` / `移动了 1 张牌`）；
   自己（`viewer === playerId`）照旧念卡名。
2. **任一端点是公开区** → 念卡名，**不看 `viewer`**（公开信息不该因为少传视角而消失）。

「任一端点公开即可见」是刻意取宽的那一档：`board → hand`（回手）时对手早在桌面上
见过这张牌，抹掉卡名不会更安全，只会让战报比桌面更封闭 —— 而 §7.5.3 要求
「战报不得比桌面更公开」，反过来也不该更封闭。

### 后果

- 新增动作（弃置 / 洗回 / 置底）**不用再改分支**：看终点在哪即可。
- `deck → cost` 恢复念卡名；对手的充能行再加上归属前缀（`电脑 将 X 置入费用区`），
  否则双方共用一列战报时分不清是谁充的。自己的文案一个字不改。
- **桌面那半不需要改**：对手费用区本来就是 `ZoneBox content='float'`（点开浮窗可看卡面），
  #142 只是把战报藏了。本次补了一条 E2E 把这件事实钉住（`zone-inspect.spec.ts`
  「对手费用区可点开查看具体卡牌」），避免以后再有人「顺手收口」。
- `viewer` 的 fail-closed 语义**只对隐藏区流向**保留；公开区流向与视角无关。


## ADR-0069 · 档位门槛只存一处，标识符不带数值

- 日期：2026-10-22
- 状态：已采纳（D-290 / issue #138）

### 背景

统领Ⅰ的子效果标识符原来是 `l1/l3/l5/l7/l9` —— **键名就是解锁门槛**。
`docs/16 §15` C-02 把门槛前移到 1/2/3/5/7 之后，`l9` 实际解锁在 7 张，
标识符与行为相反。这类「符号说谎」在本项目已复发到第 5 次（注释 / 文档 / 字段名各有过），
每一次都要靠人肉对照才发现。

同时，门槛数字原本散在三处：`core` 的 `LEVELS`、`client` 的菜单文案、`cards.ts` 的卡面散文。
前两处可以引用同一个常量，第三处（散文）只能靠人工同步并记在文档里。

### 决策

1. **标识符用序号**：`tier1…tier5`，语义是「第几个子效果」，与门槛数值无关。
2. **门槛值只存一处**：`shared/constants.ts` 的 `BLADE_EXILE_TIERS`，`core` 的 `LEVELS`
   由它派生（`tier1: BLADE_EXILE_TIERS[0]` …），客户端菜单同样引用它渲染 `≥N 个：…`。
   之所以放 `shared` 而不是 `core`：**客户端也要用**，放 core 就是让客户端抄一遍数字。
3. **霜痕档沿用已有形态**（`FROST_MARK_TIERS` 数组 + `frostTierOf` 比较最大满足项），
   本就是「数字只有一处」，本次只改数组值。

### 后果

- 下次再调档位，**只改 `BLADE_EXILE_TIERS` / `FROST_MARK_TIERS` 两行**，AI、菜单、测试自动跟随；
  只有 `cards.ts` 的卡面散文需要人工同步（散文无法引用常量，已在 `docs/16 §15.4.2` 记一句）。
- **编号兼容**：`pendingChoice.options` 里存的是标识符，旧记录里写 `l1/l3/l5/l7/l9`。
  `blade-lord.ts` 的 `choose` 入口加 `LEGACY_SUB` **入站翻译**，出站一律新编号
  （「只在读入时兼容」的既定做法，D-184 移除 `faction` 字段时同理）。
  **但别把它当回放迁移方案**：D-290 之前的回放开局血量是 8，重算按 10 铺状态，
  `replay:verify` 在 `initialHash` 就报「开局哈希不一致」，走不到这条翻译（README §10 第 17 条）。
  实测确认：D-290 之前的回放**整体不可重放**，这是数值变更的必然代价，不是缺陷。
- 代价：`selectors.test.ts` / `effects.test.ts` 里手写的 `'l1'` 类断言要一起改。
  这是**一次性**的，且改完这些用例本身变成了「门槛表」的可执行文档。

## ADR-0070 · 界面状态语义分开；危险动作必须离开原位

- 日期：2026-10-22
- 状态：已采纳（D-292 ~ D-296 / issue #117 #118 #119 #120 #116）

### 背景

批次 1（T-0029 UI 黑盒审计）里五条缺陷看起来互不相关：引导首步错位、跳过按钮太小、
攻击目标高亮太弱、危险按钮贴常用按钮、首页入口在首屏外。但它们有三个共同的根因，
每一条都已经在别处复发过：

1. **一个视觉状态被用来表达两种相反的意思。** 「发光」既表示「点我来操作」，
   又表示「点我挨打」—— 前者是**主动作**、后者是**被动目标**。同一个描边色，
   玩家只能靠试。
2. **危险动作的确认发生在原位置。** 「认输」原位变红改写文案，第二次点击落在同一个像素上 ——
   二次确认挡的是「没想清楚」，挡不住「手滑连点」。
3. **重要入口的位置取决于内容的长度。** 「编辑卡组」排在表单最后，表单每加一行它就往下掉一行，
   最后掉出首屏。这类耦合在窄视口才暴露，功能用例永远测不出来（它们会先自动滚动）。

### 决策

1. **状态语义按「谁动」分开，不按颜色深浅分开。**
   - `glow` = 「你可以操作**我**」（自己的随从、自己的指挥官）；
   - `hittable` = 「**我**可以被他打」（对手的单位、对手的指挥官）；
   - 二者不得复用同一组样式，且**至少一个用文字表达**（`hittable` 的「可攻击」角标）。
     理由：颜色可以骗人（对方卡框本来就是青色，同色系描边看不出来），字不会。
2. **危险动作的确认必须改变落点。** 确认态一律用屏心浮层，浮层内两个按钮都 ≥44px，
   且必须有一个「返回」出口（`继续对战`）。判定方式不是「DOM 里有没有浮层」，
   而是命中测试：用 `elementFromPoint` 证明原按钮已被盖住。
3. **可点目标的最小命中区 44×44**（触控通行值），与视觉尺寸解耦 ——
   靠 `min-h-11 min-w-11` 撑开可点范围，用负边距把视觉位置摆回去。
4. **关键入口不参与「内容流」。** 编辑卡组这类**必须进得去**的入口放标题行（固定位置），
   不放在表单末尾；「首屏可见」由 `boundingBox()` 与视口高比来守（E2E 强制），
   不靠肉眼。
5. **引导的第一步必须等于玩家此刻所处的阶段。** 引导文案是静态数组，
   一旦流程前面插了新阶段（本例是 D-259 的换牌），静态文案就会指向一个不存在的按钮。
   `guide.spec.ts` 因此同时断言「引导标题」与「顶栏阶段」一致 —— 只断言文案会漏。

### 后果

- 新增界面状态时先问一句：**这个状态是「谁对谁做什么」**。动作方和被作用方不复用同一视觉。
- 新增危险动作（解散房间、清空卡组、离开系列赛）直接套浮层模式，不再各写一套。
- 首页/对战桌再追加控件时，「入口是否还在首屏」由 `home-layout.spec.ts` 兜底；
  加高度要同步收紧别处，这一条会立刻红。
- 代价：`CardTile` 多了一个 prop、`ZoneBox` / `BoardSlot` 各自多一个透传字段。
  可接受 —— 用「一个 boolean 传到底」换「语义不再混用」。

## ADR-0071 · 测试的随机性必须被测试自己证明掉

- 日期：2026-10-22
- 状态：已采纳（D-298 / issue #149，后续所有用例适用）

### 背景

`drag.spec.ts` 里那条「拖拽法术卡到法术区」会随机失败，issue #149 记为「约 2/3 概率」。
拆开看是两件事叠在一起，而它们的共同点是：**测试自己没说清它依赖什么**。

1. 用例的隐含前提是「手上有一张付得起的法术」。这个前提由随机起手决定
   （炎刃卡组 30 张里只有 7 张非随从，起手全随从约 17%），但用例没写、也没兜底。
   失败信息「手牌里应有付得起的法术」读起来像引擎坏了。
2. 那份随机本来不该存在 —— `webServer.env` 里的 `GAME_SEED` 会被
   `reuseExistingServer: true` 静默跳过（手动起 dev server 时）。配置里写了，
   文档里也写了，但**没有任何东西会因为「它没生效」而失败**。

同类事件已经发生过一次：D-290 的全量跑出现 1 红，最后靠人工复跑 3 次才排除嫌疑。
偶发的红最大的代价不是红本身，是**让人开始不信红**。

### 决策

1. **用例不得以「随机输入恰好满足某条件」为前提。**
   两种合法写法：① 构造出需要的状态（换牌、建卡组、指定视口）；
   ② 有条件地重试到条件成立，并给重试次数一个上限与一个有意义的超时错误。
   `ensureSpellToCast()` 走的是 ②：推进回合抽牌，最多 10 圈，超时错误写「牌库构成变了？」——
   因为跑满 10 圈意味着牌库不再是它以为的样子，那是需要被看见的新事实。
2. **依赖固定种子的测试必须自带守卫。** `determinism.spec.ts` 连开两局比对起手，
   不一致即红，且报错正文里直接写修法。配置 + 文档是「提醒」，守卫用例是「执行」——
   只有后者能让忘记带 `GAME_SEED` 在 10 秒内暴露。
3. **概率性缺陷的红证据用注入，不用重复碰运气。**
   「跑 20 次看有没有红」既慢又不稳定（实测 20 次 0 红），无法证明修法有效。
   做法是让代码**假装**处在坏输入下：本次让第 0 圈强制找不到，观察它是否多跑一个回合
   并变绿（18.4s → 34.3s）；再把重试上限压到 1 圈（等价旧逻辑）观察它变红。
   两次注入合起来才是「修法确实救了这种输入」的证明。
4. **断言观感时，读几何 / 计算样式，不读 class 或文本存在性。**
   `toHaveText('指挥官')` 在 `truncate` 下照样通过；只有 `scrollWidth > clientWidth`
   才说明它真的被裁了。同理「提示条不压手牌」必须用矩形相交判断。

### 后果

- 新增 E2E 时先问一句：**这条断言依赖什么随机量？** 依赖就用 ① 构造或 ② 重试，
  两者都不行就说明它测的不是一件确定的事，该换个验法。
- 概率性缺陷的报告里，「红绿证据」一栏写注入方式，不写「跑了 N 次」。
- 代价：`drag.spec.ts` 多了 40 行重试逻辑、超时从 90s 提到 150s；
  `determinism.spec.ts` 让全量多花约 9s。与「绿值得信」相比，这两项都便宜。

## ADR-0072 · 未实现的功能不以「占位」形式留在玩家界面

- 日期：2026-10-22
- 状态：已采纳（D-307 / issue #122，Era 拍板「整块隐藏」）

### 背景

对战桌右侧长期挂着一块 80px 的空面板，标题「对话框（占位）」，一局下来什么都不显示。
它不是美术占位（X-14 / X-15 缺素材，纯色块至少还能表达「这里有一张卡」），
而是**功能占位**：`docs/22` N-09 已经决定第一版不做好友/私聊，界面上却留着一个入口。

玩家看到它的第一反应不是「这功能还没做」，而是「是不是有消息没加载出来」或
「我和对手的聊天坏了」—— 一块空面板无法区分「没做」和「坏了」，这个歧义本身就是缺陷。
T-0029 黑盒审计把它记为 UI-10。

### 决策

1. **功能没做 → 界面不存在。** 不做「占位 + 说明」，不置灰，不留半成品骨架。
   玩家界面上的每一块区域都必须能被玩家用起来；用不起来的就删掉。
2. **允许的例外只有一种：素材缺失的美术占位。** 它承载的是**已实现**的玩法
   （卡面、图标），只是画得不好 —— 补素材就变好，和「功能没有」是两件事。
   界线：**占位块背后有没有一条能走通的流程**。有 → 可以占位；没有 → 删。
3. **删的时候必须同时改注释与文档。** 本例 `TableScreen.tsx` 的注释写着
   「日志框 + 对话框分开展示（B2-5）」、`docs/01` / `docs/06` 也这么记。
   只删 DOM 不改文字，下一次读代码的人会以为删错了，然后加回来。
   `docs/01` 是 Era 的输入原文，**不改原句**，补一条带日期的 ✅ 已定口径。
4. **守卫用几何，不用文案。** 「占位块还在不在」的唯一客观证据是
   「日志框底边到列底边还剩多少高度」（本例修前 84px）。文案断言只能防住
   同一句话，防不住换成「聊天（暂未开放）」的同构占位。两者都写，几何为主。

### 后果

- 新加一块界面区域前先问：**它背后有没有一条能走通的流程？** 没有就不加。
- 需求池里「已决定不做」（`docs/22`）的条目，界面上不得留任何痕迹。
- 代价：将来做聊天要重新加回这一列。`aside` 已是 `flex-col`，成本是几行 JSX；
  与「玩家一直看见一块坏掉的面板」相比可以忽略。
- 本例顺手修正了 `README §9` 里过期的单测 / E2E 计数（454 / 50 → 490 / 71）——
  「文档说 50 条、实际 71 条」会让「跑过了」无法核验，同属符号与实现不一致。

## ADR-0074 · 终局界面是覆盖层，不替换对战桌

- 日期：2026-10-22
- 状态：已采纳（D-308 / issue #154）

### 背景

一局打完，`TableScreen` 直接 `return <GameOverPanel/>`，牌桌连同右侧战报整块被替换。
后果有三条，都不是「少一块 UI」这么轻：

1. **唯一的复盘手段一起消失** —— 战报 DOM 不在（`[data-testid="log"]` 取不到），
   而回放入口从 D-183 起就置灰（公网流量考虑）。
2. **结算页信息量为零** —— 只有「败北 / 对局结束 / 你的指挥官生命归零 / 返回主界面」，
   打了几回合、双方最后剩多少血，全都没有。
3. **最需要上下文的那一秒，上下文被删了** —— 玩家想知道「我怎么输的」，
   恰好发生在战报最有用的时候。

### 决策

1. **终局界面必须是覆盖层，不得替换主视图。** 结束不是「换一个页面」，是「在当前页上说明」。
   这条对之后所有「结束态」界面（结算、系列赛、断线收尾）都成立。
2. **覆盖层要避让战报列，不是「盖住但能看」。** 遮罩压过的字读不清、也不能滚，
   等于没有。实现上用 `sm:right-40 md:right-56` 把容器缩到战报列左侧 ——
   **宽度取自 `aside` 自身的 `sm:w-40 md:w-56`**，两边必须一起改。
3. **可收起，且收起后出口不能丢。** 收起是为了让玩家去看完整战报，
   但「返回主界面」必须跟着留在那条小条里，否则等于把人锁在牌桌上。
4. **终局时引擎拒绝的动作，界面必须同步收回。** 覆盖层让牌桌继续渲染，
   于是「操作条还在」从理论问题变成现实问题：`actionability` 在
   `winner !== null || draw` 时全返回 false（`choiceOpen` 除外，见下）。
5. **结算自带本局摘要**：回合数 / 双方最终血量 / 终局成因。
   成因沿用 `endReason` 的翻译，不新造文案表。

### 为什么 `choiceOpen` 不一起关

终局仍挂着待定选择是设计上不该出现、但实现上可能的组合。把它一并禁掉，
玩家会卡在一个点不动的浮层里；而「回答选择」即便在终局也是引擎允许的动作。
**「界面要跟引擎一致」的准确表述是：引擎允许什么，界面就给什么；引擎拒绝什么，界面就收回什么。**
不是「终局就把一切关掉」。

### 后果

- 以后写任何结束态 UI，先问一句：**底下的牌桌和战报，还要不要给玩家看？**
  答案是要 —— 那就用覆盖层。
- 覆盖层出现时 `footer`（推进 / 结束回合 / 认输）整体不渲染。光靠 `actionability`
  关不住「认输」，它没有 `myTurn` 前置条件。
- 教训（可复用）：**「替换式整屏」是最容易写、也最容易把上下文一起扔掉的形态。**
  凡是「玩家可能需要边看边回顾」的界面，都要按覆盖层设计。

## ADR-0075 · E2E 的红必须在干净单实例环境下取得

- 日期：2026-10-22
- 状态：已采纳（D-308 取证过程中的事故）

### 背景

本轮改完 #154 跑全量，出现 3 红：`determinism`、`turn.spec`（先攻首回合抽 1 张）、
`drag.spec`。按流程先做对照 —— **把三个文件退回旧实现再跑，`determinism` 与 `turn` 照样红**，
`drag` 反而绿了。这说明它们不是本次改动的回归。

继续查，环境侧发现三样东西：

- `3000` 端口上跑着**另一个工作树**的 server（`Worktrees\Fcardgame\master-*`），
  我起的 server 与它抢同一个端口；
- `5173` 上没有人监听，vite 已经漂到 `5177 / 5178 / 5180 / 5181` —— **四个**孤儿 vite；
- 长跑的 vite 一直在打 `ws proxy error: ECONNRESET` / `write ECONNABORTED`。

客户端通过 vite 代理连 socket，代理脏掉之后：服务端照常计时推进回合，
客户端收不到事件 → 「界面停在第 1 回合、服务端已经是第 3 回合」。
那条用例的失败快照正好写着自己跑到了「第 3 回合 · 对手回合」。

把所有 dev 进程清成单实例、重新起一遍后，**全部 72 条一次通过**。

### 决策

1. **红之前先确认「红的是谁」。** 出红时第一件事不是改代码，是拿旧实现（或 master）
   跑同一条用例：**旧实现也红 → 先怀疑环境；只有旧实现绿、新实现红，才叫回归。**
2. **跑 E2E 前必须确认单实例。** 判定用事实，不用感觉：
   `netstat` 上 `3000` 与 `5173` 各只有一个 LISTENING PID、`/health` 返回 200、
   且这些 PID 属于本次刚启动的进程。
3. **端口漂移就是脏的信号。** `vite` 发现 5173 被占会自动换 5177…，
   而 `baseURL` 仍写死 5173 —— 于是用例打在旧实例上。看到 vite 没占 5173，先清进程再跑。
4. **手动起 dev 必须带全 `GAME_SEED` / `TURN_TIMEOUT_MS`。**
   `reuseExistingServer: true` 会让 `playwright.config.ts` 的 `webServer.env` **静默失效**
   （ADR-0021 的坑，#149 已由 `determinism.spec.ts` 守卫）。
5. **Playwright 自启在本机 Windows 上仍会卡满 120s**（配置注释早有记录）。
   所以本机 E2E 的正确姿势是：**手动起干净的 dev，再跑 playwright**，
   并接受「必须人工保证环境干净」这条前提 —— 由 `determinism.spec.ts` 兜住最致命的那一半。

### 后果

- 「72 passed」这句话的含金量取决于环境是否单实例。报告里必须写明
  「本次 E2E 跑在干净重启的 dev 上」，否则这个数字不可引用。
- 代价：每次跑全量前多了 30 秒的进程清理。相对「把环境问题误判成代码回归、
  再花一小时查一个不存在的 bug」，这个代价可以忽略。
- 与 ADR-0071 的关系：0071 管「用例自己要不要证明随机性被消除」，
  0075 管「证明它的那台机器是不是干净的」。两条都失效时，
  **绿同样不可信** —— 只是绿不可信更难被发现。

## ADR-0076 · 「再来一局」是房间级重开，不是 BO3 的下一局

- 日期：2026-10-22
- 状态：已采纳（D-309 / #125）

### 背景

结算页本来只有一个出口「返回主界面」。要再打一局得重建房 / 重新加入 / 等对手，
连试一套卡组的成本高到会让人不想再试（#125 原话：决定这个 Demo 是「玩一局看看」
还是「能连打几局」）。

项目里已经有一个「下一局」：`room:next-game`（BO3 局间）。看起来可以复用 ——
但它与本需求是**语义相反**的两件事：

- `next-game` 只在**系列赛未分胜负**时成立（`room.awaitingNext === true`），
  场上的比分继续累计，先手按 H33 轮换，且**只有房主**能点；
- 「再来一局」发生在**系列赛已经结束**之后，比分要归零，先后手重新掷骰，
  而且不能由一个人替对手决定「接着打」。

### 决策

1. **新增独立事件 `room:rematch`，不复用 `room:next-game`。**
   两者在界面上都叫「再打一局」，但比分、先后手、决策权三项全不同；
   合并成一个事件就必须在服务端按 `phase` 分支改语义，改完之后
   「`next-game` 到底会不会清零比分」这个问题将无法用一句话回答。

2. **重开要求双方都点；人机房单票即开。**
   人机房的 AI 没有按钮（也不该给它一个定时自动同意的机制 —— 那等于玩家被
   强制拖进下一局）。判断依据是 `room.seats` 里有没有 AI 席位，不另存 `solo` 字段。

3. **重开 = 销毁并重建对局运行时，房间对象不删。**
   回放只在房间销毁时落盘（`sweepRuntimes`）。就地重置 `rt.state` 会让上一局的
   `ReplayRecorder` 消失，直接违反 #125 验收 6（连打两局＝两份独立回放）。
   于是重开时做与销毁完全相同的事（清计时器、拔 AI 定时器、落盘回放），
   只是**不删房间**：席位、卡组、指挥官、房间码全部保留（验收 2、3 的核心）。

4. **重开后 `phase` 回到 `lobby`，走与首次开局相同的路径。**
   不新增「重开专用开局链」：`startGame` 的 `isFirstGame` 分支本来就能处理
   「满员 + 未 seeded」，多写一条只会多一处可能分叉。

5. **旧投票在三种时机必须清空**：席位离开、断线席位被回收、又打完一局。
   投票是对**特定那两个人、特定那一局**的同意，条件一变就该重来。

### 后果

- 结算页在同一张卡片上可能出现两类按钮：BO3 局间的「开始第 N 局」（房主独裁）
  与系列赛结束后的「再来一局」（双方同意）。它们不会同时出现 —— 判据是
  `room.awaitingNext` 与 `room.phase === 'ended'`，前者与后者互斥。
- 服务端多了一份 `rematchVotes` 状态，但它是纯传输层意愿（与 `ready` 同类），
  不进 `GameState`，也不影响 `stateHash`。
- 房间会长期存活（一直重开就一直不销毁），回放按局落盘 —— 这正是想要的：
  `replays/` 的粒度从「一间房一份」变成「一局一份」，与回放清理策略（7 天 / 500MB）
  的假设一致。

## ADR-0077 · 计时是服务端事实，必须单独推给客户端

- 日期：2026-10-22
- 状态：已采纳（D-310 / #155）

### 背景

`docs/16` 与 ADR-0017 都写着「任何被接受的操作都重新计时」，服务端也是这么做的
（`syncTimers()` → `timer.arm()`）。但客户端只从 `game:snapshot` 读 `turnDeadline`，
而「操作被接受」这条路径只广播 `room:state`。

于是出现一种**两边说法相反**的状态：服务端的截止时刻一路往后推，客户端手里的
那个数一路减到 0 并夹住 —— 玩家看到「计时 0s」以为超时了，实际还能照常操作（#155）。

### 决策

1. **新增轻量事件 `game:timer`，只带 `{ turnDeadline }`。**
   不扩 `room:state`（那是房间层事实，混进对局计时会让「房间视图」变成一个
   什么都装的袋子），也不扩 `game:events`（那个载荷是事件数组，语义是「发生了什么」，
   而截止时刻是「现在的状态」）。

2. **发送点固定在 `syncTimers()` 末尾，不在各个调用点。**
   `syncTimers` 就是「重新计时」这件事的唯一定义；放在这里，任何新增的
   重新计时入口都自动带上通知，不会再漏出一个「只在某个阶段不回弹」的变体。

3. **不为了这条信息广播 `game:snapshot`。**
   客户端把快照当**新起点**，收到就清空播放队列（`useRoom.ts` 的 `onSnapshot`）。
   每个操作发一份快照 = 每次操作都掐断动画，而逐条播放是 Era 明确要的
   （#158 也印证了这段播放节奏不能被破坏）。

### 后果

- 协议多一个只下行的只读事件，客户端多一行 `setTurnDeadline`。
- 断线重连仍然靠快照里的 `turnDeadline`（同一条信息，两个入口，语义一致）。
- E2E 多一条守卫（`e2e/timer.spec.ts`）：倒计时必须先真的在往下数，
  再做一次会被接受的操作，秒数必须变大。注入「不回传计时」后这条会红
  （`Expected: > 110 / Received: 109`）。
- 遗留：终局时不再重新计时，客户端可能停在最后读到的那个数上。
  结算覆盖层盖住顶栏区域，暂时无害；真正做「观战 / 回放时间轴」时再统一处理。

## ADR-0078 · 「在途」的结束点是播放队列排空，不是网络往返

- 日期：2026-10-22
- 状态：已采纳（D-312 / #158）

### 背景

点了「推进阶段」之后，按钮立刻回弹成可点，界面没有任何「我收到了」的迹象（#158）。
玩家看不到反馈，就会连点，而每次点击都是一条新 Intent（`seq` 递增，服务端照样受理）。

第一版直觉是「等服务器 ack 回来再恢复按钮」。但这在本架构里不成立：

1. `send()` 里的 `socket.emit` 没带 ack 回调，能等到的只有随后那条 `game:events`；
2. 即使等到 `game:events`，也**不等于玩家看见了结果** —— 事件先进播放队列，
   再按 `FX_MS` 逐条播（回合切换那一串能播一两秒）。

**慢的不是网络，是播放。** 以网络往返为终点，按钮会在动画播到一半时恢复，
玩家看到的是「按下去 → 灰一下 → 又能按 → 但界面还在演上一手」。

### 决策

1. **在途 = 本地播放队列非空。**
   `syncing` 在 `send()` 里置真，在 `pump()` 的 `finally` 里队列排空时置假。
   语义是「玩家眼睛追上了服务器」，而不是「数据包追上了服务器」。

2. **`game:events` 被拒（非 `accepted`）是第二个收尾点。**
   那条路径不产生事件，队列永远排不空 —— 不单独 `endSyncing()` 就会永久置灰。

3. **加 10 秒看门狗 `INTENT_WAIT_MS` 兜底，不作为正常路径的时长。**
   一条被吞掉的事件会让按钮永久置灰，玩家只能刷新页面。看门狗把「偶发卡死」
   降级为「等 10 秒」。

4. **只置灰会重发 Intent 的按钮**（推进阶段 / 结束回合 / 抽牌），
   不做全局锁：查看卡牌、打开浮窗、认输不产生 Intent，锁住只会让人以为界面卡了。

### 后果

- 按钮灰着的时长**比请求耗时长**，且随动画条数变化 —— 这是设计意图，不是 bug。
  若要缩短，该调的是 `FX_MS`，不是这里的判据。
- `syncing` 是纯客户端状态，不进协议、不影响 `stateHash`、不影响回放。
- 与 ADR-0077 的关系：0077 解决「服务端事实没送到客户端」，0078 解决
  「客户端已有事实、但玩家还没看见」。前者修数据一致性，后者修体感。
- E2E 守卫 `e2e/latency.spec.ts`：点完之后 3 秒内必须有「同步中」，
  且播完自动消失。注入「不发 `beginSyncing`」后红（`element(s) not found`）。
