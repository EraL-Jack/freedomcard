## ADR-0001 · 采用 pnpm monorepo + 前后端同构共享层

- 状态：已采纳
- 日期：2026-10-12
- 背景：规则逻辑必须在客户端与服务端行为一致（否则必然 desync），且后续要持续扩展规则。
- 决策：使用 pnpm workspaces，拆 `shared` / `core` / `server` / `client` 四个包；`core` 为纯 TS 纯函数包，前后端同构复用同一份规则代码。
- 理由：
  1. 规则只有一份实现，从根本上消除双端逻辑漂移。
  2. 包级依赖可视，违反分层（如 `core` 引 `server`）会在编译期报错。
  3. 单测只需跑一遍 `core`，成本最低。
- 被否方案：
  - 前端独立、后端独立各写一份规则 → 双份维护，必然不一致。
  - 单包大杂烩 → 无法阻止逻辑泄漏到组件里。
- 影响：所有跨包引用走包名（`@app/core`），禁止相对路径跨包。

## ADR-0002 · 采用服务器权威 + 客户端只发意图

- 状态：已采纳
- 日期：2026-10-12
- 背景：需要联网实时对战、弱客户端（网页，含移动端），且要防作弊、支持断线重连与回放。
- 决策：客户端只提交 `Intent`，服务端校验并执行规则、产出 `GameEvent[]` 并广播；客户端只做 `reduce` + 渲染。服务端每次广播附带 `serverSeq` 与 `stateHash`。
- 理由：
  1. 弱客户端不需要跑规则，省电省算力，移动端体验可控。
  2. 作弊面收敛到服务端；回放、观战、重连由同一事件流自然获得。
  3. `stateHash` 可实时发现双端分歧，把「隐性 bug」变成「可观测事件」。
- 被否方案：
  - 客户端权威（P2P 同步）→ 易作弊，移动端算力不一致导致分歧，无权威回放。
- 影响：
  - 客户端禁止本地结算；所有网络 payload 必须在 `shared` 定义并由 Zod 校验。
  - 客户端必须有 `desync` 上报通道。

## ADR-0003 · 事件溯源 + 纯函数规则 + 插件注册表（原子化基石）

- 状态：已采纳
- 日期：2026-10-12
- 背景：需求明确要求「各操作原子化构建、相互解耦，便于后续规则扩展」。
- 决策：
  1. 状态只能由 `reduce(state, event)` 演进，不可直接改写。
  2. 规则处理器固定签名 `(state, intent, ctx) => Result<GameEvent[], Rejection>`，纯函数，无 IO / 时间 / 随机副作用。
  3. 所有规则集中在注册表 `rules[type]`，一个机制一个文件；新增机制 = 新增文件 + 注册一行。
  4. 随机走种子 RNG，时间只取服务端事件时间戳。
- 理由：
  1. 纯函数可单测、可组合、可回放，是「解耦」的技术实现手段。
  2. 插件注册表满足开闭原则：扩展不修改既有代码。
  3. 确定性让「同种子同序列 ⇒ 同结果」成为可验证的断言，而非口头承诺。
- 判定标准：任何规则扩展若改动到既有规则文件的**内部实现**，视为架构违规，必须重构。
- 影响：新增卡牌 / 关键词 / 阶段 / 模式均按 `docs/02` 第 4.4 节流程执行。

## ADR-0004 · 交付件变更日志 + 测试报告 + 用户反馈报告三件套

- 状态：已采纳
- 日期：2026-10-12
- 背景：需求要求「已输出交付件的修改需输出日志」「Demo 测试需记录测试报告与用户反馈报告」。
- 决策：
  1. `logs/CHANGELOG.md` 为 append-only，条目含 11 个必填字段，覆盖全部交付件改动。
  2. 每轮 Demo 必须同时产出测试报告（客观）与用户反馈报告（主观），缺一不算闭环。
  3. 建立 `F → CHANGELOG → T → F` 的双向闭环链路，断链即视为本轮未闭环。
  4. 破坏性变更先写 ADR。
- 理由：
  1. 日志是决策轨迹，git 是精确差异，二者互补不可替代。
  2. 客观测试与主观反馈分离，避免「测试通过就等于好玩」的误判。
  3. 闭环链路保证每条反馈都有归属，不会被静默丢弃。
- 影响：见 `docs/03`、`docs/04`。

## ADR-0009 · 刷新技术栈版本线

- 状态：已采纳（Era 于 2026-10-12 拍板 TypeScript 5.9.3；其余按建议值）
- 日期：2026-10-12
- 背景：`docs/02` 原锁定 Node 20 / TS 5 / React 18 / Vite 5 / Tailwind 3。可行性论证（D-215）实测发现：Node 20 已于 **2026-04-30 EOL**（Node.js 官方发布页与 endoflife.ai）；Tailwind 4 已移除 `tailwind.config.js`，配置方式与 v3 完全不同；多个依赖只写包名未锁版本。按旧版本线搭骨架必然返工（R-01 / R-02 / R-03 / R-20）。
- 决策：版本线刷新为 —— Node `>=22.12.0`（推荐 24 LTS，Docker 用 `node:24`）、pnpm `12.11.2`、TypeScript `5.9.3`、React `^19.3`、Vite `^8.3`、Tailwind `^4.3` + `@tailwindcss/vite`、`socket.io` `^4.8`、`fastify` `^5.12`、Zod `^4.6`、Zustand `^5.0`、Immer `^11.1`、Vitest `^5.0`、Playwright `^1.64`。所有依赖必须锁版本，禁止只写包名；ESLint 用 flat config。
- 理由：
  1. Node 20 EOL 无可辩护；Vite 8 要求 Node ≥ 22.12，本机 22.22.2 与 24.14.0 均满足。
  2. Tailwind 4 的配置方式变更属「写法级」差异，按 v3 写必然重做样式层。
  3. TypeScript 选 5.9.3 而非 7.0.2：7.x 为原生编译器重写版，ESLint / Vitest 等周边兼容性未经本项目验证；Era 拍板选稳妥线。
  4. 未锁版本会导致不同时间安装得到不同结果，环境不可复现 —— 与「结论必须可复现」的要求直接冲突。
- 被否方案：
  - 沿用原版本线 → 骨架推倒重来，返工成本最高。
  - TypeScript 7.0.2 → 生态兼容性风险，Era 否决。
- 影响：`docs/01` §2、`docs/02` §2、`prompts/01` 第 0 条与第 7 条；`pnpm why` 输出一致性纳入脚手架验收。
- 备注：本 ADR 与文档修改同轮落地，但文档先于本记录写入，**未严格遵守「先 ADR 再动工」**；后续必须纠正顺序。

## ADR-0010 · 确定性架构三补（RNG 游标 / 幂等续接 / 规范化哈希）

- 状态：已采纳
- 日期：2026-10-12
- 背景：D-215 第 5 节论证出三处机制真空 —— RNG 游标与「规则函数纯」相互矛盾（R-06）、Intent `seq` 在重连后如何续接未定义（R-08）、状态哈希缺少规范化序列化约定（R-09）。三者分别会导致回放不可复现、「重连成功但操作全被丢弃」、假 desync 刷屏。
- 决策：
  1. **RNG 游标存于 `GameState.rngCursor`**：handler 从 `ctx.rng` 取值并把消耗写入事件，reducer 依据事件推进游标；禁止把 RNG 状态藏在闭包或模块变量里。
  2. **幂等续接**：服务端按 `playerId` 记录 `lastSeq`；重连时随快照下发，客户端从 `lastSeq + 1` 续发，禁止用本地计数归零重来。
  3. **规范化哈希**：状态哈希必须对规范化序列化结果计算（对象键排序、数组顺序固定、`undefined` 统一处理）。
- 理由：
  1. 把游标放进 state 并由 reducer 推进，是让「纯函数」与「可复现」同时成立的最小改动。
  2. `lastSeq` 下发能把一个极难自查的 bug 变成可断言的行为（已写入 `prompts/03` 验收：重连后连发 3 次操作须全部结算）。
  3. 规范化序列化把「假 desync」消除在源头，避免真问题被噪声淹没。
- 影响：`packages/core`、`packages/server` 快照结构、`docs/02` §4.3 与 §5、`docs/01` §5、`prompts/03`、`prompts/05`、测试报告模板。
- 备注：补记 —— 相关内容已于 v0.1.3-docs 先行写入文档，本 ADR 补齐决策留痕；后续须先写 ADR 再动工。

## ADR-0011 · 确定性架构再补（超时入事件流 / 幂等归属 / 回放粒度 / 并发前提）

- 状态：已采纳
- 日期：2026-10-12
- 背景：第二轮可行性论证（`docs/08`，D-217）在补做构建实测与架构深审后发现四处机制真空 —— 回合超时如何进入事件流（`R2-03`）、`(playerId, seq)` 幂等去重表的归属（`R2-04`）、`replay.json` 的记录粒度（`R2-14`）、单房间 Intent 处理链的并发前提（`R2-13`）。前两条若不定义，执行方只有两种写法可选，而**两种都会破坏既有架构约束**。

- 决策：

  1. **超时以「系统 Intent」进入事件流**。服务端会话层是唯一读时钟的地方；它发现超时后构造 `{ type: 'end_turn', actor: 'system', reason: 'timeout', playerId, seq }`，喂给与玩家完全相同的链路（`applyIntent → reduce → stateHash → 写 replay → 广播`）。禁止在 `core` 内读时钟，禁止会话层绕过引擎直接改 `GameState`。
  2. **幂等去重归 Room 会话层**，不进 `GameState`，也不由 `core` 实现。Room 持有 `Map<playerId, lastSeq>`。
  3. **回放粒度 = 种子 + Intent 序列（含系统 Intent）+ hashChain**，记为 `replays/<roomId>-<ts>.json`。
  4. **单房间 Intent 处理链禁止 `await`**：`applyIntent → reduce → stateHash → 写 replay → 广播` 必须同步完成；确有异步需求（持久化等）放在整条链之后。

- 理由：

  1. **超时三选，只有系统 Intent 不违规**：在 `core` 里读时钟 → 破坏纯函数，回放不可复现；会话层直接改状态 → 绕过引擎，`stateHash` 断裂，客户端 reduce 不出同一结果且极难定位；系统 Intent 则让引擎保持纯函数，事件流完整，回放天然包含超时事件。
  2. **提炼出一条普适判据，用于未来所有新增状态的归属判断**：
     > **凡影响游戏结果的外部状态，必须入 `GameState`；凡不影响结果、只保证传输可靠性的状态，一律不入。**
     >
     > RNG 游标决定洗牌结果 → 必须入 state（`ADR-0010` 结论正确）；seq 去重表不影响任何游戏结果 → 归会话层。据此判据，去重表若入 state 会让快照随回合线性膨胀并污染哈希；若由引擎外部持有则破坏 `applyIntent` 的纯函数性质 —— 两条路都不成立，只能放会话层。
  3. **记 Intent 而非 Event**：Intent 序列可重跑规则引擎，同时验证 handler 与 `reduce`；Event 序列只能验证 `reduce`，对超时等服务端生成的行为覆盖不足。系统 Intent 必须入列，否则回放缺步、终局哈希对不上。
  4. **并发属于「论证为低风险，但前提必须写死」**：Node 单线程下无 `await` 的处理链天然原子，两玩家同时出牌不会撞状态。但一旦有人插入异步（哪怕一个 `await redis.get()`），竞态会以「旧测试通过、高并发偶发」的形式出现，属于最难查的缺陷类型。把前提写明，比事后排查便宜得多。

- 影响：`prompts/02`（引擎不实现幂等、系统 Intent 同链路）、`prompts/03`（超时构造、去重归属、replay 定义、禁止 `await`）、`docs/02` §5、`prompts/05` 与测试模板（`M1-03` 幂等改在 Room 层验证、新增超时验证项）。
- 备注：本文档修改与本 ADR 落地于同一轮（v0.1.5-docs）。此为第三次出现「文档先于 ADR」的情况 —— 前两次为 `ADR-0009`、`ADR-0010`。三轮均为同一成因：论证发现缺陷后先改了明显的文档不一致，再补决策。**此顺序问题需在后续 `prompts/01` 执行时严格纠正：先 ADR，再动工。**

## ADR-0012 · 对局状态结构与区域模型

- 日期：2026-10-13
- 状态：已接受（前置：`docs/06` A 组输入 + Era 2026-10-13 澄清「无独立充能区」）
- 背景：

  A 组规则输入到位，`applyIntent` / `reduce` 从 `TODO(slot)` 转为可实现。但 `GameState` 此前只有一个 `rngCursor`（`shared/src/types.ts` 明令禁止在规则输入前出现业务字段），现在必须定稿状态结构 —— 这是**破坏性**的：结构一旦定，后续所有规则处理器、快照协议、客户端渲染都依赖它。

  定稿前唯一悬着的破坏性问题是 `docs/01` §1.3 第 1 条「充能区 ↔ 费用区是否同一区域」。Era 已确认：**没有独立的充能区，`docs/06` X-2 里的「充能区」就是费用区。**

- 决策：

  1. **区域建模为 `zones: Record<Zone, CardInstance[]>`**，8 个区域，与 `docs/06` B2 布局逐项对应：

     | Zone | 对应 B2 布局 | 说明 |
     | --- | --- | --- |
     | `deck` | 卡组区 | 有序，牌顶在数组首 |
     | `hand` | 手牌 | 无序 |
     | `commander` | 指挥官区 | X-1：第一个充能阶段揭示后直接置入，恒 0 或 1 张 |
     | `board` | 随从区 1·2·3 | 上限 `BOARD_SLOTS = 3` |
     | `spell` | 法术区 | 法术与持续法术的结算落点 |
     | `cost` | 费用区 | **三种来源共用一个区**（见下） |
     | `graveyard` | 弃牌区 | |
     | `exile` | 除外区 | |

     **不设 `charge` 区。** 增设一个 `charge` 区会让「同一张卡到底在哪个区」产生二义，且 Era 已明确否定。

  2. **费用区的完整语义**（本次澄清的直接产物）：

     - 来源①：**充能阶段**，把场上或手牌任意数量的随从置入费用区（X-2）
     - 来源②：**指挥官受伤时**，每 1 点伤害执行一次「从卡组顶展示 1 张（如有效果则触发），置入费用区」（A5 补充 1）
     - 消耗：支付 `cost` 时，把**相应数量的卡**从费用区送入弃牌区；数量不足则无法支付（A5 补充 2）

     即：费用区的卡**可能是随从、法术或任意卡**，它是「一堆可作为费用的卡」，不是某种特定牌。界面上只显示数量（B2-3 明确要求），点击可展开全貌。

  3. **卡牌定义与实例分离**：`CardDef`（静态卡池定义，含 `cost` / `power` / `damage` / `keywords`）与 `CardInstance`（场上的一张具体卡，含 `uid` + `defId`）分开。理由：同名卡 3 张上限是「定义」层面的约束，而休眠态、攻击次数等是「实例」层面的状态，混在一个对象里会让「同名 3 张」的校验与「这张卡本回合攻击过没」互相污染。

  4. **字段最小集，结构留扩展位**：字段只落 Era 已给的 `cost` / `power` / `damage`（`damage` 取值范围仍 `TODO(slot)`），另留 `keywords: string[]`（现仅 `'taunt'`）与 `attrs: Record<string, unknown>`。理由：`docs/06` A6-3 明确「可拓展，暂无输入」且 Era 说明会另行给字段清单 —— 届时只加字段、不改结构。

  5. **六阶段固定字面量**：`'charge' | 'reset' | 'draw' | 'main' | 'battle' | 'end'`，顺序即 `docs/06` A4-1 所给顺序，均不可跳过（A4-2）。阶段推进 = 状态机，不得由客户端指定目标阶段。

  6. **最高费用曲线常量化**：`MAX_COST_CURVE = [1, 3, 5, 10]`，按「第 n 回合」取 `min(n, 4)` 索引。写成一张表而非公式 —— Era 给的是离散值，写成公式就是替他发明规则。

  7. **`rngCursor` 保留在 `GameState` 根层**（ADR-0010），不随本 ADR 改变。

- 理由：

  1. **区域列表必须能逐项对上 B2 布局**，否则界面会出现「状态里有这个区但屏幕上没地方放」或反之。`docs/06` B2 列了 8 个区域名，本 ADR 就是那 8 个，一一对应，没有我自行添加的。
  2. **「充能区 = 费用区」这个澄清的价值在于它排除了一个错解**：若误建两个区，充能阶段放进去的随从就永远无法用于支付（或需要额外规则打通），资源循环直接断裂 —— 这是核心玩法，错了整个引擎要重写。故本条单独列为第 2 点并写清三种来源。
  3. **定义与实例分离**是为了让「卡组构成校验」（31 张、同名 3 张、指挥官 1 张）与「运行时状态」各管一段，前者改不影响后者。
  4. **曲线写成表**：离散值来自 Era，插值是我猜的，不猜。

- 影响：`shared/src/types.ts`（新增玩法类型）、`core/src/`（规则处理器按本结构实现）、`prompts/02` 与 `prompts/04` 的实现基准、`docs/02` §5 状态结构章节。
- 备注：本 ADR 是首个在**动工之前**写就的决策记录 —— 此前 `ADR-0009` / `0010` / `0011` 均为「先改文档后补 ADR」，该顺序问题在 `ADR-0011` 备注中已被点名，本条起纠正。
