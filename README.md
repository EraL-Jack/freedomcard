# ETCG · 卡牌对战游戏工作区

> 游戏名 **ETCG**（代称，Era 2026-10-21 定），副标题「混合风格 · 什么样的卡组都有」。
> 本工作区以「提示词驱动」的方式产出：网页端（弱客户端）、PC 与移动端自适应、
> 支持建房与实时联机对战，并带一个用于自测的人机局。

## 1. 目录约定

| 目录 | 用途 |
| --- | --- |
| `docs/` | 主提示词、技术栈与架构规范、日志与报告规范、待输入清单 |
| `prompts/` | 可分阶段直接执行的提示词（01 → 05，按序） |
| `logs/` | 交付件变更日志（append-only）、架构决策记录 ADR |
| `reports/test/` | Demo 测试报告（T-xxxx） |
| `reports/feedback/` | 用户反馈报告（F-xxxx） |
| `app/` | 代码产物（由提示词执行后生成，当前尚未创建） |

## 2. 标准工作流

1. 读 `docs/06-规则与界面输入表.md`（**填写入口**，槽位值唯一来源；`docs/05` 作总表与状态视图），确认「游戏规则 / 界面」输入已就绪。未就绪，只允许搭骨架，不允许臆造规则。
2. 按 `prompts/01 → 05` 顺序执行，每一步都可独立验收。开工前建议先读 `docs/07`（一轮）与 `docs/08`（二轮）可行性论证 —— 里面有必看的环境坑。
3. 任何交付件的新增 / 修改 → 追加 `logs/CHANGELOG.md`，并带交付件 ID（D-xxx）。
4. 任何规则或架构层面的选择 → 写入 `logs/DECISIONS.md`（ADR-xxxx），**先写 ADR，再动工**（此顺序已被违反三次，见 ADR-0009/0010/0011 备注，不得再犯）。
5. 每轮 Demo 产出 → 一份测试报告（T-xxxx）+ 一份用户反馈报告（F-xxxx），二者与 CHANGELOG 双向关联。
6. 提问方式：一次只问一个问题，等反馈后再继续。

## 3. 三条硬约束

- **原子化**：任一游戏操作 = 一个可序列化的 `Intent`；规则 = 纯函数；要么整体生效，要么整体拒绝。
- **解耦**：`core`（规则）/ `net`（传输）/ `view`（渲染）三层零交叉；新增规则 = 新增插件文件，不修改既有代码。
- **可追溯**：交付件改动必有日志；Demo 迭代必有测试报告与反馈报告；破坏性变更必有 ADR。
