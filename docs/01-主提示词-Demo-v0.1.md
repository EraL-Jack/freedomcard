### 1.1 槽位值（2026-10-13 由 Era 填写，转录自 `docs/06`，未作推断补充）

**`{{PLAYER_COUNT}}`** — 2 人，双方对战；不组队；允许旁观位；先后手由掷骰决定（1d6，较大者先攻）。

**`{{WIN_CONDITION}}`** — 血空判负，无附加判负条件；理论不存在平局；可随时认输；掉线等待 30s，由另一方决定是否直接获胜。

**`{{TURN_FLOW}}`** — 六阶段：**充能 → 重置 → 抽牌 → 主要 → 战斗 → 结束**，均不可跳过；**可在对手回合行动**（响应 / 打断）。回合时限未指定 → `TODO(slot)`。
Era 补充（自定义条目）：
1. 指挥官在**第一个充能阶段**揭示，直接置入指挥官区；
2. 充能阶段可将**场上或手牌任意数量**的随从置入**充能区**；
3. 重置阶段重置「一切每回合一次的效果」与「每个单位的攻击次数」。

**`{{RESOURCE_SYSTEM}}`** — 资源为「费用」与「最高费用」两条：最高费用初始 1，增长序列 **1 → 3 → 5 → 10**（第 4 回合达到上限）。资源可累积、可被破坏；生命上限不可成长。

> **区域澄清（2026-10-13 Era 确认）**：本表**不存在独立的「充能区」**。`docs/06` 自定义条目 X-2 所说的「充能阶段将随从置入**充能区**」，其中的「充能区」**就是费用区** —— 两个名字指同一个区域。实现时只建一个 `cost` 区，不得另设 `charge` 区。

Era 补充：
1. 指挥官受到伤害时，**每 1 点伤害**执行一次「从卡组最上方展示 1 张卡（如有效果则触发对应效果），然后将该卡置入**费用区**」；
2. 支付费用时，将**足够数量的卡**从费用区置入弃牌区；数量不足则无法支付；
3. 充能阶段可将**场上或手牌任意数量**的随从置入费用区（即同一区域）。

由此得到费用区的三种来源：**充能阶段主动放入的随从**、**指挥官受伤时从卡组顶展示的卡**；消耗方式是**按 `cost` 数值取相应数量的卡送入弃牌区**。

**`{{CARD_SET}}`** — 卡类型：**指挥官（有且仅有 1 张）、随从、法术、设置法术**（后三者张数不限）。有衍生物。卡组 **31 张 = 主卡组 30 张 + 指挥官 1 张**，同名上限 3 张，指挥官必须有且仅有 1 张。

> **卡组 31 张的构成已确认（2026-10-13，Era 原话「30+1，主卡组30张+1个指挥官」）**：A6-5 的「31 张」是**含指挥官的总数**，A10-4 的「30 张」是**主卡组（牌库）张数**，二者不矛盾。
> 校验规则据此定为：`主卡组 = 30 张`（随从 / 法术 / 设置法术，同名 ≤ 3）+ `指挥官 = 1 张`，合计 31。指挥官开局直接置于指挥官区，**不进主卡组、不参与洗牌与抽牌**。

**战斗裁决**（`docs/06` X-3，Era 2026-10-13 补充，落地见 ADR-0013）— **只对比力量值**：

- 攻击方力量值 **大于** 被攻击方 → **被攻击方**破坏
- 攻击方力量值 **小于** 被攻击方 → **攻击方自己**破坏
- 两者 **相等** → **双方**破坏

由此确定：**本作不存在「生命值」概念**（随从只有力量值）。

> **区域命名别名（ADR-0015）**：Era 的输入里同一个区域有三个名字 —— **费用区**（A5 补充 / B2 布局）、**充能区**（X-2）、**伤害区**（卡牌样例卡面）。**三者同一，均为 `cost`**。别名只留在文档与注释，不进代码标识符。同理「弃牌区」= `graveyard`（Era 2026-10-19 更正：统一称「弃牌区」，不再使用旧称）。

**指挥官伤害与胜负**（`docs/06` X-4，Era 2026-10-13 补充，落地见 ADR-0014）— 对指挥官造成伤害 → 扣除**对应伤害值**的血量 → **血量清空，游戏结束**。由此确定**指挥官不走「破坏」路径**，与 A3-1「唯一判负是血空」一致：

- 打**随从** → 力量值对比 → 输的一方破坏，**双方血量都不变**
- 打**指挥官** → 力量值对比；防守方输则**掉血**（血空则游戏结束），攻击方输则**自己破坏、指挥官不掉血**
- 伤害值取攻击方卡定义的 `damage` 字段；**卡上未写伤害值时，伤害值默认为 1**（`docs/06` X-5，与 `power` 无关）

攻击时与被攻击时**都可能有触发的效果**：触发点已固定为「声明 → 攻击时 → 被攻击时 → 快照力量值 → 裁决」，本批不执行任何效果（A7 效果清单未给），仅产出事件供后续效果系统与动画挂载。

**指挥官力量值曲线**（`docs/06` X-7，Era 2026-10-13 原话：「是初始0然后每个充能阶段成长，第一回合就会变到1」）— `powerCurve` 是**档位序列**，不是「回合号 → 力量值」的映射表：

| 时点 | 档位 | 力量值 |
| --- | --- | --- |
| 开局（揭示指挥官时） | 0 | 0 |
| 第 1 回合充能阶段后 | 1 | 1 |
| 第 2 回合充能阶段后 | 2 | 3 |
| 第 3 回合充能阶段后 | 3 | 5 |
| 第 4 回合及以后 | 3（封顶） | 5 |

- 推进点是**己方**的充能阶段；对手回合不影响我方指挥官。开局时只推进**先攻方**一次（后攻方的第一次成长在它自己的第一回合）。
- 走到末档后保持末档，**不循环、不报错**，且不再产出成长事件。
- 未定义 `powerCurve` 的指挥官**不成长**，力量恒取 `CardDef.power`。
- 战斗裁决读的是指挥官**当前档位**的力量值（ADR-0016 §8）。

**`{{RANDOMNESS}}`** — 洗牌时一次全随机。起手 5 张，可换：选任意数量返回卡组底 → 从卡组顶抽满 5 张 → 再洗牌（确保不会换到返回去的牌）。每回合抽牌阶段抽 2 张。每当需要抽牌 / 展示卡牌而卡组已用尽时，将弃牌区所有卡洗牌放回卡组区，再执行对应动作。先攻方第一回合仅抽 1 张且不可攻击。可复现性按 §3.6 架构默认（服务端种子 RNG）。

**`{{DEPLOY_ENV}}`** — 本机 / 局域网先跑通并联机测试；`docker-compose.yml` 照写留作云部署（**本机未验证**，报告须标注）；先在局域网开放测试，暂无域名与证书。

## 2. 技术栈（已锁定）

## 3. 架构约束（原子化 + 解耦，强制）

1. **单入口意图**：任何点击 / 拖拽 / 快捷键只能产生一个 `Intent`，不得直接改状态。
2. **服务器权威**：客户端只发 `Intent`；服务端校验后生成 `GameEvent[]` 并广播；客户端只做 `reduce` + 渲染。
3. **原子性**：一次 `Intent` 的规则处理整体成功或整体失败；失败返回 `Rejection{code, message}`，不产生任何副作用。
4. **纯函数规则**：处理器签名固定 `(state, intent, ctx) => Result<GameEvent[], Rejection>`；禁止 IO / 时间 / 随机 / DOM。
5. **插件化注册**：规则集中于注册表 `rules[type]`；新增卡牌或机制 = 新增文件 + 注册一行，**不得修改既有规则文件**。
6. **确定性**：随机数走种子 RNG（种子由服务端开局下发）；时间只取事件时间戳。相同种子 + 相同 Intent 序列 ⇒ 终局状态完全一致。
7. **不可变状态 + 事件溯源**：`GameState` 只能由 `reduce(state, event)` 演进；全量事件序列可回放。
8. **幂等**：每个 Intent 带 `seq`，重复 seq 直接丢弃，保证弱网重发不双结算。
9. **可观测**：每局落一份 `replay.json`（种子 + Intent 序列 + 状态哈希链）。
10. **分层纪律**：`core` 不得 import `net` / `view`；`view` 不得依赖 `core` 内部实现，只依赖类型与事件。

## 4. 交互与界面要求

- 关键操作必须**单指可完成**：点选卡牌 → 点选目标 → 确认；必须有「取消」与「撤销未确认操作」。
- **撤销的边界**：撤销只作用于**尚未 emit 的 UI 选中态**（已选卡牌、已选目标）；Intent 一旦 emit，客户端不得本地回滚，状态只能由服务端广播的事件演进。
- 拖拽是增强，不做唯一入口；桌面 hover 态在触屏用长按替代。
- 必须有：加载态、操作中态、非法操作反馈、断线提示与重连进度。
- 响应式：375×667 / 768 / 1440 三档均无横向滚动、无元素遮挡、无点击热区小于 44×44px。
- 动效 120–250ms，不阻塞输入；遵循 `prefers-reduced-motion` 提供「减少动效」开关。

## 5. 联机要求

- **大厅**：创建房间（生成 4–6 位房间码）/ 输入房间码加入 / 房间列表（可选）。
- **房间**：准备、开始、房主踢人、断线保留席位 **60s（`RECONNECT_GRACE`）** 可重连；回合无操作超时 **30s（`TURN_TIMEOUT`）** 由服务端自动结束回合。两个常量命名固定，禁止混用。
- **实时**：同城操作广播延迟目标 < 150ms；对手操作即时可见。
- **一致性**：每个事件后服务端计算状态哈希随广播下发，客户端比对，不一致即告警并记入测试报告。
- **弱客户端**：首屏 JS ≤ 1.5MB(gzip)；低端机降级到 30fps 仍可完整操作。

- 禁止在规则函数中使用 `Date.now()` / `Math.random()`。
- 禁止为赶进度把多层逻辑塞进单个文件。
- 禁止在未确认规则槽位的情况下自行「补齐」玩法。
