# 测试与反馈报告规范

Demo 每完成一轮迭代，必须同时产出**两份报告**：
- 测试报告 `reports/test/T-xxxx-*.md` —— 客观：跑没跑通、数据怎样。
- 用户反馈报告 `reports/feedback/F-xxxx-*.md` —— 主观：你（用户）用起来什么感觉。

两者缺一，本轮迭代不算闭环。模板文件位于 `reports/test/T-模板-测试报告.md` 与 `reports/feedback/F-模板-用户反馈报告.md`。

---

## 1. 测试报告（T-xxxx）

### 1.1 必填字段

| 字段 | 说明 |
| --- | --- |
| 报告编号 | `T-0001` |
| 测试对象 | 版本号 + 对应交付件 ID（如 v0.1 / D-101~D-104） |
| 测试时间 / 执行人 | 时间 + 执行方 |
| 环境矩阵 | 设备、系统、浏览器版本、网络条件、服务端地址 |
| 用例矩阵 | 用例 ID、名称、步骤、期望、实际、判定 |
| 通过率 | 通过 / 总数，以及分模块通过率 |
| 缺陷清单 | 编号、等级、复现步骤、期望 vs 实际、状态 |
| 性能数据 | 见 1.3 |
| 结论 | 可发布 / 有条件发布（列条件）/ 阻塞（列阻塞项） |

### 1.2 必测模块（不得缺项）

| 模块 | 关键验证点 |
| --- | --- |
| M1 规则引擎 | 单测覆盖核心路径（`packages/core/src/rules/**`），覆盖率 ≥ 80%；同种子同序列结果一致 |
| M2 房间流程 | 建房 / 加入 / 准备 / 开局 / 房主踢人 |
| M3 实时同步 | 双端状态哈希一致；乱序与重发 Intent 被幂等丢弃 |
| M4 断线重连 | 断网 60s 内（`RECONNECT_GRACE`）重连，席位与状态完全恢复；超出 60s 应判负或释放席位 |
| M5 响应式 | 375×667 / 768 / 1440 三档无溢出、无遮挡、点击热区 ≥ 44px |
| M6 弱网 | 延迟 200ms / 500ms 下可完整打完一局（**丢包需额外工具**，DevTools 与 Playwright 只能模拟延迟与带宽；若无工具则降级为仅延迟档，并在报告中写明） |
| M7 弱客户端性能 | 首屏 JS 体积、可交互时间、操作到本地反馈延迟 |
| M8 回放一致性 | 用 `replay.json` 重放，终局状态哈希与原始一致 |

### 1.3 性能数据（必须带具体数值）

| 指标 | 目标 | 实测 | 判定 |
| --- | --- | --- | --- |
| 首屏 JS（gzip） | ≤ 1.5MB | | |
| 首屏可交互 | ≤ 2.5s | | |
| 操作→本地反馈 | ≤ 100ms | | |
| 操作→对手可见 | ≤ 150ms | | |
| 帧率（低端机） | ≥ 30fps | | |
| 双端同步偏差 | 0 次 desync | | |

### 1.4 缺陷等级

| 等级 | 定义 | 处置 |
| --- | --- | --- |
| P0 | 无法完成对局 / 状态分歧 / 数据不一致 | 阻塞发布，立即修 |
| P1 | 核心流程可用但有明显错误（规则算错、重连丢状态） | 发布前必修 |
| P2 | 影响体验但不阻塞（布局错位、动效缺失） | 可排期 |
| P3 | 建议优化（文案、视觉细节） | 记入待办 |

### 1.5 结论书写要求

- 必须明确给出三选一：**可发布** / **有条件发布**（逐条列出条件） / **阻塞**（列出 P0/P1 与预计修复动作）。
- 禁止出现「基本没问题」「大体可用」这类模糊结论。

## 2. 用户反馈报告（F-xxxx）

### 2.1 必填字段

| 字段 | 说明 |
| --- | --- |
| 报告编号 | `F-0001` |
| 对应版本 | 如 v0.1 |
| 反馈人 | 你（用户） |
| 体验目标 | 本轮想验证什么（如「联机流程是否顺畅」） |
| 场景与步骤 | 你实际做了什么，越具体越好 |
| 原始反馈 | **原话照录**，不要转述、不要润色 |
| 归类 | Bug / 手感 / 数值平衡 / 界面 / 联机 / 性能 / 缺失功能 |
| 严重度 | 阻断 / 难受 / 轻微 / 建议 |
| 期望行为 | 你希望它变成什么样 |
| 处置 | 立即修 / 排期（版本号）/ 不做（写清理由） |
| 结论 | 本轮是否达到体验目标 |

### 2.2 记录原则

1. **原始反馈优先**：先抄录你的原话，再做归类与转译。前者是证据，后者是分析。
2. **一条反馈一条记录**，不要合并不同维度的问题。
3. **处置必须有归属**：任何「不做」都必须写理由和替代方案，禁止静默丢弃。
4. **闭环**：处置为「立即修 / 排期」的条目，必须在后续 `logs/CHANGELOG.md` 中能找到对应修复记录，并在下一份反馈报告中标注「已解决 / 未解决 / 部分解决」。

### 2.3 两报告的双向关联

```
F-0001（你反馈 X 手感差）
   ↓ 处置：立即修
CHANGELOG 条目（D-104 修改，关联 F-0001）
   ↓
T-0002（新增/回归用例，关联 F-0001）
   ↓
F-0002（标注 X 已解决）
```

任何一个环节断链，本轮迭代即视为未闭环。
