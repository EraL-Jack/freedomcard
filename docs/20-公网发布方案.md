# 20 - 公网发布方案（需要什么、各自代价）

> 状态：待 Era 选定路线（X-16）。本文只给方案与前置清单，不做任何线上变更。
> 日期：2026-10-20

## 0. 一句话结论

这个项目**不是静态页面**，是「常驻 Node 进程 + WebSocket + 内存房间状态」的单端口服务。
所以能选的只有「能跑常驻进程」的几种载体；推荐 **B 香港轻量服务器（免备案，35~55 元/月）**，
先用 IP 直连跑通，需要 HTTPS 时再挂域名。

---

## 1. 四条硬约束（先划掉不合适的平台）

| # | 约束 | 来源 | 后果 |
|---|---|---|---|
| C1 | 必须是**常驻进程** | `packages/server` 用 Fastify + Socket.IO 长驻 | Vercel / Netlify / Cloudflare Workers 的 Serverless 免费层**不能**用（函数会被回收，房间内存随之消失） |
| C2 | 需要 **WebSocket 长连接** | `socket.io`，全量事件推送 | 任何只支持 HTTP 请求-响应的静态托管都不行（GitHub Pages / OSS / COS 静态站） |
| C3 | **单端口同源**：页面 + `/socket.io` | `SERVE_STATIC=1` + `@fastify/static` 托管 `packages/client/dist` | 部署时**必须先构建客户端**，否则线上只有一个 404 的壳；反代必须透传 `Upgrade` |
| C4 | 房间状态在**内存**、回放写**本地磁盘** | `room.ts` 的 `Map`；`replays/<roomId>-<ts>.json` | 进程重启 = 所有房间消失；容器重建 = 回放文件消失。要长期保留就得挂卷 |

> C4 是「试玩」和「运营」的分水岭。给朋友玩两周，内存态完全够；要长期挂着给人随时来，得考虑持久化。

## 2. 五个方案对照

| 方案 | 需要你提供什么 | 钱 | 大陆访问 | 备案 | 你的电脑要开吗 | 状态能不能留 |
|---|---|---|---|---|---|---|
| **A 内置发布通道** | 无（我直接打包上传） | 0 | 一般（境外节点，延迟高、可能被墙） | 不用 | 不用 | ❌ 重启即失 |
| **B 香港轻量服务器** | 云账号（已实名）+ 一台轻量 | 35~55 元/月 | 好，30~50ms | **不用** | 不用 | ✅ 磁盘持久 |
| **C 内地云主机** | 云账号 + **域名** + **ICP 备案** | 68 元/年起（新人价） | 最好，5~20ms | **必须，7~20 天** | 不用 | ✅ |
| **D 内网穿透** | 你的电脑常开 + 穿透服务 | 0 或几十元/月 | 看穿透商（见 §4） | 不用 | **要，全程开着** | ✅ 本机磁盘 |
| **E 容器托管平台**（Railway / Render / Fly.io） | 账号 + 信用卡 | 免费层或 $5/月起 | 不稳（境外） | 不用 | 不用 | ⚠️ 免费层会休眠 |

### 判定标准（怎么选）

1. **只是让朋友今天进来玩两局** → A，最省事，坏了随时下线重发。
2. **想让人随时点开就能玩、不用管电脑开没开** → B，这是唯一「花钱少 + 免备案 + 大陆不卡」的组合。
3. **要正式对外、要域名和 HTTPS、要长期** → C，代价是备案时间。
4. **一分钱不想花、电脑能一直开** → D，但要接受断电即下线。

## 3. 各方案的前置清单

### A. 内置发布通道（零成本，先验证）

- **需要**：什么都不用给。
- **我会做的**：上传源码 → 沙箱内 `pnpm install` → 构建客户端 → `SERVE_STATIC=1` 启动 → 返回分享链接。
- **限制**（必须提前知道）：
  - 沙箱在境外，大陆访问延迟高、不保证稳定；
  - 进程可能被回收，房间中途消失；
  - `replays/` 是临时盘，重启清空。
- **适合**：验收玩法、给几个朋友试一局。不适合当「正式服」。

### B. 香港轻量服务器（推荐长期）

- **需要你提供**：
  1. 一个云账号（腾讯云 / 阿里云，均已实名）；
  2. 买一台**中国香港地域**轻量应用服务器，2 核 2G 起步，Linux；
  3. 服务器公网 IP + SSH 登录方式（密码或密钥）—— 后续所有操作我来做。
- **不需要**：域名、备案、证书。
- **参考价**（2026-10 量级，以下单页为准）：腾讯云香港 2 核 2G 入门型 35~40 元/月、锐驰型 2 核 2G 约 55 元/月；阿里云香港 2 核 2G 新用户 24 元/月起。**面向大陆用户优先选「锐驰型/高带宽」**，入门型的跨境质量不保证。
- **访问形态**：`http://<公网IP>:3000` 直接可用。HTTP 页面连 `ws://` 同源 WebSocket 是允许的（只有 HTTPS 页面才禁止连 `ws://`）。所以**没有域名也能完整联机**。
- **要做的事**：装 Node 22 → 传代码 → 构建 → 进程守护（`pm2` 或 systemd）→ 开安全组端口。
- **后续升级到 HTTPS**：买域名（10~60 元/年）→ Cloudflare 免费证书或 Let's Encrypt → Nginx 反代，务必透传 `Upgrade` / `Connection`。

### C. 内地云主机（最正规，但要备案）

- **需要你提供**：
  1. 云账号 + 内地地域服务器（上海/广州/北京）；
  2. **一个已实名域名**；
  3. **ICP 备案**：身份证、手机号、人脸核验，通常 7~20 天，备案期间域名不可对外提供服务；
  4. 备案通过后服务器才能绑域名开 80/443。
- **钱**：服务器 68 元/年起（新人）、域名 10~60 元/年。
- **代价**：备案是国内独有的时间成本；且个人备案的站点内容受用途限制。
- **适合**：真的要长期对外、要一个正式网址。

### D. 内网穿透（你上次走的路）

- **需要你提供**：家里电脑保持开机 + 不断网。
- **三条子路线**：
  | 子路线 | 需要 | 大陆可达性 | 坑 |
  |---|---|---|---|
  | `cloudflared` 快速隧道 | 无（免注册） | **差**：`*.trycloudflare.com` 在国内经常 DNS 解析不到 | 地址每次重启都变；有实测证据链显示解析全空、边缘报 1016 |
  | `cloudflared` 具名隧道 | **自有域名** + 托管到 Cloudflare | 好 | 必须先有域名；否则无从验证 |
  | 花生壳 / 贝锐 | 账号 + 实名 | 好（国内服务） | 免费版带宽/流量受限，HTTPS 常要付费版 |
  | 自建 `frp` | **一台有公网 IP 的服务器** | 好 | 等于又回到方案 B，只是多一层 |
- **额外坑**：`cloudflared` 默认走 QUIC（UDP），国内 UDP 常被 QoS，需强制 `--protocol http2`。

#### SakuraFrp 隧道类型怎么选（据官方文档 `doc.natfrp.com/app/http.html`）

| 隧道类型 | 是否需要自有域名 | 内地节点可用性 | 访问形式 |
|---|---|---|---|
| `HTTP(S)` | **必须**绑定自己的域名 | 内地节点要求域名**已备案** | `http(s)://my.example.com` |
| `TCP` | 不需要 | 可用，但**应用协议是 HTTP 时必须用非内地节点** | `http(s)://<节点域名>:<远程端口>` |

结论（本项目无域名、无备案）：

- **只能选 `TCP` 隧道**；`HTTP(S)` 隧道必须有自有域名，内地节点还叠加备案要求。
- **必须选非内地节点**（香港/日本/新加坡/美国等）。本项目是 HTTP 应用，
  用内地节点 + TCP 属于文档明示的违规组合，表现就是「隧道显示已连接但外网打不开」。
- **本地 IP 必须填 `127.0.0.1`，不能填 `localhost`**。Windows 的 OpenSSH / 部分客户端
  会把 `localhost` 优先解析到 IPv6 `::1`，而服务只监听 IPv4 `0.0.0.0` —— 隧道进程显示连上，
  但转发目标不可达，外网就是 502。本机实测：`localhost` → 502「no tunnel」，`127.0.0.1` → 200。
- 隧道启动时控制台会输出 `节点域名:远程端口`，这个地址就是访问入口；
  也可在「隧道列表」页查看节点域名。
- 想让外部走 HTTPS 而本地是 HTTP，可给 TCP 隧道打开**自动 HTTPS** 开关，无需本地支持 TLS。
- **启动器自带的那份 `frpc.exe` 不能用于命令行启动**。它是定制版（2023 年版为 `0.51.0-sakura-2`），
  带 `-f <密钥>:<隧道ID>` 运行只会打印 banner 后**静默退出**（`exit 0`，无错误、不连接），
  也不认 `--log_level`。必须下载独立版：

  ```
  https://nya.globalslb.net/natfrp/client/frpc/<版本>/frpc_windows_amd64.exe
  ```

  版本目录可列 `https://nya.globalslb.net/natfrp/client/frpc/`。实测 **`0.51.0-sakura-15`** 可用；
  启动成功会输出 `使用 >>host:port<< 连接你的隧道`。

### E. 容器托管平台（备选）

- **需要**：账号 + 信用卡；仓库能构建（本项目已有 `Dockerfile`，但**未在本机验证过**）。
- **代价**：免费层会休眠（第一次打开要等十几秒），且大陆访问不稳。
- **结论**：不如 B。仅当你不想要「自己管一台服务器」时考虑。

## 4. 你上次 HTTP 穿透「访问不了」——五类原因与判别

按发生概率排序，每种都有明确判据：

| # | 原因 | 判别方法 | 解法 |
|---|---|---|---|
| 1 | **临时域名解析不到**（`trycloudflare` 高发） | `nslookup xxx.trycloudflare.com` 返回「不存在」 | 换具名隧道（需域名），或换国内穿透商 |
| 2 | **家宽 80/443 入站被封** | `curl -I http://<IP>` 连接重置 / 超时；换非标端口（如 3000）就通 | 一律用非标端口，或走隧道（隧道不需要开端口） |
| 3 | **WebSocket 未透传** | 页面能打开、能建房，但操作要等 1~2 秒才有反应（降级成轮询），或直接 400 | 反代加 `Upgrade` / `Connection: upgrade` |
| 4 | **HTTPS 页连 `ws://` 被拦** | 浏览器控制台报 `Mixed Content` | 页面与 Socket 协议保持一致（https → wss），或整站走 HTTP |
| 5 | **穿透服务限流 / 需实名** | 打开一段时间后 502 / 提示额度用尽 | 换付费版或换方案 |

> 这五条在方案 B 里只可能碰到第 3 条（如果你加 Nginx），其余天然不存在。

## 7. 公网暴露面检查（本机实测，2026-10-20）

真正挂到公网前必须确认的几项。下表是**生产形态（`SERVE_STATIC=1`，3100）实测结果**，
不是推断。

| 检查项 | 实测 / 现状 | 判定 |
| --- | --- | --- |
| 目录穿越 `/../../package.json` | `403 Forbidden`（`@fastify/static` 拦下） | ✅ |
| 编码穿越 `/%2e%2e/%2e%2e/package.json` | `403 Forbidden` | ✅ |
| 斜杠编码 `/..%2f..%2fpackage.json` | 200，但返回的是 `index.html`（SPA 回退），非文件内容 | ✅ 无泄露 |
| 静态根目录 | 只挂 `packages/client/dist`，不含源码与配置 | ✅ |
| 房间回收 | `prune()` 每 30s 扫描：断线超 `RECONNECT_GRACE=60s` 释放席位，空房立即销毁 | ✅ 有单测 |
| 房间码空间 | 6 位 × 32 字符 ≈ 10.7 亿，生成时冲突重试 | ✅ 空间够 |
| 房间码随机源 | 已换 `crypto.randomInt` + 32 字符表（去掉 `0/O/1/I`，口头报码不易听错） | ✅ 已加固（D-178） |
| 鉴权 | 无账号；房间码即凭证，玩家 token 存 `localStorage` | ⚠️ 试玩可接受 |
| 速率限制 | 已落地：按**连接**（建房 10/分、加入 20/分、Intent 20/秒）+ **全局**（房间 2000、连接 5000）—— 穿透下所有客户端都是 `127.0.0.1`，按 IP 限流没意义 | ✅ 已加固（D-182 / ADR-0039） |
| 回放磁盘 | 每间房落一个 JSON 到 `app/replays/`；保留 **7 天 / 500 MB**，启动 + 每 24 小时清一次（最近 1 小时的绝不删）。实测 8 天累积 **903 个文件 / 12.7 MB**（约 113 份/天） | ✅ 已落地（D-182 / ADR-0040） |
| 回放**观看**入口 | 结算面板「查看回放」按钮置灰；服务端没有任何读回放的 HTTP 路由，静态根也不含 `app/replays/` —— 公网取不到文件 | ✅ 按 Era 流量约束关闭（D-183 / ADR-0041） |
| 回放落盘失败 | `void flushReplay(...)` 原先**没有 catch** —— 磁盘满或目录只读时，Node 22 会因 unhandled rejection **终止进程** | ✅ 已修（D-176） |
| `/health` | 返回 `{ ok, version }` | 低风险 |

### 结论与建议

- **可以直接对外试玩**：没有文件泄露。
- **内存此前有界这一条曾被写错**：2026-10-20 实测发现「一条连接建多间房」会让旧房间永不释放
  （`prune` 只回收 `connected:false` 的席位），已在 **D-181** 修掉。现在「一连接一席位」，
  但**连接数与房间总数仍无上限**，见 §8.2。
- 上面两条 ⚠️ 已按「先回放清理、再限流」的顺序处理完（都在 D-182，见 §8）：
  回放保留 7 天 / 500 MB；限流按**连接**与**全局**，**不按 IP** —— 穿透部署下所有客户端都是
  `127.0.0.1`（§8.2）。剩下唯一的 ⚠️ 是**没有账号体系**：房间码即凭证。
- 房间码已被猜中的后果是「有人随机进到你房间」，不是数据泄露 —— 因为房间里没有敏感数据。
  随机源已换密码学安全实现（D-178），剩下能枚举的只是 10.7 亿分之一。

## 8. 两个运维项：X-20 回放保留 与 速率限制

这两项不是「有没有 bug」，而是「要不要设上限、上限是多少」。Era 2026-10-20 确认按推荐值落地，
**实现见 D-182**（`server/src/room/replay-maintenance.ts`、`server/src/room/rate-limit.ts`）。
本节保留完整推演过程与实测数据 —— 阈值将来要调整时，判断依据都在这里。

### 8.0 已落地的默认值与调参口

| 项 | 默认值 | 环境变量 | 说明 |
| --- | --- | --- | --- |
| 回放保留期 | **7 天** | `REPLAY_KEEP_DAYS` | 早于此的才可能被删 |
| 回放目录上限 | **500 MB** | `REPLAY_MAX_MB` | 超出后继续从最旧的删 |
| 清理时机 | **启动扫一次 + 每 24 小时** | — | 启动那次也受下面两条约束 |
| 清理只算不删 | 关 | `REPLAY_SWEEP_DRY_RUN=1` | 调整阈值时先看报告 |
| 建房 | **10 次/分钟 · 每连接** | `RL_CREATE_PER_MIN` | |
| 加入 | **20 次/分钟 · 每连接** | `RL_JOIN_PER_MIN` | 比建房宽：输错房码重试是正常行为 |
| Intent | **20 次/秒 · 每连接** | `RL_INTENT_PER_SEC` | 真人点击上限约 5 次/秒 |
| 全局房间数 | **2000** | `RL_MAX_ROOMS` | 达到后建房回「房间数已达上限」 |
| 全局连接数 | **5000** | `RL_MAX_CONNECTIONS` | 超出直接断开新连接 |

两条硬性保护（写死在代码里，不可配）：

- **清理永不碰最近 1 小时内写过的文件** —— 清理与落盘都是异步的，删到正在写的那份就是静默丢数据；
- **被限流的 Intent 不进回放** —— 它没有产生任何状态变化，记进去会让记录与实际不符。

### 8.1 X-20：回放文件保留策略

**机制**：每个房间销毁时（空房 / 全员断线超 60s）落一份 JSON 到 `app/replays/`，**没有任何删除逻辑**。

**实测（2026-10-20）**：

| 指标 | 数值 |
| --- | --- |
| 文件数 | **903 份** |
| 总占用 | **12.7 MB**（磁盘显示 15 MB，含簇对齐） |
| 时间跨度 | 2026-10-13 ~ 10-20，**8 天** |
| 平均 / 最大单份 | 14.4 KB / 102.4 KB |
| 增速 | 约 **113 份/天**、**1.6 MB/天** |
| 按此速率外推一年 | 约 **4.1 万份 / 590 MB**（人气 10 倍 → 约 5.9 GB） |

**风险分级**（说清哪些是真实风险、哪些不是）：

| 说法 | 是否成立 |
| --- | --- |
| 「一年就把盘写满」 | ❌ 不成立。40 GB 小盘一年用不到 2% |
| 「目录文件数无上限，遍历越来越慢」 | ✅ 成立。备份、同步、杀毒扫描都按文件数付费，4 万份时肉眼可见 |
| 「盘满时服务会异常」 | ✅ 成立。落盘失败已不会拖垮进程（D-176），但盘满是**整机**问题：日志、临时文件同样失败 |
| 「换了容器部署就自然解决了」 | ⚠️ 半成立。临时盘重启即清，问题被掩盖而非解决，且回放也一起丢了 |

**已定口径**：保留 **7 天** + 总量 **500 MB**，启动扫一次、之后每日一次。
理由：7 天足够复盘一周内的问题；500 MB 在 40 GB 盘上无感，且能挡住「某天突然被刷出 10 万间房」的尖峰。

> 首次上线先跑了 **dry-run**：扫到 919 份、**待删 0 份**、保留 12.95 MB —— 当时目录里已没有超过 7 天的文件。
> 正式模式再跑一次，结果相同（`removed: 0`）。也就是说这次落地**没有删掉任何一份回放**。

### 8.2 速率限制

先给结论：**这不是「加一个限流中间件」就完事**。本项目有三个不同层面的暴露面，而其中一层在当前的穿透部署下**按 IP 限流会失效**。

#### 三个暴露面

| 层面 | 现状 | 实测 / 判断 |
| --- | --- | --- |
| **建房** `room:create` | 无任何上限 | 单条连接 **0.3~0.5 ms/间**，2000 间 **0.7 秒**；每间约 **8.3 KB** 内存 + 一个运行时（计时器 / SeqGuard / ReplayRecorder） |
| **加入** `room:join` | 无任何上限 | 房间码 32^6 = **10.7 亿**，单连接每秒可试数千次。猜中只是「进到你房间」，房内无敏感数据，风险低于前者，但会白烧 CPU |
| **操作** `game:intent` | 无频率上限 | 每条走完整链路（zod → 引擎 → reduce → 哈希）。被拒的 Intent 不续回合计时（ADR-0017 §2），但 CPU 照烧 |

#### 已经修掉的（D-181）—— 这才是「没有限流」最严重的形式

**一条连接可以建无限个房间，而且永远不会被回收。**

原因不是回收逻辑写错，而是两处拼起来才暴露：

- `socket.data.playerId` 每次建房都被**覆盖**，旧席位仍标记 `connected: true`；
- `prune()` 只回收 `connected: false` 且超过宽限期的席位 —— 这条契约本身是对的（断线要留 60s 重连窗口），但它意味着**标着「已连接」的席位永远不会被回收**。

实测：单连接建 2000 间后断开，**只有最后那间被回收**，其余 1999 间连同运行时永久滞留，内存从 93 MB 涨到 110 MB，且不回落。

修法：建房 / 加入 / 重连写入新席位前，先释放这条连接上的旧席位（`releaseSeatOf`）。一个连接只占一个席位，本来就是产品语义。修后实测：连建 5 间，前 4 间当场 `ROOM_NOT_FOUND`，只剩当前那间。

#### 仍然敞着的三个口子

1. **连接数无上限**：一条都是合法连接，每条可以各占一间房。1 万条连接 ≈ 1 万间房 ≈ 数百 MB。
2. **单连接操作频率无上限**：修完后一条连接只能占一间房，但可以每秒建/退几百次来回刷。
3. **全局房间总数无上限**：没有任何「总共最多多少间房」的兜底。

#### 一个必须先知道的部署事实

**走 frpc TCP 隧道时，所有公网客户端在服务端眼里都是 `127.0.0.1`。**

因为隧道是 L4 转发：远端用户 → 隧道节点 → 你本机的 frpc → `127.0.0.1:3100`。服务端拿到的对端地址是 frpc 那一端，不是用户的真实 IP。

**后果：按 IP 的令牌桶会把所有朋友算成同一个人** —— 一个人手快，其他人一起被限；反过来也挡不住「用同一个 IP 换很多连接」的攻击。

所以限流只能从这三种里选（或组合）：

| 方案 | 在穿透部署下有效？ | 在 VPS 直连下有效？ | 复杂度 |
| --- | --- | --- | --- |
| A. **按连接**限流（每条连接的 create/join/intent 频率） | ✅ | ✅ | 低，几十行 |
| B. **全局上限**（最多 N 间房、总共 M 个连接） | ✅ | ✅ | 低，一个计数器 |
| C. **按 IP** 限流 | ❌ 全部同一 IP | ✅ | 中，需拿真实 IP（nginx `X-Forwarded-For` 或 PROXY protocol） |

#### 已定口径

- **只做 A + B**（穿透下 C 无效），阈值取「宽到真人永远碰不到、窄到脚本立刻撞墙」：
  - 建房：每连接 **10 次/分钟**；
  - 加入：每连接 **20 次/分钟**（输错房码重试要留余量）；
  - Intent：每连接 **20 次/秒**（真人上限约 5 次/秒）；
  - 全局：最多 **2000 间房**、**5000 条连接**；
- 超限一律**回一句人话**，不断开连接 —— 断线会让正常玩家以为是自己网掉了。
  实测回包：`{"error":"RATE_LIMITED","message":"操作太频繁，请等 60 秒再试"}`；
  Intent 超限走的是 `game:events` 的 rejected 分支（客户端 `emit` 不带 ack，只回 ack 玩家看不到）。

#### 零成本的第一步（不改代码）

在隧道/云主机那一层加一道门，比任何限流都省事：

- 隧道服务商的隧道设置里若有**访问密码 / IP 白名单**，直接开 —— 代码一行不改就挡住了绝大多数扫描器；
- 若将来上 VPS，Nginx 层可以加 `limit_req` 与基础认证。

> 判断标准：**给朋友玩**，隧道层的门 + A/B 两档限流足够；**公开对外**，还得补 C（真实 IP）与账号体系 —— 但那已经是另一个量级的工作。
