## 1. 需求 → 选型对照

| 需求 | 选型 | 为什么 |
| --- | --- | --- |
| 弱客户端（网页） | 浏览器原生 HTML/CSS/JS 技术栈，React + Vite | 免安装、跨平台、首屏可控；Vite 产物小、构建快 |
| 适配移动端 + 电脑端 | Tailwind CSS，mobile-first，单一响应式布局 | 一套代码两套端；避免维护两套 UI |
| 界面点击交互 | DOM 事件 + 状态机化的 `Intent` 派发 | DOM 天然支持可访问性（键盘/读屏），点击热区可控 |
| 图形界面显示 | 卡牌/桌面 = DOM + CSS Transform；特效 = PixiJS 懒加载 | DOM 处理布局与文字清晰；WebGL 只用在需要大量粒子的地方 |
| 联网对战房间 | Socket.IO Room / Namespace | 房间语义内置，支持广播、重连、降级长轮询 |
| 实时联网对战 | WebSocket（Socket.IO）+ 服务器权威事件广播 | 低延迟双向；权威模型防作弊、能回放 |
| 规则后续扩展 | 纯函数规则引擎 + 插件注册表 | 新增规则零侵入既有代码 |

## 4. 原子化架构（核心）

### 4.1 单一执行链路

```
[UI 点击] → Intent → 客户端校验(形状) → socket.emit
    → 服务端: 鉴权/回合校验 → rules[intent.type](state, intent, ctx)
        ├─ 通过 → GameEvent[] → reduce(state, events) → 新 state + hash
        └─ 拒绝 → Rejection{code, message}（零副作用）
    → 广播 {events, hash, seq} → 各客户端 reduce → 渲染
```

### 4.2 契约定义（示意，实际以 `packages/shared` 为准）

```ts
// ---- shared ----
export interface Intent<T = unknown> {
  type: string;          // 'play_card' | 'attack' | 'end_turn' | ...
  playerId: string;
  seq: number;           // 幂等序号，服务端按 playerId 单调递增校验
  payload: T;
}

export interface GameEvent<T = unknown> {
  type: string;          // 状态变更事实，'card_played' | 'damage_dealt' | ...
  ts: number;            // 服务器时间戳（唯一时间源）
  payload: T;
}

export interface Rejection { code: string; message: string; }

// ---- core ----
export type RuleHandler = (
  state: Readonly<GameState>,
  intent: Intent,
  ctx: RuleContext        // { rng, config, now(来自事件时间), query }
) => Result<GameEvent[], Rejection>;

export type Reducer = (state: GameState, event: GameEvent) => GameState;

export const rules: Record<string, RuleHandler> = {
  play_card: playCardRule,
  attack: attackRule,
  end_turn: endTurnRule,
  // 新增机制只需在此加一行
};
```

### 4.3 原子化七条军规

1. **一个交互 = 一个 Intent**，不允许多个状态变更藏在一次点击里（可产生多个 Event，但由同一 Intent 派生）。
2. **规则函数纯**：入参不可变，出参只有事件数组或拒绝。副作用（发牌动画、音效）由**事件订阅者**响应，属 `view` 层。
3. **校验前置**：回合归属、资源是否够、目标是否合法，全部在 handler 内先校验再产事件。
4. **单点时间源**：只信服务端 `ts`，客户端倒计时用「服务端时间 - 本地偏移」估算。
5. **单点随机源**：`ctx.rng` 为种子 RNG；同种子同序列必得同结果。**RNG 游标存于 `GameState.rngCursor`**：handler 从 `ctx.rng` 取值并把消耗写入事件，reducer 依据事件推进游标 —— 以此让「规则函数纯」与「回放可复现」同时成立（禁止把 RNG 状态藏在闭包或模块变量里）。
6. **幂等**：`(playerId, seq)` 为唯一键；重复或乱序的 Intent 直接丢弃并记录。**去重表由服务端 Room 会话层持有（`Map<playerId, lastSeq>`），不进 `GameState`，也不由 `core` 实现** —— 见 `ADR-0011`。
7. **可回放**：`replay.json = { seed, intents[], hashChain[] }`，`intents[]` 必须**包含系统 Intent**，回放一致性由单测保证。
8. **系统 Intent 同链路**：回合超时等由服务端发起的行为，必须由会话层构造 `{ actor: 'system', reason: '...' }` 走与玩家相同的 `applyIntent` 链路；禁止在 `core` 内读时钟，禁止会话层绕过引擎直接改状态。

> **状态归属判据（普适）**：凡影响游戏结果的外部状态必须入 `GameState`（如 `rngCursor`）；凡不影响结果、只保证传输可靠性的状态一律不入（如 seq 去重表）。

### 4.4 扩展方式（后续加规则的标准动作）

| 你要加的东西 | 需要改的地方 | 需要碰既有代码吗 |
| --- | --- | --- |
| 新卡牌 | `card-set` 数据文件 + 需要的 handler | 否 |
| 新关键词 / 异能 | `packages/core/src/rules/<keyword>.ts` + registry 注册一行 | 否 |
| 新阶段 / 新回合结构 | `turn-flow` 配置 + 阶段 reducer | 否 |
| 新游戏模式 | 新 `config` + 新 registry 组合 | 否 |

**判定标准**：任何一次规则扩展，如果 diff 触及了已有规则文件内部实现，视为架构违规，必须重构。

## 5. 联网与同步细节

- **握手**：`create_room` → 返回 4–6 位房间码；`join_room(code)`；`ready()`；`start()`。
- **席位**：playerId 绑定 socket，断线 **60s（`RECONNECT_GRACE`）** 内 `reconnect(playerId, token)` 恢复席位；回合无操作超时为 **30s（`TURN_TIMEOUT`）**。两个常量命名固定，不得混用。
- **超时入链路的方式**：会话层发现超时后构造系统 Intent `{ type: 'end_turn', actor: 'system', reason: 'timeout' }`，喂给与玩家相同的 `applyIntent → reduce → stateHash → 写 replay → 广播` 链路。读时钟只允许发生在会话层（见 `ADR-0011`）。
- **顺序**：服务端为每次广播编号 `serverSeq`；客户端发现缺口则请求 `sync_since(serverSeq)` 补发。
- **幂等续接**：服务端按 `playerId` 记录 `lastSeq`；重连时随快照下发，客户端从 `lastSeq + 1` 继续，禁止使用本地计数重置（否则所有 Intent 会被判为重复而丢弃）。
- **一致性校验**：客户端每次 reduce 后算状态哈希，与服务端下发的 `hash` 比对，不一致 → 上报 `desync` 事件并记入测试报告。哈希必须对**规范化序列化**结果计算（对象键排序、数组顺序固定、`undefined` 统一处理），否则会产生假 desync。
- **并发前提**：单房间的 Intent 处理链 **禁止出现 `await`**。Node 单线程下无异步让出的同步链路天然原子，两玩家同时出牌不会撞状态；一旦插入异步就会引入「旧测试通过、偶发才现」的竞态。确需异步（持久化等）放到整条链完成之后。
- **观战**：只订阅广播、不持有 Intent 权限（Demo 阶段可选）。

## 6. 性能预算（弱客户端）

| 指标 | 目标 |
| --- | --- |
| 首屏 JS（gzip） | ≤ 1.5MB（特效包懒加载不计入） |
| 首屏可交互 | ≤ 2.5s（4G） |
| 操作到本地反馈 | ≤ 100ms |
| 操作到对手可见 | ≤ 150ms（同城） |
| 对战帧率 | ≥ 30fps（低端机）/ 60fps（主流） |

## 7. 部署

```yaml
# docker-compose.yml（示意）
services:
  server:
    build: ./packages/server
    ports: ["8080:8080"]
  client:
    build: ./packages/client
    ports: ["80:80"]
  # nginx: / → client 静态；/socket.io → server (WSS)
```

Nginx 需为 `/socket.io` 开启 WebSocket 升级头：`Upgrade`、`Connection`。

> **验证口径（C1 已定）**：本机（Windows）无 Docker 与 WSL，`docker-compose.yml` 属于**照写留档**，不在本机验证。
> 联机测试走局域网直连：`pnpm dev` 后手机访问 `http://<本机局域网 IP>:<port>`。
> 部署验证须在云主机执行，测试报告中「部署」一项应标注**本机未验证**，不得写成通过。

> **client 容器需 multi-stage 构建**（`vite build` 产物 → Nginx 静态目录），`server` 需为 `replay.json` 挂卷；这两点在写 compose 时一并补齐（见 `docs/07` 的 R-17）。
