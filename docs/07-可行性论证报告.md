## 5. 架构层论证：三个真问题

### 5.1 RNG 状态 vs 纯函数（R-06）

规则处理器被要求纯函数、无副作用；但洗牌/抽牌必须推进随机游标。规范只写了「`ctx.rng` 为种子 RNG」，没写游标存在哪里 —— 这是个真空。
**若不补**：回放时 rng 起点不同 ⇒ 终局哈希不同 ⇒ M8 必然失败，且失败原因难以定位。
**补法**：`GameState` 增加 `rngCursor`；handler 从 `ctx.rng` 取值并把消耗写入事件；reducer 依据事件推进游标。这样「纯函数」与「可复现」同时成立。

### 5.2 单向 Intent 协议 vs 触发式选择（R-07）

当前协议是 `客户端 Intent → 服务端 Event` 单向。玩家主动出牌指定目标没问题（目标随 Intent 一起发出）。但**由规则触发的、需要玩家在结算中做选择**的效果（例如「打出时：选一张手牌弃掉」）缺少表达：服务端需要反过来向玩家发起一次选择请求。
**这不属于玩法发明，是协议完备性问题。** 是否启用取决于你的 A7 关键词；但若届时才发现，改动会波及 shared 协议、服务端房间状态机、客户端 UI 三处。
**建议**：现在就预留 `pendingChoice` 字段与状态位（成本极低），等 A7 输入后再决定是否激活。

### 5.3 状态哈希与幂等续接（R-09 / R-08）

- 哈希：只要序列化时键顺序不稳定（对象在不同代码路径下构造顺序不同），双端就会算出不同哈希，产生**假 desync**，把真问题淹掉。必须规定 canonical 序列化。
- seq：重连后客户端若从本地计数继续发，服务端判定为「seq 不递增」而全部丢弃 —— 表现为「重连成功但点什么都没反应」。这个 bug 极难自查，必须提前约定由服务端下发 `lastSeq`。
