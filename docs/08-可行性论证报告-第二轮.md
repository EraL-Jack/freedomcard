## 0. 结论

**判定：有条件可行 —— 维持一轮结论，但新增 2 条阻塞级缺陷。**

一轮的架构判断没有被推翻：`core / net / view` 三层分离 + 事件溯源 + 权威服务器的组合依然成立，且本轮用真机构建实测证明了它在 Windows + pnpm workspace 下跑得通。

但一轮的论证方式存在一个盲区：**只审了文本，没跑构建；只查了版本号，没验证版本能不能一起干活。** 二轮把这两块补上后，暴露出两个新问题，其中一条直接命中 `prompts/01` 的第一条验收标准。

### 2.2 实测副产品结论

**① 一轮改的 Tailwind v4 写法是对的，实测可落地。**

一轮我把 `prompts/01` 第 7 条从 v3 的 `tailwind.config.js` 改写为三条（`@tailwindcss/vite` 插件 / `@import "tailwindcss"` / `@theme` 断点）。二轮本地真实构建验证：`xs:` → `@media (width>=375px)`，`lg:` → `@media (width>=1440px)`，全部生成。这条属于「一轮改对了但没验证」，二轮补票通过。

**② `--breakpoint-*` 变量本身不输出到 CSS，直接编译进 media query 字面值。**

产物里搜不到 `--breakpoint-xs` 变量，但 media query 用的是 `375px`。这是 Tailwind v4 的正常行为（主题变量 tree-shake）。**对测试有意义**：验收「断点是否生效」时，只能查 media query，不能查变量是否存在 —— 否则会得出假阴性。

**③ Vite 8 已切换为 rolldown 打包。**

实测安装过程下载了 `@rolldown/binding-win32-x64-msvc`（8.25 MB）。本次涉及的 `@tailwindcss/vite` 已验证兼容，但任何依赖 rollup 插件生态的第三方库都需重新验证（见 `R2-16`）。

**④ Zod 在客户端产物里占体积。**

仅引一个 `z.object` 的情况下，client 产物已达 **83.93 kB / gzip 24.17 kB**，其中 Zod 是大头。当前远低于 M7 的 1.5MB 上限，不构成问题，但见 `R2-10`。

## 3. 新风险登记表

> 编号 `R2-xx`，与一轮 `R-xx` 独立编号，便于追溯来源。

### 3.1 阻塞级

#### R2-01 · `pnpm install` 退出码非 0 —— 直接作废 `prompts/01` 首条验收

- **位置**：`prompts/01` 验收第 1 条；本机 pnpm 12.11.2
- **现象**：`pnpm install` 以 `exit=1` 结束，报 `ERR_PNPM_IGNORED_BUILDS`（被忽略的构建脚本：`esbuild@0.28.2`）。依赖其实装上了，后续 `vite build` / `tsx` 也正常，但退出码是 1。
- **后果**：`prompts/01` 的验收写的是 `pnpm install && pnpm dev` —— **`&&` 短路，`dev` 永远不会执行**。任何把它抄进 `package.json` 脚本或 CI 的地方都会直接失败。这是「看起来做完了、实际第一步就断」的典型。
- **返工代价**：脚手架阶段即触发，执行方大概率以为是环境问题乱改一通，而不是退出码语义问题。
- **处置**：三方可用方案见 §6 待决项 `S1`。验收条款改为「`pnpm install` 必须 `exit=0`」。

#### R2-02 · 工作区没有 git 仓库 —— 变更日志规范缺少载体

- **位置**：`docs/03` §4；工作区根目录
- **现象**：`git rev-parse` 报 not a git repository，`prompts/01` 八个步骤里也没有 `git init`。
- **后果**：
  1. `docs/03` §4 规定「每次 commit 必须与一条日志条目对应」—— 没有 commit，这条规范落空，「可追溯」这条硬约束缺一半；
  2. 没有 `.gitignore`，`.workbuddy/`（含记忆、实测残留、`node_modules`）存在被误提交的风险；
  3. 规则引擎改错了没法回滚，与「未写日志的改动视为未交付」配套的强制手段失效。
- **返工代价**：越晚 init，历史越不可追溯，属于随时间放大的缺陷。
- **处置**：已在 `prompts/01` 补第 9 步（`git init` + `.gitignore` + 首次提交绑定到 `D-101`）。是否现在就 init 待 Era 确认。

### 3.2 高级

#### R2-03 · 超时事件如何进入事件流，规范未定义 ★架构核心

- **位置**：`docs/02`（9.房间/席位）、`prompts/03`（超时：30s 自动 `end_turn`）
- **问题**：规则引擎的硬约束是「禁 `Date.now()`」，但 `TURN_TIMEOUT=30s` 显然要读时钟。**这个 30 秒的判断到底写在哪一层，没有任何文档说清楚。**
- **执行方最可能的三种实现及其后果**：

  | 实现 | 后果 |
  | --- | --- |
  | ① 在规则 handler 里读时钟 | 违反纯函数约束 → 回放不可复现，M8 必挂 |
  | ② 会话层定时器直接改状态 | 绕过规则引擎 → **`stateHash` 断裂，客户端 reduce 不出同一结果，M3/M8 挂**，且极难定位 |
  | ③ 会话层检测超时 → 构造**系统 Intent** 喂给同一套处理器 | 引擎保持纯函数，事件流完整，回放天然包含超时事件 |

- **处置**（已写入 `ADR-0011`）：采用 ③ —— 会话层唯一的职责是「发现超时」，然后构造 `{ type: 'end_turn', actor: 'system', reason: 'timeout', seq }` 走与玩家完全相同的处理链路。`core` 不感知时间，只感知 Intent。
- **连带项**：两次操作之间计时是否重置属玩法输入（`A4-4`），等 Era 填。

#### R2-04 · 幂等去重表的归属未定义 ★架构核心

- **位置**：`prompts/02` 第 2 条「内置幂等表：`(playerId, seq)` 去重」，写在 `engine.ts` 里
- **问题**：这一条没有说去重状态存哪里，而它偏偏是「纯函数」约束的第三个受害者（前两个是 `R-06` RNG 游标、`R2-03` 超时）：

  | 存放位置 | 后果 |
  | --- | --- |
  | 入 `GameState` | `stateHash` 含去重集合，快照随对局线性膨胀；且每个 Intent 都要带着历史 seq 集合参与哈希，开销随回合数增长 |
  | 引擎外部持有 | `applyIntent` 依赖外部可变状态，**不再满足纯函数**，与 `docs/01` 硬约束 4 直接冲突 |

- **判据**（这一条我认为应该长期生效）：
  > **凡影响游戏结果的外部状态，必须入 `GameState`（如 `rngCursor`）；凡不影响结果、只保证传输可靠性的状态，一律不入（如 seq 去重表）。**
  >
  > RNG 游标影响洗牌结果 → 必须入 state（一轮 `ADR-0010` 结论正确）；seq 去重不影响任何游戏结果 → 归服务端会话层（Room）持有。
- **处置**（`ADR-0011`）：幂等去重从 `core` 移出，`core` 只负责「给定 state 与 intent，判断合不合法」；`(playerId, seq)` 去重由 Room 层 `Map<playerId, lastSeq>` 承担。

#### R2-05 · `prompts/02` 预设了玩法 —— 与「不得发明玩法」冲突

- **位置**：`prompts/02` 第 5 条
- **问题**：在 A 组规则全部为「待输入」的情况下，提示词已经写死了五个规则文件：
  ```
  draw.ts 抽牌 / play-card.ts 出牌（含费用校验）/
  attack.ts 攻击（含目标合法性与召唤失调校验）/
  end-turn.ts 结束回合 / game-over.ts 胜负判定
  ```
  其中 **`attack.ts` 的「召唤失调」是一个明确的炉石术语**，等于替 Era 发明了一条玩法规则。
- **性质**：与一轮已修正的 `R-05`(`docs/05` 建议范围未作废) 是**同一类错误，只是藏得更深** —— 一轮把明面上的建议范围废掉了，但没有顺着这条线检查其他文件里散布的同款预设。
- **后果**：执行方可能直接实现「召唤失调」，把它当成既定需求；若 Era 的玩法没有随从/攻击概念，整个 `rules/` 目录作废返工。
- **处置**：已改为「示例骨架 + 显式声明」（见 §5）。

#### R2-06 · `prompts/04` 预设了界面 —— 同 `R2-05`

- **位置**：`prompts/04` §4.1 页面、§4.3 响应式表
- **问题**：B 组全部「待输入」，但提示词已写死：四页清单（大厅/房间/对战桌/结算）、竖屏「场面网格 2×4」、桌面 hover 预览与快捷键。这些都是 `B1`/`B2`/`B3` 的待输入内容。
- **处置**：已标注为缺省骨架，明确「B 组输入后以输入为准」。

## 6. `S1` 定案记录（2026-10-13 三轮补测）

> 本节内容是对 §2.1 `V2-10`「未修复」结论的**追平**。Era 授权后，我用干净环境做了反向对照，问题已彻底解决。

### 6.1 三轮对照实测（干净重装，删 `node_modules` + lockfile）

| 组 | 配置 | `pnpm install` 退出码 |
| --- | --- | --- |
| A | `pnpm-workspace.yaml` **无** `allowBuilds` | **1**（`ERR_PNPM_IGNORED_BUILDS`） |
| B | `pnpm-workspace.yaml` **有** `allowBuilds: { esbuild: true }` | **0** |
| 辅助 | 由 `pnpm approve-builds --all` 自动生成 B 组配置 | 写入正确，无需手抄 |

真实项目场景（Vite 8 + Tailwind 4 + tsx，35 个包）下，**只有 `esbuild` 一个包需要批准**；`@tailwindcss/oxide` 是平台可选依赖、无 postinstall，不在白名单内。

### 6.2 根因：键名在 pnpm 12 已改名

| 写法 | pnpm 10 | pnpm 12（本机 12.11.2） |
| --- | --- | --- |
| `onlyBuiltDependencies` | 有效 | **失效**（`pnpm config get` 返回 undefined，写了等于没写） |
| `allowBuilds` | 不存在 | **有效** ✅ |
| `.npmrc` `dangerously-allow-all-builds=true` | 有效 | 失效 |
| CLI `--dangerously-allow-all-builds` | 有效 | 有效（但等于全局放开，**不采用**） |

二轮 `V2-10` 判定「白名单无效」的真正原因**不是方案错了，而是键名过时** —— 我照 pnpm 10 的文档写 `onlyBuiltDependencies`，pnpm 12 静默忽略。教训已写入 `prompts/01` 第 10 条。

### 6.3 定案

**采用白名单（最小授权）**，由 `pnpm approve-builds --all` 自动生成：

```yaml
packages:
  - 'packages/*'
allowBuilds:
  esbuild: true
```

后续新增带 postinstall 的依赖（`playwright`、`sharp` 等）时**追加进白名单**再重装，不得改用全局放开。

### 6.4 另一项已执行

**git 仓库已建立**（2026-10-13）：工作区根目录 `git init`，分支 `master`，`.gitignore` 已写入。`docs/03` §4「commit 与日志条目对应」从此有载体。
