# 交付件变更日志规范

适用对象：`docs/`、`prompts/`、`logs/`、`reports/`、`app/` 下一切交付件。
落盘位置：`logs/CHANGELOG.md`（**append-only，禁止改写历史条目**）。

---

## 1. 交付件编号

| 前缀 | 含义 | 示例 |
| --- | --- | --- |
| `D-1xx` | 代码 / 工程交付件 | D-101 可运行工程 |
| `D-2xx` | 文档 / 规范交付件 | D-201 主提示词 |
| `D-3xx` | 配置 / 部署交付件 | D-301 docker-compose |
| `T-xxxx` | 测试报告 | T-0001 |
| `F-xxxx` | 用户反馈报告 | F-0001 |
| `ADR-xxxx` | 架构决策 | ADR-0001 |

编号一经分配不得复用；交付件删除时保留编号并在日志中标注 `→ 作废`。

## 2. 日志条目字段（全部必填）

| 字段 | 说明 |
| --- | --- |
| 时间 | `YYYY-MM-DD HH:mm`（本地时间） |
| 交付件 ID | 如 `D-201` |
| 交付件名 | 文件路径或名称 |
| 版本 | 如 `v0.1 → v0.2` |
| 类型 | 新增 / 修改 / 修复 / 重构 / 删除 / 作废 |
| 原因 | 为什么改（需求变更 / 缺陷 / 反馈 / 架构调整） |
| 变更摘要 | 具体改了什么，一句话到三条 |
| 影响范围 | 受影响的交付件 ID 列表 |
| 关联 | 需求槽位 / `T-xxxx` / `F-xxxx` / `ADR-xxxx` |
| 回归验证 | 做了什么验证，结果如何（未验证必须写「未验证」） |
| 破坏性 | 是 / 否；为「是」时必须已有对应 ADR |

## 3. 条目模板（复制即用）

```markdown
### [2026-10-12 15:30] D-201 · docs/01-主提示词-Demo-v0.1.md
- 版本：无 → v0.1
- 类型：新增
- 原因：项目启动，建立 Demo 生成主提示词
- 摘要：
  1. 新增 11 个待填充槽位（规则 / 界面 / 部署）
  2. 锁定技术栈与原子化硬约束 10 条
  3. 定义 8 项验收标准与 6 条禁止事项
- 影响范围：D-202、D-203、prompts/01~05
- 关联：ADR-0001, ADR-0002
- 回归验证：人工通读，槽位与 docs/05 清单逐项对齐 —— 通过
- 破坏性：否
```

## 4. 与 git 的关系

- 每次 commit 必须与一条日志条目对应，commit message 里带上交付件 ID：`docs(D-201): 建立主提示词 v0.1`。
- 一次 commit 只做一件事；日志条目的一行 = 一个 commit 的意图。
- 变更日志是**人可读的决策轨迹**，git 是**机器可读的精确差异**，两者互补，不可互相替代。
- **仓库初始化责任**：若工作区尚无 git 仓库，由 `prompts/01` 第 9 步负责 `git init` 与 `.gitignore`（须忽略 `node_modules/`、`dist/`、`.workbuddy/` 等）。在此之前本节关于 commit 的条款暂时无法执行 —— **但日志必须照常记录，留痕先行于 git，不得因为没仓库就省略条目。**

## 5. 强制规则

1. 未写日志的改动视为未交付。
2. 破坏性变更（协议字段、状态结构、部署方式）→ 必须先写 ADR，再改代码，日志中引用 ADR 编号。
3. 每个 Demo 版本发布时，在日志顶部追加一条「版本汇总」条目，列出该版本包含的全部交付件 ID 与版本号。
4. 缺陷修复必须引用其来源：来自测试的写 `T-xxxx`，来自你（用户）的写 `F-xxxx`。无来源的修复不予记录。
