# ETCG · 运行说明

> 游戏名 **ETCG**（Era 2026-10-21 定的代称，正式名待定），副标题「混合风格 · 什么样的卡组都有」。
> 本文件是运行 / 部署 / 接口手册；玩法条文见 `docs/16`，架构决策见 `logs/DECISIONS.md`。

## 1. 环境要求

| 项 | 版本 | 备注 |
| --- | --- | --- |
| Node.js | `>=22.12.0` | 本机实测 22.22.2 与 24.14.0 均可 |

## 2. 安装

```bash
cd app
pnpm install
```

安装必须返回 `exit=0`。若出现 `ERR_PNPM_IGNORED_BUILDS`：

```bash
pnpm approve-builds --all   # 非交互，自动把待批准清单写进 pnpm-workspace.yaml
pnpm install
```

## 3. 启动（开发态）

```bash
pnpm dev          # 同时起 server(3000) 与 client(5173)
```

- 客户端：<http://localhost:5173>
- 服务端直连：<http://localhost:3000/health> → `{"ok":true,"version":"0.1.0"}`

客户端通过 Vite 代理访问 `/health` 与 `/socket.io`，因此页面与服务端**同源**，无需处理 CORS。

### 3.1 建房选项：卡组 / 赛制 / 每回合时限

主界面填昵称后，建房前可以定三件事：

| 选项 | 取值 | 说明 |
| --- | --- | --- |
| 我的卡组 | 三套基础卡组 + 你的自建卡组 | 一套 = 30 张主卡 + 1 位指挥官（D-184）。不足 30 张的置灰，并提示「开局将使用哪套」 |
| 赛制 | BO1 / BO3 | BO3 双方各先手一次；第 3 局由上一局败者先攻（H33） |
| 每回合时限 | 30 / 60 / 180 / 999 秒 | 默认 **60 秒**（H18 / D-244）。回合内任何被接受的操作都会重新计时 |

- **人数固定 2**：规则只验证过两人对局，界面不再给人数输入（T-07 / D-245）。
- 时限是**房间级**的：建房时定，全场不变，准备页会显示「BO1 一局定胜负 · 每回合 60 秒」，
  对手也看得见。服务端只认这四个档位，传别的值（如 120000）会回落默认而**不报错**。
- 开始下一局（BO3）沿用同一时限。

### 3.2 人机对战（D-242）

主界面点 **「人机对战（对手：电脑）」** 就能开一间单人房，**不用再开第二个窗口**：

- 建房瞬间服务端就坐入一个 AI 席位（昵称「电脑」），房间容量固定 2 人；
- AI 永远就绪 —— 你点「准备」立刻开局；
- AI 每 600ms 走一步，走法与真人**完全相同**（服务端系统 Intent），
  所以断线重连、回放记录、事件日志全都照常，不需要任何特殊处理；
- 用的是你当前选的**卡组 / 赛制 / 时限** —— 想试新卡组就开人机房；
- 定位是「能完整打完一局」的启发式，不是博弈 AI（不算斩杀、不留牌）。
  要调强度只改 `core/src/ai.ts` 的 `decideAiMove`，其它层不受影响。
- **会用技能、会充能**（D-288 / issue #137）：主要阶段先问一次指挥官技能
  （统领Ⅰ / 裁决官Ⅰ，星轨观测者则挂在指挥官攻击的付费展示上），
  充能阶段把「本回合付费超出剩余额度」的随从换进费用区。
  技能的**发动门槛由效果模块回答**（`EffectModule.aiCouldUse`），AI 侧不抄档位数字 ——
  改档位常量（D-290 把除外档前移到 1/2/3/5/7）AI 会自动跟随。
- 改完 AI 想验证强度，跑一次基线（1200 局，约 3 秒）：
  `AI_BASELINE=1 AI_BASELINE_GAMES=200 pnpm --filter @app/core test --run src/ai-baseline.test.ts`
  —— 会打印两张表：**每组对局**（技能/局、充能张/局、先手胜率、平均回合、平均轮数、未结束）
  与**每个体系**（出场人次、胜率、顶档可达率），外加空过率。
  这些就是 `docs/16 §15.4` 的验收线，指标口径写在 `ai-baseline.test.ts` 文件头。
  轮数 / 体系胜率 / 空过率**超标会直接红**；顶档可达率只打印（达不到要 Era 拍板降档）。

### 3.3 新手引导与音效

- **首次**进入对战桌会弹四步引导（**换牌** → 充能 → 推进阶段 → 出牌与攻击），点完或跳过就写入
  `localStorage['fc.introSeen']`，之后不再出现（P-03 / D-292）。
  第一步必须与玩家此刻所处的阶段一致 —— 首次进桌停在换牌阶段，引导就从换牌讲起（issue #117）。
- 音效三条（打击 / 抽牌 / 结算）用 Web Audio 现场合成，不依赖素材文件（P-06 / D-248）。
  操作条右侧「音效：开/关」可静音，选择存本机。

### 3.4 开局换牌与出牌两段式（D-257 / D-259）

**开局换牌**（ADR-0048）：双方准备后**不会直接进第一回合**，而是先停在「换牌」阶段 ——
顶部回合数显示 **「开局」**，进度条最左边多一枚紫色「换牌」标签。

- 双方**同时**选：点手牌切换取舍（可多选），选好后点 **「确认换牌（N）」**；
- 不想换就直接点 **「不换牌」**（等价于提交空数组，没有「取消换牌」这条路）；
- 各自确认一次即锁定，顶栏显示「你已确认 · 对手换牌中」；
- **双方都确认**才进入第一回合充能阶段。
- **有倒计时，且到点自动开局**（D-267）：顶栏「计时 Ns」+ 提示条里「剩余 N 秒」，
  倒计时归零时服务端替还没确认的人提交「不换牌」，按钮变成「换牌时间到，正在开局…」。
  时长**跟随建房里选的回合时限**（30 / 60 / 180 / 999 秒），不再固定 30 秒 ——
  Era 2026-10-21：「换牌时间也按每回合时间来定，不要固定值」。
- **人机房一样有这个阶段**（D-262）：AI 会自己提交「不换牌」，你先手时它也会提交，
  不会让你干等。换牌阶段是双方**同时**进行的，没有「轮到谁」。

**出牌两段式**（ADR-0049）：主要阶段点手牌旁的「出牌」之后 ——

1. **选位置**：我方三格全部高亮，标签写「放这里」或「顶替 X」。
   点哪一格就放哪一格；该格已有随从则**顶替**，被顶替者进弃牌区（满场也能出牌）。
   拖拽手牌到某一格等同于选那一格。
2. **选费用**：费用区比「该付的张数」多时，弹面板让你挑用哪几张付（点击切换，选满才能确认）；
   刚好够付则不弹，直接结算。

**拖拽出牌**（D-272 / issue #108）：法术与设置法术**没有位置**，所以拖到**我方法术区**就是直接出牌
（等价于点「出牌」）；万一拖到随从格，也按「无位置出牌」处理，不会出现「只有随从需要指定位置」。
拖着随从时随从区高亮（充能阶段则是费用区），拖着法术时法术区高亮 —— 高亮跟着牌型走。

行动条上方常显一句「现在该做什么」的提示（`data-testid="phase-hint"`）：
充能阶段是**琥珀底色**、换牌阶段是紫色 —— 这两个阶段最容易迷路。

**回合交棒期间**（D-268 / issue #101）：上一回合的结束阶段推进到下一回合时，
客户端为了动画会把「进入充能」与「换席位」分两帧播放，这两帧之间顶栏显示
**「回合切换中…」**（琥珀色，`data-testid="turn-label"`），且**不给**「该你做什么」的提示。
原因是那一帧「阶段已充能、席位还没换」的局面从未真实存在过 —— 照着它提示，
刚结束回合的人会看到「你的回合 · 充能阶段：点手牌里的随从…」，然后才交棒给对手。
动画落地后归属文案才恢复成「你的回合 / 对手回合」。

**先攻第一回合抽 1 张**（D-287 / issue #139）：先攻方第 1 回合的抽牌阶段**和别处一样停在抽牌**，
点卡组抽 **1 张**（后攻方与之后每回合是 2 张），抽完自动进主要阶段。
张数只有 `FIRST_TURN_DRAW` / `DRAW_PER_TURN` 两个常量 → `drawCountFor()` 一个出口，
客户端的 `canDraw` 与阶段指引都读它，不复制规则。

**抽 0 张的阶段自动推进**（D-271 / issue #109 的能力，**保留**）：若某个抽牌阶段该抽 0 张
（改数值或以后加特殊模式时会出现），引擎补一条 `draw:completed` 后立刻进主要阶段、不停住；
但事件流完整，界面照常播「抽牌阶段」那一拍 —— **自动推进 ≠ 跳过抽阶**
（Era 2026-10-22 校正口径）。判定收在 `shouldAutoAdvanceDraw(count)` 一处，`core` 直接导出。

### 3.5 查看卡牌详情（D-261）

原来卡面右上角那个 16×16 的小「?」已经删掉（Era 反馈「太难点了」）。现在三条入口：

| 入口 | 场景 |
| --- | --- |
| **长按卡面 400ms** | 手机主路径；整张卡都是命中区，敌我双方、堆叠区浮窗里的卡都能长按 |
| **右键** | 电脑上快捷入口 |
| **选中手牌 → 卡上方「详情」** | 想看清楚再决定时用这个（正常按钮大小） |

详情里显示完整效果文本、关键词注释与当前实际数值；可发动的效果按钮也长在里面。
长按与拖拽不冲突：手指移动超过 10px 就转成拖拽。

### 3.6 查看堆叠区（D-265）

场上那五个「卡组 / 法术 / 弃牌 / 除外 / 费用」区**只显示区名与张数**，内容不铺在牌桌上 ——
弃牌区到 15 张、费用区到 10 张是很常见的量，牌桌那一格再怎么也塞不下。

| 区域 | 框里显示 | 点开 |
| --- | --- | --- |
| 法术 / 弃牌 / 除外 / 费用 | 区名 + 张数 + `›` | **浮窗**里看全部卡（390px 三列 / 宽屏五列，可滚） |
| 卡组 | 区名 + 张数 | 不给看 —— 卡组顺序是隐藏信息，能翻看就等于提前知道下一张抽什么 |
| 指挥官 | 直接显示（不可收起） | 它是**攻击目标**，必须一直看得见 |

浮窗是**居中模态**（Era 2026-10-21 确认，不做可拖动面板，D-266）：
点遮罩或「关闭」退出，关掉才能继续操作牌桌。卡面照常可以长按看详情。
0 张的区域不给点（五区大部分时间空着，点出一片空浮窗只是噪音）。

### 跑 E2E 的两个前置（本机 Windows 必读）

1. **先手动起服务，再跑 E2E** —— `playwright.config.ts` 里的 `webServer` 自行拉起
   `pnpm -r --parallel dev` 时**收不到就绪信号**，会卡到 timeout；但服务本身是能起来的。
   故本机改为先 `pnpm dev`，靠 `reuseExistingServer` 复用已跑着的服务：

   ```bash
   pnpm dev &                              # 或另开一个终端
   pnpm --filter @app/client test:e2e
   ```

2. **想要确定牌序就带 `GAME_SEED`** —— 手动起服务时环境变量要自己传，
   因为复用已有服务时 `playwright.config.ts` 里的 `webServer.env` **不会生效**（ADR-0021）：

   ```bash
   GAME_SEED=20261013 pnpm dev
   ```

   生产**不要**设这个变量，否则每局牌序相同。

   > 忘了带会怎样？**测试不会告诉你「seed 没生效」**，只是部分用例开始偶发红，
   > 而红的信息看起来像功能坏了（issue #149 就误伤过一次 D-290）。
   > 现在有一条守卫用例专门抓这个：`e2e/determinism.spec.ts` 连开两局比对起手，
   > 不一致就直接失败并把修法写在报错里。跑全量时它会排在前面，早失败早发现。

想只跑某一个文件：`pnpm --filter @app/client exec playwright test e2e/combat.spec.ts`

### 跑 E2E 的第三个前置：端口必须单实例（ADR-0075）

本机最容易踩的不是代码，是**环境**：之前的工作树或另一个会话可能还留着 dev 进程。

```bash
# 跑之前查一次：3000 / 5173 各应只有一个 LISTENING PID，且属于你刚起的进程
netstat -ano | grep LISTENING | grep -E ":(3000|5173)\b"
```

- **`5173` 上没有监听、而 vite 报的是 `5177` / `5178` 之类** → 端口已被占，vite 自动漂移了，
  而 `baseURL` 还写死 5173，用例其实打在**旧实例**上。清掉再跑。
- **`3000` 上有别的 server**（例如 `Worktrees\Fcardgame\master-*` 下的）→ 房间建在那个实例上，
  env / 配置不一定是你的。
- 长跑的 vite 打 `ws proxy error: ECONNRESET` 也是脏的信号：客户端收不到事件、
  服务端照常计时，于是「界面停在第 1 回合、服务端已经第 3 回合」——
  失败信息看起来像引擎坏了。

**出红时的正确顺序**：先拿旧实现（或 master）跑同一条用例。
旧实现也红 → 先查环境；只有「旧实现绿、新实现红」才叫回归。
2026-10-22 就是这样白白追了一轮：3 条红里 2 条退回旧实现照样红，根因是脏环境。

## 6. 生产形态

```bash
pnpm build
cd packages/server && SERVE_STATIC=1 pnpm start
```

`SERVE_STATIC=1` 时服务端托管 `client/dist`。**只有像前端路由的路径**（`/`、`/room/ABC` 这类
不带扩展名、也不在 `/assets/` 下的）才回退到 `index.html`；缺失的哈希资源一律 **404 JSON** ——
以前一律回 `index.html`，缺一个 CSS 就变成「HTML 冒充 CSS」，浏览器按 MIME 拒绝解析，
页面静默无样式（issue #107 / D-273）。
缺省不启用，开发态由 Vite 提供页面。

缓存策略（同样来自 issue #107）：

| 路径 | `cache-control` | 理由 |
| --- | --- | --- |
| `/assets/*`（Vite 内容哈希产物） | `public, max-age=31536000, immutable` | 内容变则文件名变，可永久缓存；不设的话每次打开都要重新校验 39 kB CSS + 407 kB JS，穿过隧道多一次失败机会 |
| `index.html` | `no-cache` | 它决定加载哪个哈希包，缓存住等于发版后还跑旧包 |

客户端另有一道兜底：样式表 / 脚本加载失败时页面顶部出现红条「页面资源加载失败…请刷新重试」
（`data-testid="asset-error"`），不再静默变成白纸。

### 7.1 本机常驻 + 穿透发布（Windows）

双击 `scripts\serve-public.cmd`（默认 3100，可传参 `serve-public.cmd 3200`）。
它做两件事：先 `pnpm --filter @app/client run build:atomic`，再以 `SERVE_STATIC=1` 起服务，
**同一个端口**同时提供页面与 `/socket.io` —— 所以一条隧道就够，不必开两个口。

```cmd
cd app\scripts
serve-public.cmd
```

穿透侧的硬性要求（踩过两次，务必照做）：

| 项 | 必须这样填 | 为什么 |
| --- | --- | --- |
| 本地地址 | **`127.0.0.1`** | Windows 把 `localhost` 优先解析到 IPv6 `::1`，而服务只绑 `0.0.0.0`，表现是隧道「已连接」但外网 502 |
| 本地端口 | `3100` | 与脚本默认值一致 |
| SakuraFrp 隧道类型 | **`TCP`** | `HTTP(S)` 隧道强制要求绑定自有域名，内地节点还要求已备案 |
| SakuraFrp 节点 | **非内地**（香港/日本/新加坡等） | 官方文档：TCP 隧道穿透 HTTP 应用时必须用非内地节点 |

隧道启动后控制台会输出 `节点域名:远程端口`，那就是访问入口。
自检两条命令：`curl http://127.0.0.1:3100/health` 应回 `{"ok":true,...}`；
再用手机 4G 打开隧道地址，能进主界面且出牌无延迟，才算真的通了。

> 进程与房间状态都在内存里：脚本窗口关掉、电脑重启、隧道断开，都会导致房间消失。
> 回放文件写在 `app/replays/`，但进程重启不会补写。

### 7.2 回放校验（`replay.json`）

每局结束会在 `app/replays/` 写一份 `<roomId>-<时间戳>.json`。校验一份记录能否**逐帧重放**：

> **观看入口当前置灰**（D-183）：游戏里看不了回放，接口也没开 —— 公网隧道每月流量有限。
> 记录本身一直正常写盘，下面这条 CLI 校验的就是同一批文件。原因与开放方式见 §10 第 11 条。

```bash
cd app
pnpm --filter @app/server run replay:verify replays/<file>.json            # 只比哈希链
pnpm --filter @app/server run replay:verify replays/<file>.json --events   # 连事件序列一起比
```

退出码：`0` 完全一致 / `1` 有差异（会指出第几步、哪一步的哪个哈希） / `2` 文件不可用
（例如 D-159 之前的旧格式没有 `setup`，只能对照哈希、无法重建开局）。

⚠️ **时间源取记录里每步事件的 `at`，不能用「起点 + 步长」推算**。
`startRule` 会把 `ctx.now` 写进 `state.startedAt`，而原局用的是真实时钟；
用固定步长重放，第一步哈希就会对不上（实测踩过）。

⚠️ **开局随机游标跟着 `setup.rngCursor` 走**（D-269 / ADR-0058）。
每份记录都会写这个字段；重放时用它而不是「拿 seed 重新派生」，
所以以后换派生算法也不会让老文件失效。
**D-269 之前录的文件没有这个字段**，校验工具按 `0` 补 —— 那时的游标确实是 0
（也正是「每局固定起手」那个缺陷本身），补上后老文件依旧能逐帧校验。

### 7.3 运维开关：回放清理与限流（D-182）

两者都有默认值，**不配也能跑**。要调就设环境变量：

| 环境变量 | 默认 | 作用 |
| --- | --- | --- |
| `REPLAY_KEEP_DAYS` | `7` | 回放保留天数，更早的会被删 |
| `REPLAY_MAX_MB` | `500` | 回放目录总量上限，超出后从最旧的删 |
| `REPLAY_SWEEP_DRY_RUN` | 未设 | 设 `1` 时**只算不删**，日志里打「将删多少份 / 多少 MB」 |
| `RL_CREATE_PER_MIN` | `10` | 每连接建房次数/分钟 |
| `RL_JOIN_PER_MIN` | `20` | 每连接加入次数/分钟 |
| `RL_INTENT_PER_SEC` | `20` | 每连接 Intent 次数/秒 |
| `RL_MAX_ROOMS` | `2000` | 全局房间数上限 |
| `RL_MAX_CONNECTIONS` | `5000` | 全局连接数上限 |

行为要点：

- **清理在启动时跑一次，之后每 24 小时一次**；最近 1 小时内写过的文件**绝不删**
  （清理与落盘都是异步的，删到正在写的那份就是静默丢数据）。
- **限流按「连接」不按 IP**：走 frpc TCP 隧道时，所有公网客户端在服务端眼里都是 `127.0.0.1`，
  按 IP 罚会连坐所有朋友（`docs/20` §8.2）。将来上 VPS 直连才谈得上按 IP。
- 超限一律回人话（`操作太频繁，请等 N 秒再试`），**不断开连接** ——
  断线会让正常玩家以为是自己网掉了。

调整阈值想先看影响面时：

```bash
cd app
REPLAY_SWEEP_DRY_RUN=1 SERVE_STATIC=1 PORT=3100 pnpm --filter @app/server run start
# 日志里会有一行「回放清理（dry-run：只算不删）」带 scanned / removed / kept
```

## 9. 房间接口（Socket.IO）

事件名常量在 `packages/shared/src/constants.ts` 的 `SOCKET_EVENTS`，禁止在业务代码里写字面量。

| 事件 | 方向 | payload | 说明 |
| --- | --- | --- | --- |
| `room:create` | C→S | `{ nickname, capacity, format?, solo?, turnTimeoutMs?, deck?, commander?, opponentDeck? }` | 建房。**`capacity` 已不再生效**（T-07：房间恒 2 席，传几都一样）；`format` = BO1/BO3；`solo: true` = 人机房（服务端立刻坐入 AI）；`turnTimeoutMs` = 30/60/180/999 秒四档之一（H18，缺省或非法档位回落 60s）；`deck` = 30 个 `defId`；`commander` = 指挥官 `defId`（D-184，两者成对，不传即服务端默认）；`opponentDeck` = 人机对手用哪套基础卡组（`blade`/`frost`/`star`，D-314，缺省或非法值回落「按房码散列」） |
| `room:join` | C→S | `{ code, nickname, deck?, commander? }` | 加入；满员返回 `ROOM_FULL`。**没有 `faction`**（ADR-0042：不存在阵营，老客户端带了会被 strip，不报错） |
| `room:reconnect` | C→S | `{ playerId, token }` | 断线重连；返回快照（含 `lastSeqByPlayer`） |
| `room:leave` | C→S | — | 主动离开；房主离开则移交房主 |
| `room:ready` | C→S | — | 准备；满员且全员 ready → 服务端走系统 `game:start`（ADR-0019） |
| `room:next-game` | C→S | — | BO3 开下一小局，**仅房主**；第 2 局换先手、**第 3 局由上一局败者先攻**（H33 / D-145） |
| `room:rematch` | C→S | — | **系列赛打完之后**原地重开（D-309 / #125）：比分归零、重新掷骰定先后手、**双方都要点**（人机房单票即开）。与 `room:next-game` 是两件事，见 ADR-0076 |
| `room:deck` | C→S | `{ deck: string[], commander? }` | 准备页换卡组（**卡组与指挥官一起换**，D-184），**仅未开局**（BO3 局间也拒，H37）；空数组 = 回到服务端默认卡组 |
| `room:state` | S→C | 房间视图 | 房间变化时广播（**不含 token**；卡组只给 `deckSize`） |
| `game:intent` | C→S | `Intent` | 走完整处理链：去重 → 引擎 → reduce → 哈希 → 回放 → 广播 |
| `game:events` | S→C | 处理结果 | `accepted` 广播全房；`rejected` / `dropped` 只回发送方 |
| `game:snapshot` | S→C | 状态快照 | 重连 / 开局前下发**起点状态**；客户端必须先用它建立起点，否则那一批事件会被丢弃 |
| `game:timer` | S→C | `{ turnDeadline }` | 计时基线变更（D-310 / #155）：任何被接受的操作都会重新计时（ADR-0017），这条事件把新的截止时刻推给客户端。**刻意不用快照代替** —— 客户端收到快照会清空播放队列，等于掐断动画（ADR-0077） |
| `echo` | C→S→C | `{ message }` | 连通性自检，无业务含义（`EchoSchema` 校验；D-180 补进本表） |

要记住的三条：

1. **客户端须保存 `playerId` 与 `token`** —— 重连全靠它俩。
2. 重连后 **从 `lastSeq + 1` 续发** Intent，本地计数归零重来会被判 `STALE` 全部丢弃。
3. 断线席位保留 **60s（`RECONNECT_GRACE_MS`）**，超时由服务端巡检释放。两个时刻都要有反馈（D-233）：
   - **刚断开**：`markDisconnected` 后立即 `broadcastRoom`，对手顶栏出现
     「对手已断线（60 秒内可重连）」徽标（`data-testid="foe-offline"`，消费席位上的 `connected` 字段）；
   - **到期释放**：按「离开」处理 —— 对局中 → 以 `actor: 'system'` 的 `concede` 收尾
     （`reason: 'opponent-left'`）、BO 系列赛同时判负；局间（`awaitingNext`）→ 直接判负系列赛；
     随后再广播一次，留下的一方看到对局结束。

> ⚠️ 自建卡组的 `deck` 字段**必须在入站 schema 里显式声明**。`z.object()` 对未声明的键是
> strip，漏掉会让卡组被静默丢弃、服务端回退默认卡组，且没有任何报错。已由
> `server/src/schema.test.ts` 钉住。

## 10. 已知限制

1. **移动端未真机实测**：只做了 375 / 768 / 1440 三档视口渲染验证 + Playwright 390×844 的
   日志抽屉用例，触摸拖拽与安全区表现仍待实机确认。
2. **卡图与特效素材缺失**（X-14 / X-15 未给）：视觉为纯色 + 文字卡、动效靠 CSS。
   音效已有三条**程序化合成**的占位（打击 / 抽牌 / 结算，D-248），不依赖素材文件；
   真给素材包时只改 `client/src/sfx.ts`，调用点不动。
3. **图标与配色为占位方案**（X-14 未定）：纯色 + 文字卡。
4. **卡池不限体系**（ADR-0042）：45 张同池，随便混搭；服务端只校验张数 / 同名 / 不含指挥官，没有「阵营纯度」这回事。
   一套卡组 = 30 张主卡 + 1 位指挥官，**指挥官在卡组编辑里选**，不是一个单独的入口。
5. **准备后不能改卡组**：`room:deck` 只在 `lobby` 阶段接受；目前也没有「取消准备」入口。
6. **BO3 局间不能换卡组**：`awaitingNext` 时房间仍是 `playing`，`setDeck` 会拒 `DECK_LOCKED`。
7. **40 轮裁定只在单测覆盖**：E2E 跑 80 回合成本过高。当前口径是「血量高者胜、同血量进即死模式」
   （D-237 / H48），不再判和；即死模式下若双方都打不出伤害，理论可无限拖（H50，暂无兜底计时）。
8. **认输没有「取消」**：两段式确认（第一次点只是变红）是防误触，确认后不可撤销。
9. Tailwind 断点在 `client/src/style.css` 的 `@theme` 中定义，**没有** `tailwind.config.js`（v4 已移除）。
10. **限流阈值是经验值**（D-182）：建房 10 次/分、Intent 20 次/秒等，按「真人碰不到、脚本立刻撞墙」估算，
    尚未在真实多人负载下校准。要调就改环境变量（§7.3），不必动代码。
11. **回放观看入口置灰**（D-183）：结算面板的「查看回放（暂未开放）」可见但不可点 ——
    公网走隧道、每月流量有限，开放观看等于每次复盘都从服务器拉一份 `replay.json`。
    **记录不受影响**：服务端照常写 `app/replays/`（`replay:verify` 可校验，见 §7.2）。
    要开放就把 `client/src/features.ts` 的 `REPLAY_VIEW_ENABLED` 改成 `true` 并重新 build
    （客户端改动 `pnpm build` 后**即时生效** —— 静态资源每次请求读盘，不必重启服务）。
12. 工程内禁止使用 `xl:` / `2xl:` 变体 —— 五档断点已全部覆盖默认值。
13. **首屏体积**：`pnpm build` 后主 chunk 约 **122 kB gzip**（D-250 / ADR-0046 之后不再含 zod）。
    想加体积敏感的东西前，先确认它没有被 `@app/shared` 根入口顺带拖进来 ——
    **类型走 `@app/shared/types`、常量走 `@app/shared/constants`**，只有 `@app/shared` 根入口才带 zod。
14. **`defId` 硬编码与卡组合法性校验仍分散在多处**（T-06，暂缓）：能工作、有测试，但加第三套卡前
    值得先把 `cardFlags` 与共享校验抽出来。暂缓理由：纯结构收益，当前无缺陷、无阻塞。
15. **窄屏战报是抽屉而不是常驻列**（T-02 / D-251）：390px 竖屏要点「日志」展开；
    抽屉会盖住操作条，收起入口在抽屉底部（层级已确保可点）。
16. **建房 / 加房等 8 秒没有回应就判超时**（D-256 / `ACK_TIMEOUT_MS`）：正常局域网 100ms 级、
    公网经隧道 1s 级，8 秒足够；超时后提示「请检查网络后重试；一直不恢复就刷新页面」。
    提示条**粘在视口顶部**（`sticky`）—— 这是 D-256 的教训：提示画在屏幕外等于没有提示。
17. **D-259 之前录下的回放无法用新版本校验**（`replay:verify` 会在第一处分叉）：
    换牌从「第一个充能阶段」搬到开局前的独立阶段，`game:started` 之后的状态机分支变了，
    重算的 `stateHash` 与文件里记录的不一致。回放保留期 **7 天**，过期自动消失，故不做迁移。
    D-259 之后录的文件不受影响。
    **同理，D-290（血量 8→10）之前录的文件也校验不过** —— 开局血量取自常量，
    重算时按 10 铺状态，`initialHash` 第一步就与文件里的 8 血记录不一致（实测报
    「开局哈希不一致」）。这不是缺陷：规则数值变了，旧局本来就不该按新规则重放。
18. **换牌阶段没有「谁在换」的实时进度推送**（不需要，但值得知道）：顶栏的
   「对手换牌中 / 对手已确认」来自 `mulliganDone`，服务端每次提交都会广播整份状态，
   所以是准的；但没有逐张「对手换掉了 2 张」的可见信息 —— 换掉的牌进的是**卡组底**，
    对新手来说「对手换了什么」本来就不该也不能被看到。
19. **开局那句 toast（「已开人机房，对手是电脑」/「房间已创建」）会短暂压住顶栏中段**
   （D-262 实机自查发现，桌面与 390px 都有）：它压住的正好是「阶段 · 换牌」和
   「对手手牌 N 张」。toast 约 3 秒后消失，不影响操作；换牌阶段的其它标识
   （进度条紫色「换牌」标签、顶部换牌提示条、底部「不换牌」按钮）都不被遮挡。
   要改属于视觉决策（X-14），暂记为已知观感项。
20. **390px 下各区之间的高度权重还没定**（D-264 的剩余部分；与卡片溢出无关了）：
   「区域里的卡横向溢出、压到隔壁区」已在 D-264 修掉，而「堆叠区内容塞不下」
   在 D-265 换成**浮窗**后不再是问题 —— 五个堆叠区现在只占「区名 + 张数」那么高。
   仍然**没有**动的是「哪一排该高、哪一排该矮」以及「五区一行是否该拆成两行」，
   这会改变整桌观感，属于视觉决策，等 Era 定。
22. **没有内建聊天，对战桌右侧只有战报**（#122 / D-307）：`docs/22` N-09 定了第一版不做好友/私聊，
    原来那块「对话框（占位）」是**空承诺** —— 玩家会以为「有消息没加载出来」或「聊天坏了」，
    所以整块删掉了（不是加一句说明）。真要加聊天时，`aside` 那一列塞回去即可。
21. **充值/充能被连点时会出现一条「这张牌已经不在你的手牌或场上了」**
   （D-265 实机自查发现，桌面与 390px 都有）：这是**正常拒绝** —— 第一下已经充能成功、
   第二下用的是同一个 uid。提示已经改成人话（原来会把 40 位内部 uid 直接印在 toast 上）。
   真正的行为修正（请求在途时禁掉充能按钮）还没做，先记为已知项。
22. **换牌窗口到点的最后几毫秒仍可能接受一次换牌**（D-267 / ADR-0056 的代价项）：
   窗口只在服务端计时器里判定，计时器真正触发的瞬间之前，状态还是 `mulligan`，
   此刻到达的请求会被接受。结果无害（多换/少换一张），且提交是原子的，不会「接受一半」。
   换来的是「窗口只有一个裁决者」—— 原来 core 与计时器各判一次，一旦时长改成跟随房间档位
   就必然分裂，代价是换牌阶段直接卡死（issue #99 就是这条链）。
23. **D-267 之前的换牌窗口是固定 30 秒**，与建房选的回合档位无关。现在跟随时限，
   所以「建了 180 秒的房，换牌也是 180 秒」。想要更短的换牌窗口，可以把建房档位调小。

24. **回合交棒的那 1~2 秒里，顶栏显示「回合切换中…」且没有阶段提示**（D-268 / ADR-0057 的代价项）：
    这是刻意的 —— 事件逐条播放期间，「阶段已充能、席位还没换」的中间帧不是真局面，
    照着它给指引会误导（issue #101）。代价是交棒动画期间桌面「安静」一点。
    `turnPending` 有兜底：队列播空仍未复位就强制清除，不会卡在「切换中」。

25. **开发态（Vite dev server）仍会把缺失的 `.css` 回成 `200 + index.html`**（issue #107 的邻项）：
    生产形态已经改成 404（D-273），但 Vite 自己的 SPA 回退没变 ——
    所以本地「指向一个不存在的样式表」不会触发 `onerror`（浏览器把它当加载成功、解析出 0 条规则）。
    写这类用例要模拟**请求失败**（`route.abort()`），不要靠不存在的路径。
    只影响开发态，公网/生产不受影响。

26. **结算是对战桌上的覆盖层，牌桌与战报仍留在下面**（#154 / D-308 / ADR-0074）：
    一局打完不再整屏替换 —— 右侧战报照读、照滚，压暗的只是牌桌那一半
    （桌面端遮罩容器 `sm:right-40 md:right-56`，宽度与战报列同源）。
    结算卡片给三行摘要（回合数 / 双方最终血量 / 终局成因），右上角「收起」后
    只剩底部一条「查看本局结算 / 返回主界面」。
    终局期间操作条整体不渲染 —— 引擎在 `winner !== null` 之后会拒掉一切 Intent，
    界面留着按钮只会换来一句 `GAME_OVER`。
    **回放入口仍是置灰状态**（D-183），所以此刻战报就是唯一复盘手段。

27. **「再来一局」共用原房间，比分从 0:0 重来**（#125 / D-309 / ADR-0076）：
    结算卡片上的主按钮，点了**原地开下一局** —— 房间码、双方昵称、卡组、指挥官都不变，
    只有对局状态重置（血量 / 牌库 / 弃牌 / 除外 / 回合数 / 计时）。
    联机要求**双方都点**（点过的一方看到「等待对手确认…」，另一方看到「对手想再来一局」）；
    人机房的 AI 不会点按钮，玩家一票即开；对手已离开时按钮置灰并写明原因。
    ⚠️ 它与 BO3 的「开始第 N 局」不是同一个动作：那个比分继续累计、只有房主能点，
    只在系列赛**未**分胜负时出现；「再来一局」只在整场**已**结束（`phase === 'ended'`）时出现，
    两者不会同时在场。重开会把上一局的回放先落盘 —— **连打两局得到两份独立 `replay.json`**，
    不是一份追加。

28. **回合内任何被接受的操作都会让倒计时回弹**（#155 / D-310 / ADR-0077）：
    服务端本来就每次重新计时（ADR-0017），现在会把新的截止时刻推给客户端（`game:timer`）。
    此前客户端只从快照读 `turnDeadline`，于是界面一路数到 `0s` 停住、操作却仍被接受 ——
    那种「界面说超时、引擎说没超时」的状态不会再出现。
    ⚠️ 人机局的 AI 每动一手也会重新计时，所以**对手回合里时钟看起来几乎不动**，这是对的。

29. **打指挥官的战报不再写「裁决」**（#156 / D-311）：
    打脸没有防守方，也没有任何东西被破坏，现在只写
    `炎刃骑士 直击指挥官 → 造成 2 点伤害`（法术直伤写「对指挥官造成 N 点伤害」）。
    随从对撞仍然是「裁决 X vs Y → …」。旧回放不受影响 —— 引擎事件流没改，
    这一层只是渲染（ADR-0077 之外的另一条取舍：改文案不改协议）。

30. **操作发出后立刻有「在处理」的迹象，播完才恢复**（#158 / D-312）：
    点「推进阶段 / 结束回合 / 抽牌」的同一刻，按钮置灰并变「处理中…」，顶栏出现「同步中…」；
    播放队列排空后自动恢复。
    ⚠️ 恢复的判据是**逐条动画播完**，不是网络往返 —— 慢的从来不是网络，是播放
    （`FX_MS`）。所以按钮灰着的时长看起来比「请求耗时」长，这是对的。
    另有 10 秒兜底看门狗（`INTENT_WAIT_MS`），防止某条事件被吞导致按钮永久置灰。

31. **回合横幅贴顶，不进入随从格区域**（#159-1 / D-312）：
    「第 N 回合」原来出现在屏幕正中 —— 而那一刻玩家正要选格子放随从，它是
    `pointer-events-none`，于是「点得到、看不见」，最坏的一种遮挡。
    现在贴顶显示，字号也降了一档（390px 下 `text-2xl` 会撑到接近满宽）。
    伤害 / 裁决 / 收入是**结算**提示，此刻没有可点的操作，仍居中。

32. **指挥官区只显示血量，不显示张数**（#159-2 / D-312）：
    它恒有 1 张，那个 `1` 紧跟在「血 10」后面会被读成两位数。张数只在
    看不到卡的区域（弃牌 / 除外 / 费用区）显示。

33. **卡面费用就是实际支付**（#164 / D-313 / ADR-0079）：
    随从原来的「−1 费」已烘焙进 `cards.ts` 的 `cost`（24 张），
    `MINION_COST_DISCOUNT` 常量已删除，`costToPay(def)` 恒等于 `def.cost`。
    卡组编辑 / 局内手牌 / 卡牌详情 / 选择弹窗从此是同一个数字。
    ⚠️ **不要再加任何全局减费** —— 调价请直接改卡面 `cost`，
    定价约定写在 `docs/18 §3.6`。效果类临时减费（星轨传令）不受影响。
    0 费随从因此从 6 张变 12 张（占 40%），这是原来的事实被写到明面上，强度没变。

34. **人机房可以指定对手用哪套基础卡组**（#161 / D-314 / ADR-0080）：
    首页「人机对战」按钮左侧的紧凑下拉：不指定 / 炎刃 / 霜律 / 星轨，
    选择结果写进按钮文案（`人机对战（对手：炎刃）`）。
    **不指定 = 维持原行为**：服务端仍按房间码散列（同房码同对手，不同房会轮换）。
    非法 slug 不拒建房，静默回落散列 —— 这个字段只是偏好，不值得为它挡住开房。
    只影响人机：联机建房的协议入参与行为都不变。
    ⚠️ 该控件**必须与按钮同一行**：1366×768 下首页只剩 22px 余量，
    单独一行会把「编辑卡组」顶出首屏（`home-layout.spec.ts` 会红）。

## 11. 本轮验收清单（D-137 ~ D-149）

按顺序点一遍即可覆盖本批全部改动。两个浏览器窗口（或两台设备）各开一个客户端。

### 11.1 卡组接入开局（D-141 / D-143）

| 步骤 | 预期 |
| --- | --- |
| 主界面点「编辑卡组」→ 新建 → 加满 30 张（同名 ≤3） | 顶部显示 `30 / 30 张`，出现「设为开局卡组」按钮 |
| 点「设为开局卡组」 | 按钮变成「开局使用中」 |
| 返回主界面 | 「我的卡组」下拉已选中这套；未满 30 张的卡组是灰的并显示 `N/30` |
| 建房 → 进准备页 | 显示「本局使用：<卡组名>」 |
| 切换下拉到另一套再切回来 | 出现提示「卡组已更新」，本局使用那一行跟着变 |
| 双方准备 → 开局 | 我方牌库/手牌的卡来自这套卡组（挑一套混了别的体系的卡组，最容易看出来）；指挥官是这套自带的 |
| 编辑页点另一位指挥官 → 设为开局 → 开局 | 本方指挥官区显示**新选的那位**，主卡组仍是原来的 30 张（D-184） |
| 编辑页在「待选」的搜索框里输入「炎」→ 再输成「炎刃军」 | **一边打一边筛**，不用回车：标题变「命中 N / 44」，列表只剩名字含这串字的卡；点「清空」立刻恢复全部（D-186） |
| 搜索框里输入 `不存在的卡名` | 显示「没有卡名含「…」的卡」，不是一块空白 |

### 11.2 冻结口径（D-139）

| 步骤 | 预期 |
| --- | --- |
| 霜律方冻结对方一个随从（学徒/律令等） | 该随从横置并带冻结标记；霜痕 +1 |
| 对**同一个**随从再发动一次冻结类效果 | 选择浮层里**不出现**它；对方场上全被冻住时不弹选择 |
| 缚锁者登场时只能选到已冻结单位 | 走「抽 1 张」分支，不产生新的冻结与霜痕 |

### 11.3 指挥官伤害加成（D-137）

| 步骤 | 预期 |
| --- | --- |
| 星轨方指挥官点「攻击并展示（1 费）」 | 先展示、后结算伤害 |
| 展示中出现「星轨侍僧」 | 日志出现「指挥官本回合伤害 +1」，本次伤害为 2 |

### 11.4 设置法术（D-140）

| 步骤 | 预期 |
| --- | --- |
| 卡面类型徽章 | 显示「**设置**」而不是「持续」 |
| 打出炎刃战旗 / 霜律寒域 / 星轨环 | 卡留在法术区（不弃掉），效果持续生效 |
| 打出普通法术（如律令） | 结算后进弃牌区 |

### 11.5 认输与 BO3 第 3 局（D-147 / D-145）

| 步骤 | 预期 |
| --- | --- |
| 对局中点底部「认输」 | 按钮变红并改为「确认认输（本局判负）」，**不会立刻生效** |
| 再点一次 | 本局结束：认输方显示「本局败北」，对手显示「本局胜利」 |
| BO1 认输 | 直接显示「败北」并结束，没有「开始下一局」 |
| BO3 第 1 局认输（房主认输也算） | 出现「开始第 2 局」；点它进入第 2 局 |
| BO3 打到 1:1 后点「开始第 3 局」 | 第 3 局的**先手是第 2 局的败者**：先手方起手 5 张、后手 6 张 |
| 点「离开」 | 与认输不同：**判负整个系列赛**，不会再有下一局 |
| **待定选择浮层弹出时**（学徒冻结 / 焚典选牌等）点「认输」 | **可以点**（操作区压在浮层之上）；此时「推进阶段」「结束回合」不显示，因为它们必然被拒 |

### 11.6 展示区（D-149 / D-151）

| 步骤 | 预期 |
| --- | --- |
| 星轨 ≥3 层时点「攻击并展示」 | 双方半场的**展示区**各出现对应的卡（我方亮出，对手能看到） |
| 观察翻牌过程 | 卡**逐张**出现（每张约 0.18s），不是整批同时冒出来 |
| 观察展示区的卡 | 至少停留约 0.9s 后才归位；「展示时」效果（抽牌 / 打点 / 星轨 +1）在这段时间里结算，卡片不会闪一下就没了 |
| 结算结束 | 展示区的卡消失，日志不出现「展示区 → 卡组区」这类位移行，牌库底就是那几张（按翻开顺序） |
| 展示批次里有「展示时：抽 1 张」（守卫 / 星轨环） | 抽到的是**下一张**，不会把同批展示的卡抽进手牌 |
| 焚典 / 号令这类「看一眼但不离场」的翻牌 | 仍然显示在展示区（客户端回执），翻开后立刻归位，日志只写「展示：X」 |

> 若某项与预期不符，记下「卡组/指挥官 + 卡名 + 第几回合 + 你点了什么」，比截图更好定位。
