## 角色

你是本项目主程，负责把游戏规则实现为**纯函数**，不含任何 IO、网络、DOM、系统时间。

## 任务

在 `packages/core` 实现完整的规则引擎骨架 + 已确认槽位对应的规则。

## 具体要求

1. `types.ts`：`GameState`（不可变结构，含 `rngCursor`；业务字段如牌库/手牌/场面/资源/回合信息等**按 `docs/06` A 组输入确定**，未定的一律不写）、`PlayerState`、`RuleContext`。
2. `engine.ts`：
   - `applyIntent(state, intent, ctx): Result<GameEvent[], Rejection>`
   - `reduce(state, event): GameState`
   - `stateHash(state): string`（稳定序列化后哈希，用于双端一致性校验）
   - **不实现幂等去重**。`(playerId, seq)` 去重属于传输层职责，由服务端 Room 会话层持有（见 `ADR-0011`）：入 `GameState` 会让快照随回合线性膨胀并污染哈希；放在引擎外部持有则会破坏 `applyIntent` 的纯函数性质。本引擎只回答「给定 state 与 intent，是否合法、产出哪些事件」。
3. `rng.ts`：确定性伪随机（同种子同序列同输出），提供 `next()` / `nextInt(min,max)` / `shuffle(arr)`。
4. `registry.ts`：`rules: Record<string, RuleHandler>`，`register(type, handler)`。
5. `rules/`：每个机制一个文件，经 `registry` 注册。

   > **⚠️ 下面的清单只是目录骨架与命名风格演示，不是需求。**
   > 实际要建哪些文件、文件名叫什么、内容是什么，**完全由 `docs/06` A 组的实际输入决定**。
   > 若 Era 的玩法不含「攻击」「召唤失调」「费用」等概念，对应文件一个都不许建 —— **严禁把下列示例反向当成既定规则推导玩法**。
   > A 组未填时，本目录保持为空，或仅放一份 `README.md` 说明注册表的用法。

   _示例（假设玩法是某种回合制时可能的形态，不代表建议）：_
   - `draw.ts` 抽牌
   - `play-card.ts` 出牌
   - `attack.ts` 攻击
   - `end-turn.ts` 结束回合
   - `game-over.ts` 胜负判定（产事件，不直接改 UI）
6. 每个 handler 的固定结构：**校验 → 产事件 → 返回**。任何失败走 `Rejection`，且保证 `state` 零变更。
7. 所有规则文件顶部写注释块：机制名 / 触发时机 / 输入 / 产出的 Event 类型 / 边界情况。

## 约束

- 禁止 `Date.now()`、`Math.random()`、`fetch`、`require` 任何包以外的副作用。
- 禁止在 handler 里直接改传入的 `state`（用拷贝 + 返回新对象，或 Immer）。
- 不认识的 `intent.type` → 返回 `Rejection{ code: 'UNKNOWN_INTENT' }`，不得抛异常。
- 每个规则文件必须可独立单测，不依赖其他规则文件的内部实现。
- **系统 Intent 必须与玩家 Intent 走同一条链路**：回合超时产生的 `end_turn` 由服务端会话层构造 `{ actor: 'system', reason: 'timeout' }` 后喂给同一个 handler；不得在 `core` 内读时钟，也不得由会话层绕过引擎直接改状态（见 `ADR-0011`）。

## 验收（对应测试报告 M1）

- [ ] 每个 handler 至少 3 个用例：正常路径、边界、非法输入。
- [ ] 覆盖率 ≥ 80%（`pnpm test --coverage`）。
- [ ] 确定性测试：固定种子跑 100 次相同 Intent 序列，`stateHash` 完全一致。
- [ ] 幂等测试：同一 `(playerId, seq)` 提交两次，状态只变一次（**在服务端 Room 层验证**，非 `core` 层）。
