# 提示词 03 · 联网对战（房间 + 实时同步）

> 前置：提示词 02 已通过验收（规则引擎可单测跑通）。
> 本步产物：`D-103`。

---

## 角色

你是本项目主程，负责服务端权威的联网对战链路。

## 任务

实现「建房 → 加入 → 准备 → 开局 → 实时同步 → 断线重连 → 结算」的完整闭环。

## 具体要求

### 3.1 房间
1. `create_room` → 生成 4–6 位房间码（避免易混字符 `0/O/1/I`），返回房主 token。
2. `join_room(code, name)` → 席位绑定 socket，返回 `playerId + token`。
3. `list_rooms`（可选）、`leave_room`、`kick(playerId)`（仅房主）。
4. 全员 `ready` 后房主可 `start` → 服务端生成随机种子、初始化 `GameState`、广播 `game_started{seed, snapshot}`。

### 3.2 对战链路（严格按此顺序）
```
客户端 emit('intent', intent)
服务端：① 会话鉴权 ② 是否为该玩家回合并带合法 seq
      ③ 调用 core.applyIntent
         ├─ Rejection → emit('rejected', rejection) 仅回给发起者
         └─ 通过 → reduce → stateHash
                → 写 replay
                → 广播('events', { serverSeq, events, hash })
客户端：reduce → stateHash → 比对 hash → 不一致则 emit('desync') 并记录
```

### 3.3 健壮性
- 每个广播带单调递增 `serverSeq`；客户端发现缺口 → `sync_since(serverSeq)` 补发。
- 断线：席位保留 **60s（`RECONNECT_GRACE`）**，`reconnect(playerId, token)` 恢复并补发完整快照。
- 超时：某玩家 **30s（`TURN_TIMEOUT`）** 无操作 → 服务端自动结束回合。
  **实现方式强制约定（`ADR-0011`）**：会话层只负责「发现超时」（读时钟是会话层的事），然后构造一个**系统 Intent**：
  `{ type: 'end_turn', actor: 'system', reason: 'timeout', playerId: <当前回合玩家>, seq }`
  并喂给**与玩家完全相同的链路**（`applyIntent → reduce → stateHash → 写 replay → 广播`）。
  禁止两种写法：① 在 `core` 里读时钟（破坏纯函数，回放不可复现）；② 会话层绕过引擎直接改 `GameState`（`stateHash` 断裂，客户端 reduce 不出同一结果，且极难定位）。
- 重复/乱序 Intent 一律丢弃并记日志。
- **去重状态的归属**：`(playerId, seq)` 去重表由服务端 Room 会话层持有（`Map<playerId, lastSeq>`），**不进 `GameState`、不在 `core` 内实现**。理由是它不影响任何游戏结果，入 state 会让快照随回合线性膨胀并污染哈希。
- **幂等续接**：快照必须带 `lastSeq`；客户端重连后从 `lastSeq + 1` 续发，不得用本地计数归零重来。

### 3.4 可观测
- 每局结束落 `replays/<roomId>-<ts>.json = { seed, intents[], hashChain[], result }`。
  `intents[]` 必须**包含系统 Intent**（超时等由服务端构造的），否则回放会缺步、对不上终局哈希。回放以「种子 + Intent 序列」为粒度重跑规则引擎，可同时验证 handler 与 `reduce`（比只记 Event 序列更严格）。
- pino 结构化日志：房间生命周期、每次 Intent 的接受/拒绝原因、desync 告警。

## 约束

- 服务端是唯一的规则执行者；客户端不得本地结算。
- **单房间的 Intent 处理链必须同步完成**：`applyIntent → reduce → stateHash → 写 replay → 广播` 之间**禁止出现 `await`**。Node 单线程下这条链目前天然原子（两玩家同时出牌不会撞状态）；一旦插入异步（哪怕只是一个 `await redis.get()`），就会引入竞态，而这属于「通过了旧测试、在高并发时才偶发」的最难查那一类缺陷。确需异步（如持久化），放到整条链完成之后。
- 所有网络事件名与 payload 类型必须先在 `packages/shared` 定义并以 Zod 校验（运行时校验只在服务端入站处执行），禁止匿名 payload。
- 客户端对 `intent` 的调用必须走统一封装 `net/sendIntent()`，禁止在组件里裸调 socket。

## 验收（对应测试报告 M2 / M3 / M4）

- [ ] 两台设备（PC + 手机同局域网）可互相加入同一房间并打完一局。
- [ ] 全程 0 次 desync（双端 `stateHash` 一致）。
- [ ] 拔网线 60s 内（`RECONNECT_GRACE`）重连，手牌、场面、回合数与断线前完全一致。
- [ ] 断网 61s（超窗口）按设计判负或释放席位，不允许出现「重连成功但状态丢失」的中间态。
- [ ] 重连后连发 3 次操作均被正常结算（验证 `lastSeq` 续接，避免全部被判重复丢弃）。
- [ ] 重发同一 Intent 两次，服务端只结算一次（Room 层去重）。
- [ ] **超时验证**：玩家挂机 31s，服务端自动结束回合，客户端显示的对局状态与服务端一致（验证 `stateHash` 未断裂、超时事件回放可复现）。
- [ ] 关闭服务端后客户端有明确断线提示与重连进度。
