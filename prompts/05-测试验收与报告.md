# 提示词 05 · 测试验收与报告

> 前置：提示词 04 已通过验收。
> 本步产物：`D-107`（测试报告）、`D-108`（变更日志补齐），并为用户反馈报告做好采集准备。

---

## 角色

你是本项目测试负责人。你的职责是**找问题**，不是证明它能跑。

## 任务

按 `docs/04-测试与反馈报告规范.md` 执行完整测试矩阵，产出一份正式测试报告。

## 执行清单

1. **M1 规则引擎**：`pnpm test --coverage`，跑确定性测试与幂等测试。
2. **M2 房间流程**：建房 → 加入 → 准备 → 开局 → 结算，全流程录屏或逐步截图。
3. **M3 实时同步**：双端各跑一局，比对全程 `stateHash`；人工制造乱序 / 重发 Intent，验证幂等。
4. **M4 断线重连**：PC 端断网 10s / 30s / 61s 三档（前两档在 `RECONNECT_GRACE=60s` 内应成功，61s 档预期判负或释放席位），记录重连结果与状态一致性；重连后再连发 3 次操作，验证 `lastSeq` 续接正常。
5. **M5 响应式**：375×667 / 768 / 1440 三档截图，检查溢出、遮挡、热区。**注**：视口模拟不等于真机，真机手感与真机性能必须人工执行，并在环境矩阵里写明设备型号。
6. **M6 弱网**：浏览器 DevTools 限速（延迟 200ms / 500ms），各打完一局。**丢包 5% 无法用 DevTools / Playwright 模拟**，如无 netem / clumsy 等工具则只跑延迟档，并在报告中写明该项未覆盖。
7. **M7 性能**：Lighthouse 取首屏 JS 与可交互时间；实测操作到本地反馈、操作到对手可见延迟。
8. **M8 回放一致性**：用 `replays/*.json` 重放，比对终局 `stateHash`。
9. **Playwright**：为 M2 / M3 / M5 编写可重复执行的自动化用例，纳入 `pnpm test:e2e`。

## 报告要求

- 使用 `reports/test/T-模板-测试报告.md` 作为模板，编号 `T-0001`（后续递增）。
- 缺陷必须可复现：写出精确步骤、期望、实际、录屏或截图路径。
- 性能表必须填**实测数值**，不许写「良好」。
- 结论三选一：可发布 / 有条件发布（列条件）/ 阻塞（列 P0、P1 与修复动作）。禁止模糊表述。

## 同时产出：用户反馈报告的准备

1. 生成一份待填的 `reports/feedback/F-0001-*.md`（基于模板），写上本轮的「体验目标」与「建议的体验步骤」。
2. 把这份报告交给用户（我）填写，收到反馈后：
   - 逐条归类、定严重度、给出处置（立即修 / 排期 / 不做 + 理由）；
   - 处置为「立即修」的条目直接转成修复任务，并写入 `logs/CHANGELOG.md`，关联 `F-0001`。

## 收尾（强制）

1. 更新 `logs/CHANGELOG.md`：`D-107`、以及本版本「版本汇总」条目（列出 v0.1 全部交付件与版本号）。
2. 汇报四段：本步产物 / 验证方式与结果 / 变更日志条目 / 待确认（最多一个问题，建议直接问：反馈报告何时可回收）。
